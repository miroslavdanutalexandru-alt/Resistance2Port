# Resistance 2 — native PC port/recomp (work in progress)

A static recompilation of the PS3 game *Resistance 2* into a native Windows program. No emulation of the CPU: the game's PowerPC and SPU code is translated to C/C++ and compiled for your PC. Graphics go through RPCS3's Vulkan renderer, with NVIDIA DLSS / AMD FSR upscaling, 60 fps, keyboard and mouse controls, and higher resolutions.

> ⚠️ **Not Perfect.** I have only tested it **on my PC** (Ryzen 5 5600X, GeForce RTX 5070, 32 GB RAM, Windows 11, 1080p screen) and haven't beaten the game. The campaign has been played through the opening Iceland levels; past that it's untested, so things could go wrong. Some crashes or freezes may happen.

> **No game files and no translated game code are distributed, in this repository or in the installer.** You need your own copy of the game. Setup decrypts its program on your PC, translates it into C/C++ and builds the game there; the generated code and the built game never leave your PC, and no prebuilt game program is released. The repository holds the port's own code plus the small references it needs to find its place in the game's program: function addresses, patch values and short context lines from the generated code (`tools/hooks/` and `project/r2_patches.cpp`).

## What you need

- A PC running Windows 10 or 11 (64-bit).
- A CPU with AVX2: Intel 4th gen or newer, or any AMD Ryzen. Older CPUs get the slower variant without AVX2 (`build_baseline\`, built by setup); its minimum is SSE4.1 (Intel Core 2 Penryn / 45 nm or newer, AMD Bulldozer / FX or newer). On a CPU below that, the game says the processor is below the minimum (SSE4.1) and exits; setup skips the variant without AVX2 only when Windows reports SSE4.1 as missing (older Windows 10 versions can't tell, and then it is built as usual).
- A Vulkan 1.3 GPU. DLSS needs a GeForce RTX card; everything else (including FSR) works on AMD, NVIDIA and Intel. Only tested on NVIDIA so far.
- Your own dump of **Resistance 2, EU disc (BCES00226), version 1.00**. This is the folder that contains `PS3_GAME`, the same kind of folder RPCS3 uses. Other regions and patched versions are not supported yet.
- About 35 GB of free disk space: ~22 GB for the game files and the rest for the build tools and the build.
- An internet connection for the setup.

## Install

**Quick install (recommended):**

1. Download the release zip from the Releases page and unzip all of it to a folder with no spaces in the path, for example `C:\Games\Resistance2Port`.
2. Run **`Setup.exe`** in that folder. (It is not code-signed: if Windows says *"Windows protected your PC"*, click **More info → Run anyway**.)
3. Pick your game: **ISO...** or **Folder...**. Setup checks the copy at once and says what to do if it can't be used (see *If your game copy is not accepted* below).
4. Click **Install** and wait. Setup lists the build tools that are missing, says what each one is for and where it comes from, and asks before installing them (system-wide with one administrator prompt, or, experimental, portable inside the port folder; [details](docs/INSTALL.md#build-tools)). Then it copies your game files, builds the game with as many parallel jobs as your RAM allows, adds Start-menu and desktop shortcuts and starts the launcher. It shows the progress and the time left. If it stops (error, sleep, power cut), run `Setup.exe` again and click **Resume**.

The release contains no game code: the game is always built from your own copy. Requirements, disk space, build times, uninstalling and troubleshooting (SmartScreen, antivirus, low RAM, no winget): [docs/INSTALL.md](docs/INSTALL.md).

### Manual install (advanced)

**With the Inno installer** (if a `-Setup-<version>.exe` is on the Releases page): download `Resistance2Port-Setup-<version>.exe` from the Releases page and run it. It installs the port (default `C:\Games\Resistance2Port`), adds Start-menu and desktop shortcuts, and asks for your game. It lists the copies it finds on the PC (common folders and RPCS3's game list); you can also type or paste a path, or use the **ISO...** / **Folder...** buttons. It checks the copy before going on and says what is wrong and what to do if it can't be used (see *If your game copy is not accepted* below). At the end it opens **Setup**, the window with the progress bar, with your game already filled in: click **Install** there (step 2 below). The installer contains only the port; the game files always come from your own copy. Use a decrypted ISO or a game folder (the same kind RPCS3 uses). Tick **Portable mode** to keep settings only in the install folder. The install folder can't contain spaces (the build tools need that): a folder with spaces handed to the installer before its folder page (RecompLauncher suggests `C:\Recomp Library\...`) is replaced with the previous install's folder or `C:\Games\Resistance2Port`. The Start-menu shortcut is named *Resistance 2 PC Port (Resistance2Port)* so RecompLauncher recognises the install (it matches two words of the shortcut's name; an update removes the old *Resistance 2 PC Port* shortcut, and the uninstall entry is unchanged). RecompLauncher then finds the game through that shortcut and reads `recomplauncher.json` in the install folder.

**By hand:**

1. Download this repository: click on Code at the top, then Download ZIP, then unzip it somewhere with no spaces in the path, for example `C:\Games\Resistance2Port`.
2. Double-click **`Setup.bat`**. It will:
   - list the free build tools that are missing (Visual Studio 2022 Build Tools, LLVM 22 or newer, CMake, Ninja, Python, Git), what each is for and where it comes from, and ask first: **S** installs them system-wide with `winget`, **P** puts them only into `tools_cache\` in the port folder (experimental), **N** stops. `Setup.bat -RemoveTools` removes what Setup installed again ([docs/INSTALL.md](docs/INSTALL.md#removing-the-build-tools));
   - look for your game (an ISO or a game folder), check it, then copy it into the port folder (or move a folder, if it's on the same drive);
   - decrypt the game's program file, using the application keys from RPCS3's public source code;
   - download RPCS3's source at a fixed version and apply this port's renderer patch (`ps3recomp/patches/r2-rpcs3.patch`);
   - generate the game code from your copy and build the game.

   The first run takes a while: tool installs plus a 20–60 minute build. At the end, Setup offers to put a "Resistance 2" shortcut to the launcher on your desktop.
3. Play with **`Launcher.exe`**. It has the settings (display mode, resolution, frame rate, VSync, anti-aliasing, upscaling, texture filtering, sharpening) and the key bindings.

You only need to run Setup again after downloading a newer version of the port; otherwise just use the launcher.

**Choosing the game in Setup.bat:** it lists the copies it found, numbered. Type a number, or type or paste the path of the ISO or game folder (you can also drag it into the window). **B** opens a file picker (Windows only). `Setup.bat -Game "<path>"` skips the question. The path can be an ISO, the game folder, or a file inside it. An ISO is opened by Windows, copied from and closed again; if Windows can't open it, Setup reads it directly.

### Setup FAQ

- **Why does the first setup take so long? Is it a one-time thing?** Mostly, yes. The first run installs the build tools (10-30 minutes, once per PC), copies your game (5-15 minutes) and then compiles the whole game from your copy. That compile is the long part: the generated game code is split into a few very large files, each needing up to 8 GB of RAM, so a PC can only compile as many of them at once as its RAM allows. Measured on a 12-thread desktop CPU: about 35-50 minutes with 32 GB of RAM, about 1.5 hours with 16 GB, about 2 hours with 12 GB; slower CPUs, laptops on battery and antivirus scanning add to that. Setup prints its own estimate and the time each step took (in `logs\setup.log`).
- **Updates are much faster.** Unzip the new version **over your existing port folder** (overwrite the files) and run Setup again: the tools, your game copy, the generated code and the compiled files are reused and only what changed is rebuilt, usually in 5-20 minutes. Unzipping into a **new** folder starts the game copy and the build from scratch again (the tools are still reused). When an update changes the code generator, Setup notices it by itself and generates the game code again (10-25 minutes; the first update after 0.2.3 does this once). Generated files that come out the same keep their date, so only the files that really changed are compiled again.
- **Making the first build faster:** close browsers and games while it runs (free RAM = more files at once); put the port on an internal NTFS drive (not a USB/exFAT drive or a network drive); optionally exclude the port folder from Microsoft Defender's real-time scan (Windows Security, *Virus & threat protection > Manage settings > Exclusions > Add an exclusion > Folder*), which otherwise scans every file the build writes. Setup tells you if Defender is scanning the folder; it never adds the exclusion itself.
- **"fatal: not in a git directory" / "detected dubious ownership" while fetching RPCS3:** fixed in Setup after 0.2.0 (GitHub issue #5). It happened on exFAT/FAT32 drives (most external and USB drives), network drives and folders owned by another Windows account, where Git can't confirm the folder's owner. Update the port, or move it to an NTFS drive (for example `C:\Games\Resistance2Port`).
- **How much disk space does it take, and what can I delete?** A finished install is about 35-40 GB: your game copy (`gamefiles`, the largest part), the generated code (`recompiled`), the compiled files (`build*` folders) and the tools. Keep them all: the build folders are what makes updates fast. Setup no longer copies the disc's bonus videos (`PS3_CONTENT`) or system update (`PS3_UPDATE`), which the game never reads, and deletes them and its work folder (`build_regen`) after a successful build. At the end Setup prints how much each part takes; run `powershell -ExecutionPolicy Bypass -File tools\build_doctor.ps1 -DiskUsage` to see it again. It also points out folders Setup did not make, such as a second copy of the port left by unzipping an update into a subfolder. Your original ISO or game folder is not needed after Setup has finished.
- **Can I keep the game files (`gamefiles`) on another drive?** Yes. Move the whole `gamefiles` folder (or copy it and delete the old one when the game works), then in the launcher open **Saves & tools > Game files folder > Choose folder...** and pick it (the folder that holds `PS3_GAME`; picking the folder above it, `PS3_GAME` or `USRDIR` also works). The launcher checks that the game's files are there (`PS3_GAME\PARAM.SFO`, `USRDIR\EBOOT.BIN`, `USRDIR\packed\game\game.psarc`) and that it can write there, and offers to copy the game's install data (`game\BCES00226` inside the game files folder) along, so the game does not install again. The game, the launcher's updates and rebuilds (Setup), Setup.exe, trophies, the HD UI pack and the problem report all use that folder from then on; **Use default** goes back to `gamefiles` in the port folder. Your saves do not move: they stay where *Save location* puts them (`gamedata` in the port folder by default). The path must be a full path in plain English letters (no accents, `%`, `!` or `"`), at most 200 characters. A `PS3_VFS_ROOT` you set yourself (in Windows' environment variables, or by hand in `run.bat`) wins over the launcher setting; updates replace `run.bat`, so the launcher setting is the one that lasts. Setup can also be pointed at a folder once with `setup.ps1 -GameFiles <folder>`. Uninstalling only ever deletes `gamefiles` in the port folder, never a folder you picked.
- **"ninja: error: manifest 'build.ninja' still dirty after 100 tries" and other build errors:** the "still dirty" error came from files dated in the future (the release zip's time zone, or a PC clock that was set wrong), which made the build loop. Fixed in 0.2.2: every build now resets such dates first. If a build still fails, Setup shows the first error and tries once more with a fresh build configuration (the files already compiled are kept). It does the same after the port folder was moved. To do it by hand: `powershell -ExecutionPolicy Bypass -File tools\build_doctor.ps1 -ResetConfig`, then run `build.bat` or Setup. `-FirstError` shows the first error from `logs\build.log` / `logs\build_rpcs3.log`; include that line and `logs\setup.log` when reporting a problem.

### If your game copy is not accepted

The installer and Setup check the copy before copying anything. The supported version is **Resistance 2 (EU disc, BCES00226)**, about 23.3 GB.

| Message | What to do |
|---|---|
| compressed archive (.zip, .7z, .rar) | Extract it first, then pick the ISO or folder inside. |
| PlayStation Store package (.pkg) / game update folder | Pick the disc copy. Game updates are not needed. |
| not &lt;game&gt; / from another region | Use the supported disc version listed above. |
| PlayStation Store version | Only the disc version is supported. |
| encrypted disc image / PARAM.SFO is not valid | Decrypt the ISO first (for example PS3Dec with the disc key from the `.dkey` file), or use a game folder from a PS3 or RPCS3. |
| program file was decrypted or replaced (plain ELF) | Use the original, unmodified files. Setup decrypts them itself. |
| files are missing / smaller than expected | The copy is incomplete. Copy or dump it again. |
| different from the known file (warning) | The copy may be modified. You can continue; Setup stops later if the decrypted program is not the supported version. |
| not enough free space | Free up space, or install on another drive. |

The checks run on your PC only. Nothing is uploaded.

**Updates:** the launcher checks this repository's Releases page once at start. The *Updates* option (Advanced page) picks what happens when a newer version is out: **Notify** (default) asks **Update now** / **Release page** / **Skip version**; **Auto-install** asks once, then updates; **Off** does not check (also `PORT_NO_UPDATE_CHECK=1`; `PORT_UPDATE_NOTIFY_ONLY=1` brings back the old notice that only opens the release page). *Update now* closes the launcher and runs `tools\update.ps1`: it downloads the release zip (checks its size and SHA-256), waits for the game to close, replaces the port's files, runs Setup in update mode (incremental: usually 5-20 minutes) and starts the launcher again. Your settings, key bindings you changed, saves, logs, game copy, generated code, build folders and shader caches are kept; a file is deleted only if an older release shipped it and you did not change it. If anything fails, the previous files are put back (log: `logs\update.log`; `tools\update.ps1 -Rollback` undoes an interrupted update, `-DryRun` only shows what would change). Git checkouts (`git pull`, then Setup) and copies installed by RecompLauncher (update them there) only get the notice. The installed version is in the `VERSION` file.

**Settings and controls** (`settings.ini`, `settings.bat`, `controls.txt`, `mouselook.cfg`) are also kept in `%USERPROFILE%\Saved Games\Resistance 2\config`. Missing files are restored from there when the launcher or game starts, so they survive reinstalling or updating the port. To keep everything in the port folder only, create an empty file named `portable.txt` next to `Launcher.exe` (the installer's *Portable mode* does this). Saves are still kept in the port folder (`gamedata`); the uninstaller asks before deleting it, and its default is to keep it.

**No console window:** the launcher starts the game without a console. The game's output goes to `logs\run.log`.

**First launch:** the game shows its own one-time setup screens and an autosave notice. Before the game starts, the launcher prepares the shader cache from your game files (a progress panel; **Skip for now** or Esc skips it), and the game then compiles every known shader behind a **Compiling shaders N / M** panel (see *Shader precompile*), so levels play without shader stutter from the first visit. Shaders are cached for later starts.

## Controls

Keyboard and mouse are supported out of the box (WASD, mouse look, Mouse1 fire, Mouse2 aim, R reload, G grenade, E use, V/Mouse4 melee, Q / wheel switch weapon, T flashlight, M map, Esc pause). Controllers work too. All keyboard and mouse bindings can be changed in the launcher.

**Button prompts follow the device you used last.** Touch the keyboard or mouse and the on-screen prompts (hints, menu legends, tutorial text) show your keys; press a button or move a stick on a controller and they switch to that controller's buttons. Switching is instant and works mid-game. With an Xbox / XInput controller (or any non-PlayStation pad) the prompts show Xbox buttons, drawn by the port as simple coloured letters (no copied artwork):

| PS3 | Xbox | PS3 | Xbox |
|---|---|---|---|
| Cross | A | L1 / R1 | LB / RB |
| Circle | B | L2 / R2 | LT / RT |
| Square | X | L3 / R3 | LS / RS (stick click) |
| Triangle | Y | Select / Start | View / Menu |
| D-pad | D-pad | Left / right stick | Left / right stick |

With the XInput backend (`PAD_BACKEND=xinput`), a Sony DualShock 3/4 or DualSense that is plugged in (detected by its USB/Bluetooth ID, used through DS4Windows / Steam Input as XInput) keeps the PlayStation symbols; with SDL3 (default) the prompts follow the controller type, see *Controllers (SDL3)* below. The launcher's **Controller button prompts** option forces Xbox or PlayStation. Prompts name the game's default button layout; if you remap buttons in the game's own options, the prompts still name the default ones.

**Mouse look is direct:** raw mouse counts turn the camera's yaw and pitch each frame (× the launcher's sensitivity × the game's own Look Sensitivity), not an emulated right stick — no acceleration, dead zone or speed cap. While aiming down sights the turn rate is scaled by the scope zoom so the same mouse movement covers the same part of the screen (`R2_ZOOM_SENS`: 1 = default, 0 = no scaling, up to 2). The game's aim assist only acts on stick input, so it doesn't pull against the mouse, and while the mouse is in use the right stick's turn rate is ignored so the two never add up. Mouse counts made while the camera isn't yours (menus, pause, cutscenes, scripted sequences) are dropped, so the view doesn't jump afterwards. The launcher's **Mouse aiming = Classic** switches back to stick emulation. The game has no mouse pointer in its menus; they are driven by the keyboard (arrows / Enter / Esc) or a controller. F8 frees the cursor.

**Controllers (SDL3).** The port reads controllers through SDL3 (built in, no extra DLL): Xbox, DualShock 4, DualSense, DualShock 3 (with its Windows driver), Switch Pro and Joy-Con work directly, over USB or Bluetooth. **DSX, DS4Windows and Steam Input are not needed**, and work best closed: they can hide the real controller from other programs (HidHide) and show only their virtual Xbox pad. If they run anyway and the port sees both the real controller and the tool's virtual copy, the copy is recognised by its mirrored input and ignored, so it doesn't become a ghost player 2 (with local co-op off, the default, a second controller never becomes player 2 anyway). Controllers can be plugged in and out at any time, no restart, up to 8. Rumble works on every pad that has it (DualSense included), and a DualShock 4 / DualSense light bar shows the player's colour (player 1 blue, player 2 red). If SDL3 can't start, the port falls back to XInput automatically (`logs\run.log` shows `[cellPad] controllers: SDL3` or `SDL3 could not start`; a build made without SDL3 says `controllers: XInput only`). If a controller isn't seen, `logs\run.log` lists every controller SDL3 found (`[pad-sdl3] controller 1: ...`), controllers it can't use, and notes when HidHide or a Steam setting may be hiding one.

**Button prompts by controller type:** with *Controller button prompts = Auto*, a PlayStation pad (DualShock 3/4, DualSense) shows PlayStation symbols and an Xbox or other pad shows Xbox letters. Switch controllers are read by button position (the bottom button is Cross); with *Nintendo button layout = Nintendo style* A (right) confirms and B cancels as on a Switch, and the prompts show the Xbox-style letters. Under Steam Input the real controller type is used when SDL reports it; otherwise set the prompts by hand.

**Gyro aiming** (DualShock 4, DualSense, Switch Pro, Joy-Con; off by default): turning the controller turns the view, added directly to the camera like the mouse (smooth, not limited by the stick). *While aiming* only uses it with the Aim button (L1 / LB) held. Leave the controller still for about a second after it connects so the resting drift is calibrated. In split-screen co-op each player's gyro moves only their own view (as a right-stick input, like the second player's mouse).

| Option (launcher Controls page / in game *More PC Options*) | Values | Variable |
|---|---|---|
| Controller support | **SDL3**, XInput | `PAD_BACKEND=sdl3\|xinput` (restart). `sdl2` is accepted and uses SDL3 |
| Gyro aiming | **Off**, On, While aiming | `PAD_GYRO=0\|1\|aim` |
| Gyro sensitivity | **2x**, 0.5x-6x | `PAD_GYRO_SENS=<0.05..20>` (view degrees per controller degree) |
| Gyro vertical | **Normal**, Inverted | `PAD_GYRO_INVERT_Y=1` (on top of the game's own invert setting) |
| Gyro turning axis | **Controller**, Player | `PAD_GYRO_SPACE=local\|player` (player = yaw around gravity, works flat or upright) |
| Gyro calibration | **On connect**, Off | `PAD_GYRO_CALIBRATE=0` turns off the 1 s still-calibration |
| Light bar | **Player colour**, Off | `PAD_LIGHTBAR=0` |
| Nintendo button layout | **By position**, Nintendo style | `PAD_NINTENDO_SWAP=1` |
| Stick outer deadzone | **Off**, 5 %, 10 %, 15 % | `PAD_OUTER_DEADZONE=<0..50>`: that much of the stick's edge already counts as full deflection (worn sticks) |
| Stick anti-deadzone | **Off**, 10 %, 20 %, 30 % | `PAD_ANTI_DEADZONE=<0..50>`: the smallest movement past the deadzone starts at this much, skipping the game's own deadzone |
| Trigger deadzone | **Off**, 10 %, 20 %, 30 % | `PAD_TRIGGER_DEADZONE=<0..90>`: L2 / R2 count only past this much travel (rescaled after it) |
| Turn boost | **Off**, 90, 180, 270 deg/s | `PAD_TURN_BOOST=<deg/s>`: right stick held at the edge for a moment ramps in extra turn speed (0.35 s), added like gyro/mouse turning; not while aiming |
| Crouch button (experimental) | **As the game**, Toggle, Hold | `PAD_CROUCH_MODE=toggle\|hold` (L2 / LT, player 1): the port turns presses into a held button (toggle) or taps on press and release (hold). In Resistance 2 the same button also sprints while you run, so sprint follows the same mode |
| Sprint button (experimental) | **As the game**, Toggle | `PAD_SPRINT_MODE=toggle` (L2 / LT held while running, Shift on keyboard): once you are sprinting, letting go keeps the sprint going until you stop moving (about a quarter of a second) or press the button again; a quick tap still crouches. Resistance 2 already sprints only while the button is held, so there is no Hold choice. Not used when Crouch button is Toggle or Hold |
| Weapon wheel on keyboard & mouse (no launcher option) | **On**, Off, Left stick only | `PORT_KBM_WHEEL=0\|left`: while the weapon wheel key (Q) is held, moving the mouse toward a slot (or WASD, diagonals full length) picks it, and the choice stays until you let go of Q; the view holds still meanwhile. The direction goes to the left stick and, with direct mouse look, the right stick. `0` = old behaviour; `left` = left stick only |
| Vibration | **100 %**, 75 %, 50 %, 25 %, Off | `PAD_RUMBLE=<0..100>` (`off` = 0): both motors scaled; Off also tells the game rumble is off (system setting) |
| Confirm button | **Cross**, Circle | `PS3_ENTER_BUTTON=circle`: the PS3 system setting the game reads at start (Japanese layout: Circle accepts, Cross goes back). Keyboard Enter / Esc / Backspace keep meaning confirm / back in menus. Restart; a menu that hard-codes its buttons ignores it |
| Controller in the background | **Auto**, On, Off | `PAD_BACKGROUND_INPUT=1\|0`: Auto = controllers keep working while another window has the focus only with *Keep running* or *Mute only* in the background (SDL's background-events hint is always on; the port decides) |
| (no launcher option) | **On** | `PAD_DEDUP=0` keeps virtual duplicates (DSX / Steam Input / DS4Windows / ViGEm) as separate controllers. With it on, a controller that connects while another one is playing joins once it is used on its own; one that copies several different inputs of the other controller is ignored until several different buttons are pressed on it while the other controller is untouched (and is still watched after that) |
| (no launcher option) | **360** | `PAD_GYRO_STICK_DPS=<deg/s>`: gyro speed that equals a full right stick (co-op / classic mouse aiming, where gyro drives the stick) |

With `PAD_BACKEND=xinput` the old behaviour returns: XInput only (up to four), PlayStation pads through DS4Windows / Steam Input, no gyro or light bar.

## Local co-op

Two players on one PC, split-screen, as on PS3. No PSN account is needed: the port provides a second local user.

**Starting it:** in the launcher, Controls page, set **Local co-op (split-screen)** to **On** (it is off by default, so a second controller, or a virtual copy of your controller made by DSX / DS4Windows / Steam Input, can't start split-screen by itself). Plug in two controllers (or one, with *Player 2 uses keyboard and mouse*). Main menu → **Co-op** → the offline / split-screen co-op staging screen (the online options need PSN and don't work). On the staging screen player 2 presses **START** (or Enter / Esc on the keyboard for a keyboard player 2) to join: on PS3 this opens the "select a user" box; the port answers it at once with a local user named **Player 2**, and player 2 shows as logged in. Start the mission and the screen splits.

Only the offline, split-screen part of co-op works: everything that needs PSN (online co-op, competitive, the lobby browser) stays unavailable.

**Who is who:**

- With local co-op off (the default): one player. Player 1 = the keyboard and mouse plus **the controller you used last**: pick up any connected controller and press a button, and it takes over. The game never sees a second controller.
- With local co-op on: player 1 = the keyboard and mouse plus the first controller found.
- Player 2 = the next controller. A controller keeps its player while it stays plugged in. A controller plugged in later takes the lowest free player; when one is unplugged, its player has no input until it is plugged back.
- With two local players the direct mouse look is off. The mouse then moves the keyboard player's view like a right stick (it would otherwise turn both heroes).

**Options** (launcher, Controls page; or `settings.bat`):

| Option | Values | Variable |
|---|---|---|
| Local co-op (split-screen) | **Off**, On | `PAD_COOP=1`: a second controller can join as player 2. Off (`PAD_COOP=0` or unset): the game sees only player 1, and extra controllers (or duplicate virtual pads from DSX / Steam Input / DS4Windows) can't join. *Player 2 controller* and *Player 2 uses keyboard and mouse* apply when it is On (outside the launcher, with `PAD_COOP` not set at all, setting `PAD_P2_CONTROLLER` or `PAD_P2_KEYBOARD` turns it on) |
| Player 1 controller | **Automatic**, Controller 1-8 | `PAD_P1_CONTROLLER=<1..8>`: the controller that is player 1 (SDL3: in the order they were connected; XInput: 1-4, Windows' XInput order). Automatic = the controller used last (co-op off) or the first one found (co-op on) |
| Player 2 controller | **Automatic**, Controller 1-8 | `PAD_P2_CONTROLLER=<1..8>`: the controller that is player 2 (numbered as above) |
| Player 2 uses keyboard and mouse | **Off**, On | `PAD_P2_KEYBOARD=1`: player 1 = the first controller only, player 2 = keyboard and mouse |
| (no launcher option) | **2** | `PS3_LOCAL_USERS=<1..4>`: local users the game sees. `1` = player 2 can't sign in. `PS3_USER2_NAME=<name>` renames player 2 |

`logs\run.log` shows which controller each player got (`[cellPad] player 2 <- controller 2`) and when the game counts two local players (`[coop] local players: 2`).

**A real second controller is ignored?** With the duplicate check on, a controller that is plugged in while another one is playing joins once it is used on its own, and one that copies the other controller's inputs is ignored (`logs\run.log`: `... ignored as a duplicate`). If a real second co-op controller is ever ignored, unplug it and plug it back in; `PAD_DEDUP=0` turns the duplicate check off.

**Known limits:** Player 2's progress and settings are not saved separately (as on PS3 for a guest player). If you use NVIDIA DLSS, it may not work right in split-screen. Turn it off (or use FSR / no upscaler) for co-op if the image smears or one half looks wrong.

## Online (experimental)

Off by default; nothing here touches the network unless you turn it on. This is groundwork, not working online play: see the limits below.

**Turning it on:** launcher, Controls page → **Online (experimental)** → On (or `set PORT_ONLINE=1`). Copy `online.ini.example` to `online.ini` next to `run.bat` and put in **your own** RPCN account (make one with RPCS3 first; the port never creates accounts). `online.ini` is ignored by git; never share it.

What it does with `PORT_ONLINE=1`:

- Turns on real sockets for the game (`PS3_NET_ONLINE=1`).
- With `rpcn_user` and `rpcn_password` set, the game is told it is signed in, as that RPCN name. When the game asks for a sign-in ticket, the port connects to `rpcn_host` (TLS, port 31313), logs in and gets the ticket from RPCN, as RPCS3 does.
- Sends the game's server lookups (`gethostbyname`) to `host.<name> = <ip>` entries first, then to the `dns =` server (for community revival servers that are reached through a custom DNS), then to Windows' DNS.

| Variable / `online.ini` key | Meaning |
|---|---|
| `PORT_ONLINE=1` | Turn it on (default off) |
| `PORT_ONLINE_CONFIG=<path>` | Read another file instead of `online.ini` |
| `PORT_ONLINE_PROBE=1` | At start-up, only check that `rpcn_host` answers (TLS + server version; no login). The result is in `logs\run.log` (`[online] probe`) |
| `rpcn_host`, `rpcn_user`, `rpcn_password`, `rpcn_token` | RPCN server (default port 31313) and your account. The password and token are never written to the log |
| `dns` | IPv4 address of a DNS server for the game's lookups |
| `host.<name>` | Fixed IPv4 address for one host name |

`logs\run.log` lines start with `[online]` (config read, sign-in state, ticket requests) and `[sys_net] gethostbyname` (each server name the game looks up and where it went).
**Limits:** Resistance 2's online modes need the community (revival) servers, which RPCS3 reaches with RPCN plus the revival's DNS. The port does the same steps, but nobody has played online with it yet: whether those servers accept the port's tickets, and whether the rest of the game's online code (matchmaking, voice, NAT) works, is untested. Some online functions are still stubs. Online co-op and competitive play are therefore not expected to work yet.

## Launcher settings

PC-port options added on top of the PS3 game. Each one is an environment variable that the launcher writes to `settings.bat` (set it there yourself, or in the launcher; unset = the default shown first). The overlay toggle is also exported for the in-game PC menu (`r2pf_overlay_set`).

**Display**

- **Ultrawide / arbitrary aspect** — `R2_ASPECT` = *(unset)* / `off` / `16:9`: the PS3 16:9 picture, pillarboxed on wider screens (default). `auto` (launcher *Fit window*): the 3D view takes the window's shape, re-read live when the window is resized. `21:9` (= 64:27), `32:9`, `W:H`, `WxH` or a plain ratio (`2.4`) force one. The port widens the game's camera frustum Hor+ (horizontal FOV grows, vertical FOV stays as on PS3; the aspect handed to the projection follows) by hooking the game's two frustum setters, and the RPCS3 renderer then stretches the frame to the window instead of letting it in a 16:9 box. The HUD and menus are stretched to the width: the game draws them in the same 16:9 render target as the 3D scene, and they could not be told apart reliably enough to keep them in a centred 16:9 region (so `R2_HUD_MODE=center` is not available). Only the main 3D camera is widened; with a narrower than 16:9 window (e.g. 4:3) the view is Vert-.
- **Presentation mode** — `R2_PRESENT` = `immediate` (also `vrr`, `tearing`): never wait for vblank (best with G-Sync / FreeSync); `mailbox`: newest frame each vblank, no tearing, but at the fixed refresh, so G-Sync / FreeSync do not follow it (falls back to FIFO-relaxed); `fifo` (or `vsync`): classic VSync. Unset follows the VSync setting (`RSX_VSYNC`). Compatible (RPCS3) renderer only.
- **Frame rate just under refresh** — `R2_FPS=vrr`: caps at refresh − refresh²/3600 (≈ 57.1 on 60 Hz, 138 on 144 Hz, 228 on 240 Hz) so a VRR display never leaves its range. Pair it with *Presentation mode = Immediate* or VSync off.
- Exclusive fullscreen / borderless / windowed, monitor choice and Alt+Enter: see *PC features* above.

**Frame pacing, VSync and G-Sync / FreeSync** (Compatible renderer)

- Present mode per setting (the log prints it once: `[display] Vulkan present mode FIFO, 3840 x 2160`): VSync *Off* / `R2_PRESENT=immediate` = IMMEDIATE; *On* / `fifo` = FIFO; *Adaptive* = FIFO relaxed (MAILBOX if the driver has no FIFO relaxed); `R2_PRESENT=mailbox` = MAILBOX. *Auto* (`RSX_VSYNC=auto`) = FIFO whenever the frame rate is capped at or under the display refresh (the cap means it never waits on vblank) and Adaptive when uncapped or above the refresh.
- G-Sync / FreeSync follow FIFO, FIFO relaxed and IMMEDIATE. MAILBOX shows the newest frame at the fixed refresh, so VRR does not follow it: 60 fps on a 144 Hz screen then holds frames for 2, then 3 refreshes (judder) even with G-Sync on. Earlier builds mapped *Auto* and *Adaptive* to MAILBOX; they now use FIFO / FIFO relaxed.
- Without VRR, a fixed-refresh display is only even at a divisor of its rate (60 on 60 / 120 / 240 Hz, 72 or 48 on 144 Hz); the log warns (`[fps] note: ...`). **Refresh rate switch** — `PORT_REFRESH_SWITCH` (default off, `1` = on, experimental: every switch blanks the screen and can glitch audio; launcher *Display › Frame rate › Refresh rate switch*): in exclusive fullscreen (`RSX_DISPLAY=exclusive`) the display is switched to the nearest mode at the same resolution whose refresh is a multiple of the frame rate (`[fps] display switched 144->120 Hz`), and back to the desktop rate when the game loses focus, is minimised, leaves fullscreen, closes or crashes. Borderless and windowed never switch (use G-Sync / FreeSync or an even frame rate there) unless `PORT_REFRESH_SWITCH=2` (opt-in): any fullscreen, borderless too, switches the desktop rate the same way (144 -> 120 Hz for a 60 fps cap) and gives it back on focus loss / exit. With VRR the switch is harmless but unnecessary; `0` avoids the mode-change flash.
- **Display sync** — `R2_DISPLAY_SYNC` (launcher *Display › Frame rate › Display sync*; `PORT_DISPLAY_SYNC` when unset). `auto` (default): a background thread waits for the display's vblanks (D3DKMT) and checks over 2 s windows whether they follow the game's frames (VRR working) or keep a fixed period (`[display] VRR effective: yes` / `no -- the screen refreshes at a fixed 165.00 Hz`); it can only tell while the game shows fewer frames than the refresh rate, and windows while the game is minimized or another program is in front (plus the one after) don't count. After three "no" windows in a row (any other result in between starts over) fixed-refresh pacing turns on (`[display] fixed-refresh pacing ON`): present mode FIFO and the frame limit = refresh / k (/ the Frame Generation multiplier) for the smallest k within the frame-rate setting (60 allows up to 75), phase-locked to the vblanks when k ≥ 2, so every frame is shown for exactly k refreshes (`[display] fixed-refresh pacing: 165.00 Hz: 55.00 fps, each frame 3 refreshes`, `[fps] frame limit 55 fps (fixed-refresh pacing)`). Examples: 165 Hz 55 fps (Frame Generation 2x: 41.25 -> 82.5); 144 Hz 72 (FG: 72 -> 144); 120 Hz 60 (FG: 60 -> 120); 240 Hz 60 (FG: 60 -> 120); 60 Hz 60 (FG: 30 -> 60). With `R2_FPS=30` the frame-time floors are patched while it is on. Two "yes" windows in a row turn it off again. Not paced (frame limit and VSync as set) when even every refresh would mean under 30 rendered fps (60 Hz with Frame Generation 3x). `vrr`: never (only measured and logged); `fixed`: always; `off`: no measurement. The Reflex cap under the refresh rate is not used while it is on. A PC that can't hold the paced rate (more than 20% of frames late over 2 s, ignoring loading frames and stalls) steps one refresh slower (144 Hz: 72 -> 48 instead of 2 / 3 refresh judder) and tries the faster rate again after 10 s of clean frames (back at once if it misses; the wait doubles up to 2 min); never faster than `R2_FPS` allows, logged as `[display] fixed-refresh pacing: stepping to ...`. `PORT_PACING_ADAPT=0`: never steps.
- With `PORT_OSD=layered`, popup windows over the game (performance overlay, extra crosshair, toasts) make Windows compose the screen, which can turn G-Sync off while they are visible. By default they are drawn into the game image and do not.

**No-flip watchdog** — `PORT_NOFLIP_WATCHDOG` (default `5` s, `0` = off) and `PORT_NOFLIP_NUDGE` (default `500` ms, `0` = off): when the game has shown no new frame for that long while it is not paused (after a death in Bryce Canyon the screen stayed black for ~20 s and only moved on when the window lost focus), `logs\run.log` gets one `[noflip]` line per stall with the HLE call each game thread is inside, every game thread's return address (`[WATCHDOG] guest-tid ... lr=`), what the main thread waited on over the next second (usleep spin / sleep, lwmutex, lwcond, yields), whether the game still reads the pad and the pad state it last read; the thread stacks and SPU state go to `logs\noflip_<tick>.txt` (first 3 stalls of a run). Then, if the game read the pad in that second and read no file since its last frame (a load is left alone), all input is released for `PORT_NOFLIP_NUDGE` ms, the only part of an alt-tab the game can see before the focus pause, and the log says whether frames came back right after it (`[noflip] flips resumed after ... right after the input release`) or not (`still no flip 3 s after the input release`); otherwise it says why it did not (`[noflip] no input release: ...`). The thread stacks are taken without any loader or heap call while a thread is suspended, so the report cannot hang the game itself.

**RSX stall report** — `RSX_STALL_DIAG_MS` (diagnostic, default `0` = off; `3000` = report after 3 s; read by the no-flip watchdog thread, so it also runs with `PORT_NOFLIP_WATCHDOG=0`): when the RSX command buffer's GET has not moved for that long while PUT is elsewhere (report #153831: after ~20 min the game printed `GPU sit and spin timeout` with GET fixed and nothing else in the log), `logs\run.log` gets one `[rsx-stall]` line per stall (up to 8 a run) with GET / PUT / REF, where the RSX puller is and the last command word it read (decoded: method name and count, JUMP / CALL / RET target), whether it is parked on a jump-to-self that the game has not patched yet or inside a semaphore acquire (label address, wanted value, value it holds, how long), the last acquired label and its value, the 8 words at GET and at the puller, and one `[rsx-stall] rawSPU0` / `rawSPU1` line each (image, pc, status, mailbox counts). `[rsx-stall] GET moves again` follows if the RSX recovers. A semaphore acquire ended by the Driver Recovery Timeout (1 s) now also logs `[rsx-stall] semaphore acquire at ... timed out` (first 20). The last stall report and the raw SPU lines are also written to `logs\noflip_<tick>.txt`. Read-only: it never changes what the RSX does.

**Hitch logger** — `PORT_HITCH_LOG` (diagnostic, default off, `1` = on; it also turns on the `[fps] 5 s`, `[occ]` 10 s, `[occ] precise 5 s` and `[usleep-watch]` lines; `PORT_HITCH_MS=<ms>`, default 25): every game frame over 25 ms (or over 2x the frame-time target) prints one `[hitch]` line with where that frame went (game, limiter, sync waits, pad, RSX flip interval, present / acquire / GPU wait / DLSS, pipeline compiles, texture uploads, audio wait, and `present-iv` = the longest present-to-present interval). Every 5 s: `[hitch] 5 s:` (CPU frame time p50 / p99 / max) and `[hitch] present 5 s:` (present-to-present interval p50 / p99 / max, `uneven` = intervals more than 4 ms off the median, and how many frames a fixed-refresh display would hold for 1 / 2 / 3 / 4+ refreshes; a mix of 2 and 3 = judder unless VRR is active). Since this build the `[hitch]` line also splits `guestwait` (the game thread's own guest waits) into spin / sleep / lwmutex / lwcond and names the guest call site that waited longest (`top 0x... X ms`), shows the game thread's CPU time (`game X (cpu Y)`: a gap = the thread was preempted), and breaks down the RSX thread: `fifo-idle` (waiting for commands), `label ms/n` (NV406E semaphore waits), `zcull ms/n` (occlusion report reads waiting for the GPU), `hard-sync ms/n`, `submits n` and `rsx-limit` (RPCS3 flip limiter sleep). Hot-thread log lines (`[pipe]`, `[fps]`, `[hitch]`) are queued to a writer thread (`PORT_LOG_SYNC=1` writes them at once). Per-frame `[hitch]` lines are capped at `PORT_HITCH_LINES` per 5 s window (default 10, `0` = only the 5 s summaries; was 20 per second) and, with `PORT_HITCH_ADAPT` (default on, `0` = off), a frame is only listed when it is over max(`PORT_HITCH_MS`, 1.5x the frame-time target, 1.5x the previous window's p50), so a game running steadily below the target no longer logs every frame (frames over 2x the target still count in the summary). **Frame-spike attribution** — each `[hitch]` line is followed by a `[spike]` line (`PORT_SPIKE_LOG=0` turns it off) listing that frame's contributors sorted by ms: `game(ppu)`, the top 3 guest waits by call site, `gpu-busy` (GPU execution time from Vulkan timestamps; off by default, `RSX_GPU_TIME=1` turns it on; gpu-busy close to the frame time = GPU-bound, low gpu-busy with long waits = latency / serialization), `spu-jobs` (summed over SPU lanes), `rsx-fifo-idle`, present / GPU wait / DLSS, `readback` (surface reads by CPU/SPU waiting on the GPU), `blit`, `tex-upload`, `pipe-compile`, `zcull-read`, `hard-sync`, `label`; then counts (draws, submits, `zcull-forced`, `ads-kicks`, texture uploads and same-slot re-uploads, readbacks, blits) and the 4 SPU job images that took the longest (`spu top jobs: img N ms/runs`; R2's job-manager return address is `SPU_WWSJOB_LINK`, default `0x35D8`). The `[hitch] 5 s:` summary adds the per-frame mean `gpu-busy`, `spu-jobs`, `draws` and `readback`. SPU job images in `[spike]` and `[spu-jobs]` carry a class tag (`phys` igPhysicsColl rigid bodies, `pcf` ragdoll / joint solver, `limb` gibs, `water`, `ocean`, `geom`, `mesh`), and `[spike]` adds the SPU time per class (`PORT_SPU_JOB_TAGS=0` = no tags). Every frame of 30 ms or more (up to 10 per 5 s, whatever the `[hitch]` threshold and `PORT_SPIKE_LOG`) also prints `[spike] cause:`, which ranks only the parts the frame loop really waited on, one after another (game, extras including the Reflex sleep, limiter, sync, pad, RSX ring and readback, and each guest wait site named by class, such as `rsx:occlusion-report`, `spu:job-list` and `rsx:frame-label`), and lists the SPU lane-sum separately because SPU jobs run in parallel and are not frame time. `[spike] causes 5 s:` counts every such frame by its largest cause, without the per-5 s line cap (`PORT_SPIKE_CAUSE=0` = off, `PORT_SPIKE_CAUSE_MS=<ms>`, default 30). A `[spu-jobs]` job line ending in `INTERPRETED X ms (N entries)` means that job spent X ms in the SPU interpreter because it reached code that has no translated version (`[spu] img=... unlifted job code at LS 0x... -- interpreting [entry pic 00DFF680 00C58]` names the module and offset); when the untranslated code was reached by a call from translated code, only that call is interpreted and the job goes back to translated code when it returns (`[spu] unlifted call 0x... returned to lifted caller`; `SPU_UNLIFTED_SCOPED=0` restores the old behaviour, where the rest of the job runs interpreted, hundreds of times slower — R2's `mesh` job took 33-143 ms per run that way), so report such lines.
- **gpu-busy is the union of command-buffer GPU time** (with `RSX_GPU_TIME=1`; `RSX_GPU_TIME_UNION`, default on, `0` = the old per-buffer sum). The summary prints `gpu-busy X (cb-sum Y)`: X counts overlapping command buffers once, Y is the old sum. If Y is well above X, buffers overlap on the GPU. X close to the frame time means the frame is GPU-bound.
- **`zcull-forced`** counts only occlusion-report hints that actually submitted a command buffer. Hints that found nothing to submit are no longer counted.
- **New `[spike]` counts:** `instanced clauses` (draw clauses RPCS3 merged into one instanced draw), `render-passes` (render pass begins) and `barriers` (pipeline barriers). The 5 s summary adds `render-passes` and `barriers` per frame.
- **Submit reasons and depth copies** (with the `[spike]` line): a second `[spike] submit reasons:` line counts why each Vulkan command buffer was submitted that frame (`bind-dma` = render-target bind with a pending DMA copy, `av-flush`, `zcull-hint` / `zcull-hard` (occlusion reports), `blit`, `label`, `ads`, `present`, `hard-sync`, `other`) and how many scaled depth copies took the direct blit or the carrier path (`RSX_DEPTH_BLIT_DIRECT`). The 5 s summary adds the same counts per frame.
- **RSX thread CPU split** (`PORT_RSX_CPU_PROF`, diagnostic, off by default; `1` = every frame, `N` = 1 frame in N (whole flip-to-flip frames, scaled to per-frame averages; about 0.06 ms/frame at N = 8 instead of 0.42 ms when every frame is timed); needs `PORT_HITCH_LOG=1`). When on, the `[hitch] 5 s:` line ends with `rsx-cpu per frame: work W (U us/draw) = decode … state … shader … vertex … tex … surface … draw … zcull … submit … blit …; present … readback … label … idle …` (ms per frame of RSX thread time).
  - `work` is the RSX thread's own CPU work, split into:
    - `decode`: FIFO decode and method handlers;
    - `state`: draw begin/end and program/descriptor state;
    - `shader`: program resolve and pipeline lookup;
    - `vertex`: vertex/index upload and layout;
    - `tex`: texture cache lookups, uploads and binds;
    - `surface`: surface cache, framebuffer bind and on_write;
    - `draw`: draw command recording, including the DLSS object-motion pass;
    - `zcull`: occlusion reports and their waits;
    - `submit`: command buffer submits;
    - `blit`.
  - The time after `;` is waiting or not per-draw: `present` (flip, DLSS/AA), `readback` (texture-cache flushes waiting for the GPU), `label` (semaphore waits) and `idle` (FIFO empty).
  - Cost: one `rdtsc` per category switch. A large `readback` or `zcull` with small `work` means the RSX thread is waiting on the GPU, not CPU-bound.

**Frame-time report (stutter log)** — the port records every present-to-present interval (lock-free, no per-frame allocation). At exit, and when a crash or hang report is written, it writes `logs\frametimes_<date>_<time>.txt`: average, 1% low, 0.1% low, worst frame, a histogram, the 20 worst frames with their time and clock time, and stalls of 1 s or more (loading screens, hangs; left out of the numbers). Game pauses (menu, unfocused window) are left out. The newest 10 files are kept; **Report a problem** includes the newest five (user name scrubbed). Press **Scroll Lock** while playing to flag a bad moment: a `[frametime] MARKER` line with the last 2 s of frame times goes to the log and to the file (F8 is the mouse-release key). `PORT_FRAMETIME=0` turns the recorder off; `PORT_FT_MARKER_KEY=scroll|pause|f1..f24|off` picks the marker key. If the recorder ran for over 60 s without seeing a frame, the log gets a `[frametime] WARNING: ... present hook ... is missing` line.

**Frame pacing** — one pacer: when the frame rate is not 30, the game limiter (`R2_FPS`) paces the frame loop and the RPCS3 flip limiter is off (it was a second 60 Hz clock: the RSX thread slept in the flip while the game waited on it, then the next frame ran at once). `GCM_FRAME_LIMIT=vblank` restores the old double pacing.

**Performance overlay** — **F3** in game shows or hides a small box in the top-left corner: game fps and frame time (average and worst of the last 0.5 s), and on the Compatible renderer the RSX (GPU-side) frame rate, draws per frame and average µs of render-thread time per draw. `R2_OVERLAY=1` shows it at start, `R2_OVERLAY=0` disables F3; `R2_OVERLAY_POS=tl|tr|bl|br` picks the corner. It is drawn into the game's own image (`PORT_OSD`), so it also shows in exclusive fullscreen; while it is shown the renderer's profiling counters run (a small cost; `R2_RSX_PROF=1` also prints them to the log every 5 s).

**Trophies → local achievements** — every trophy the game awards is recorded (the runtime's `gamedata\trophies\NPWR00291.json`, plus a readable copy in `%USERPROFILE%\Saved Games\Resistance 2\trophies.json` with names, grades and unlock times). The names come from the game's own `TROPHY.TRP` in `gamefiles\PS3_GAME\TROPDIR` (read at run time; nothing is shipped). A PS3-style pop-up: a dark rounded box near the top corner (opposite the F3 overlay) that slides in for about 6 s, with the trophy's own icon from `TROPHY.TRP` (a cup in the grade's colour if it can't be read) at the left, "You have earned a trophy." and the name below it (scaled to the window height; drawn into the game image, so it also shows in fullscreen, HDR included). Several unlocks queue. `PORT_TROPHY_STYLE=old` (or `R2_TROPHY_STYLE=old`; launcher *Trophy pop-up style: Classic*) brings back the older notification with the grade badge and description. `PORT_TROPHY_TEST=1` shows one sample pop-up per grade a few seconds after start-up, to check the look. `R2_TROPHY_TOAST=0` turns it off. The platinum is awarded once every trophy it counts is earned. The launcher's **Trophies** page shows a summary at the top (earned / total, percentage, a progress bar and the count per grade), then every trophy with its icon from `TROPHY.TRP` (greyed until earned), name, description, grade and the date it was earned, newest first. Hidden trophies show as *Hidden trophy* until earned. It merges both records (a trophy counts if either has it; the earliest time wins), so the platinum the port awards also shows. Before anything is earned it says *Play the game to start earning trophies*. The page reads nothing until it is opened, re-reads only when those files change, and never writes to them.

**Input** (launcher: Controls › Aiming and sticks)

- Key / mouse-button rebinding: Controls page (`controls.txt`).
- `PAD_MOUSE_SENS_Y=<0.1..4>` — vertical mouse sensitivity relative to horizontal (direct and classic mouse aiming).
- `R2_ADS_SENS=<0.1..3>` — mouse sensitivity while aiming down sights / scoped, relative to hip fire (on top of `R2_ZOOM_SENS`).
- `PAD_AIM_TOGGLE=1` — Aim (L1 / Mouse2 / LB) toggles instead of hold, for keyboard and controller; menus and the pause screen release it.
- `PORT_AIM_ASSIST=on|off` — the game's aim assist (your aim slows down over an enemy and is pulled toward it). Unset / `auto`: off with keyboard & mouse, on with a controller (in split-screen only the keyboard & mouse player loses it); `on` (`1`): always, as on PS3; `off` (`0`): never. Launcher Controls › Aiming and sticks › *Aim assist*; F9 and PC SETTINGS › PC CONTROLS & HUD (changes at once). Enemies are not affected.
- `PAD_DEADZONE=<0..0.9>` — controller stick deadzone, radial (unset: the XInput standard 24 % per axis, as before).
- `PAD_CURVE=<0.5..3>` — stick response exponent past the deadzone (1 linear, >1 finer near the centre, <1 faster).
- `PAD_OUTER_DEADZONE`, `PAD_ANTI_DEADZONE`, `PAD_TRIGGER_DEADZONE`, `PAD_TURN_BOOST`, `PAD_CROUCH_MODE` — stick edge, anti-deadzone, trigger travel, turn boost and crouch toggle/hold: see the table under *Controllers (SDL3)*.
- Invert vertical look: Controls page (`controls.txt`). DualShock 4 / DualSense / Switch: supported natively through SDL3 (see *Controllers (SDL3)* under Controls); Steam Input and DS4Windows are not needed.

**Mods folder** — `R2_MODS=1` (launcher: Mods folder = On) loads files from `mods\` next to the game (`R2_MODS=<folder>` names another folder). Each sub-folder is one mod laid out like the game's `PS3_GAME` folder: `mods\MyMod\USRDIR\<path of the file to replace>`. Mods are applied in alphabetical order (a later one wins on the same file), or in the order of `mods\order.txt` (launcher *Saves & tools › Mods*, see *PC extras*); a folder name starting with `_` or `-` is skipped. Every file layer of the runtime (cellFs, sys_fs) uses the replacement. `logs\run.log` lists each mod and override at start-up (`[mods] override: ...`) and the first use of each (`[mods] using ...`). Single members of a `.psarc` archive and single level assets (by tuid) can be replaced as well: see [docs/MODDING.md](docs/MODDING.md). Single textures by content hash go through the renderer's texture packs (*Graphics enhancements*, `RSX_TEXPACK`).

**Shaders** — the Compatible renderer keeps every GPU pipeline it builds in `shadercache\rpcs3\` and, at start-up, builds all of them again before the first frame (RPCS3's shader cache preload), so after the first play-through nothing is compiled in game. The log shows the progress (`[r2rsx] shader preload: compiling n/N pipelines`, then the total time); `R2_SHADER_PRELOAD=0` keeps the preload but without the log lines. `R2_VK_PIPE_CACHE` (default on) also keeps the graphics driver's own pipeline cache on disk (`shaders_cache/vk_pipeline_cache.bin`, used only by the same GPU and driver build), so the start-up preload mostly reloads instead of recompiling; `0` starts with an empty driver cache every run as RPCS3 does. Every pipeline first linked during play is logged (`[r2rsx] shader cache miss #n during play`) and is preloaded from the next start. With `R2_RSX_PROF=1`, the `r8 per frame` line's *in-memory misses* and *draws skipped (program not ready)* should stay at 0 in a level you have played before. `R2_SHADER_CACHE=0` turns the disk cache off; `R2_SHADER_MODE` (launcher: Shader compilation) picks synchronous (default) / asynchronous / interpreter compilation for pipelines that are not in the cache yet: synchronous builds one at once (a short hitch the first time an area or effect is seen, no skipped draws, so no purple / green patches), asynchronous never waits but skips those draws until the pipeline is ready. A settings.ini saved by an older launcher with `shaders=async` switches to synchronous once. The pipelines depend on the game's state and cannot be generated before they are first seen, but they can be recorded and shipped:

- `R2_FOSSILIZE=record` writes every pipeline built in a session (with its shaders, layouts and render pass) to `shadercache\rpcs3\shaders_cache\r2_pipelines.foz` (Valve's Fossilize format, the one Steam's shader pre-caching uses; sessions append). By default (`auto`) the renderer replays that file, if it is there, on low-priority threads after the start-up preload, so a new GPU or driver compiles them into its pipeline cache in the background. `0` = off; `R2_FOSSILIZE_DB=<path>` = another file.
- `R2_PRELOAD_ASYNC` (default on with the asynchronous shader mode, off otherwise) compiles every cached shader before the first frame but links only the first `R2_PRELOAD_BOOT` (384) pipelines recorded; `R2_PRELOAD_THREADS` (default a quarter of the CPU threads, 1 to 4; 1 on AMD GPUs, with the Low CPU profile or 8 threads or fewer) background threads link the rest while you play (`[r2rsx] shader preload: background done ...`). `0` = everything before the first frame, as before.
- **Preload safety** (GitHub issue #10, an AMD driver crash while a background thread linked an MSAA pipeline; all on by default): cached pipelines that render with MSAA are skipped while MSAA is off (FSR 3.1, DLAA and `R2_MSAA=0` turn it off; logged as `skipped n MSAA pipelines`), since they can never be used; `PORT_PRELOAD_ALL_MSAA=1` preloads them anyway. On AMD GPUs the background preload uses 1 thread; `PORT_PRELOAD_THREADS=N` (or `R2_PRELOAD_THREADS`) sets the count on any GPU. Each preload thread writes the pipeline it is linking to `logs\preload_inflight.txt`; a crash report names it (`preload faulting: <file>`) and the next start skips that pipeline, listed in `shadercache\rpcs3\shaders_cache\preload_quarantine.txt` (delete the file to retry them; `PORT_PRELOAD_QUARANTINE=0` ignores it, `PORT_PRELOAD_BREADCRUMB=0` turns the breadcrumb off). On the background threads a driver crash inside pipeline creation is caught, logged (`the driver faulted while linking ...`), the pipeline is quarantined and the background preload stops instead of the game closing; `PORT_PRELOAD_SEH=0` turns that guard off.
- `R2_VK_GPL` (default on when the GPU supports `VK_EXT_graphics_pipeline_library` with fast linking, logged as `[r2rsx] pipeline libraries (R2_VK_GPL): on`): a pipeline first needed during play is linked in well under a millisecond from separately cached parts, and the fully optimised pipeline is compiled in the background and swapped in. Same shaders and state; `0` = the normal path.
- `R2_PIPE_LOG` (diagnostic, default off; `1` = on) prints a `[pipe]` line every 5 seconds with the time the render thread spent waiting for shader or pipeline compilation, the number of waits over 2 ms (histogram) and the fast-link / background counts.

**Not done:** native HDR rendering (the game produces an 8-bit SDR image; the opt-in HDR output below maps that image into an HDR swapchain at a chosen paper white - brighter UI and correct SDR-in-HDR, but no extra highlight range; real HDR needs the game's tone mapping rewritten). Frame generation is available (see *PC extras*). A centred 16:9 HUD at ultrawide is available as an experiment (`RSX_HUD_FIX=1`, *Graphics enhancements*).

The in-game page writes the same `settings.ini` / `settings.bat` lines as the launcher. Rows marked *(next start)* apply after a restart; the rest apply at once. Code: `project\r2_pcextra.cpp` (game side), `project\launcher_extra.inc` (launcher), `ps3recomp\third_party\rpcs3\rpcs3\Emu\RSX\VK\VKR2PcExtras.cpp` (Vulkan HDR / colour-blind / Reflex).

- **Automatic prompts** — `R2_PAD_GLYPHS=auto` (default): the prompts follow the last device used (keyboard/mouse → key names, controller → Xbox or PlayStation symbols by the controller's type). Already in the port; listed here for completeness.
- **Post effects** — `R2_FX_SCREEN_BLUR=0` (damage / sprint / explosion full-screen blur), `R2_FX_CAMERA_SHAKE=0`, `R2_FX_LETTERBOX=0` (cutscene black bars). Implemented by pointing the game's Lua script bindings for these effects at a no-op, so they switch live. Resistance 2 has no film grain, depth-of-field, chromatic aberration or vignette pass of its own to turn off (none were found among its render passes or script functions).
- **Colour-blind filter** — `R2_COLORBLIND=1|2|3` (protanopia / deuteranopia / tritanopia): daltonization in the final output pass (Compatible renderer). Applies at once. The filter decodes sRGB to linear light, daltonizes (ReShade *Daltonize* matrices: simulate the deficiency, shift the lost red/green error into green/blue), re-encodes, and runs before HDR encoding. Strength is fixed at full.
- **Extra crosshair** — `R2_CROSSHAIR=dot|cross`: a small marker at the window centre during play (shown while the game's look input is active; hidden in menus, the PC menu and photo mode). **Crosshair colour** `R2_CROSSHAIR_COLOR` (`white` default, `green`, `yellow`, `cyan`, `red`, `pink`, `orange`) and **Crosshair size** `R2_CROSSHAIR_SIZE` (`small` default = 24 px, `medium`, `large`, `huge`, or a percentage 50-400) — always with a dark outline; live in F9 and in the launcher.
- **Window** — `RSX_RESIZABLE` (default on): the windowed-mode window has a sizing border and the swapchain follows the new size. `RSX_ALT_ENTER` (default on): Alt+Enter switches windowed ↔ borderless fullscreen.
- **Frame rate** — the cap stays the game's own frame limiter (`R2_FPS`, launcher *Frame rate*); there is only one limiter. 120 / 144 / Uncapped are marked *experimental*: the game measures real time per frame and the port rescales its 30 Hz frame-counted timers (`r2_timing_frames`, `R2_PATCH_TIMING_FRAMECOUNT`), so the game does not speed up, but its physics step is fixed at 60 Hz, so above 60 fps moving objects judder slightly and some camera smoothing was written for 30/60 fps and was not audited frame by frame. Walking from a standstill works at any frame rate (GitHub #21): the hero's ground update zeroes its velocity when the first step from rest is under 0.3 m/s, and that step is the steering rate × frame time, so above ~75–100 fps it never got past the test (only jumping and steering in the air moved the hero). `R2_MOVE_START_FIX` (default on; `0` = the game's test as is) scales the steering rates while the hero stands still so the first step is as large as at 60 fps; nothing changes at 60 fps and below.
- **NVIDIA Reflex** — `R2_REFLEX=1` (`2` = + Boost), opt-in, Compatible renderer, GeForce with `VK_NV_low_latency2`: low-latency mode plus the Reflex sleep at the start of each frame. It does not cap the frame rate (the game's limiter still does); no latency markers are sent, so the NVIDIA overlay's latency readout stays empty. Does nothing when the extension is missing.
- **Latency reduction** — `PORT_LATENCY=off|reflex|antilag|auto` (launcher: Upscaling & Frame Gen › *Latency reduction*, F9 too; unset = `R2_REFLEX` alone decides, as before). `reflex` turns NVIDIA Reflex on (Boost with `R2_REFLEX=2`); `antilag` = **AMD Anti-Lag 2** through `VK_AMD_anti_lag` (Radeon with a driver that exposes it): `vkAntiLagUpdateAMD` INPUT stage once per frame after the limiter and PRESENT stage around each present; `auto` = Reflex on NVIDIA, Anti-Lag 2 on AMD. With Reflex on, the Compatible renderer now also sends the **Reflex latency markers** (`vkSetLatencyMarkerNV`: SIMULATION_START/END, INPUT_SAMPLE at the first port-0 `cellPadGetData` of a frame, RENDERSUBMIT_START/END, PRESENT_START/END) so the driver and the NVIDIA overlay's PC latency see the frame; `R2_REFLEX_MARKERS=0` = sleep only (the old behaviour). Neither is used while frame generation is on (it has its own Reflex). Experimental.
- **DLSS Frame Generation** — `R2_DLSS_FG=2|3|4` (launcher: Upscaling & Frame Gen › *Frame Generation*; `0`/unset = Off), Compatible renderer, GeForce RTX 40 (2x) or RTX 50 (up to 4x Multi Frame Generation), Anti-aliasing = NVIDIA DLSS, setup's optional NVIDIA Streamline download. The GPU inserts 1-3 generated frames between the game's own (`ps3recomp\third_party\rpcs3\rpcs3\Emu\RSX\VK\VKR2FrameGen.cpp`, NVIDIA Streamline 2.14.16, manual hooking). Smoother motion when the CPU is the limit; adds a little input lag, so Reflex is switched on with it (Streamline drives Reflex while FG is set up; `R2_REFLEX=2` = Boost; each present carries the Reflex frame id of the game frame it shows — the oldest finished one — so Reflex no longer sleeps the game thread for the GPU time on top of the frame, which dropped the base rate to ~30-45 fps; `R2_DLSS_FG_REFLEX_IDS=0` = old ids (the newest game frame), `R2_DLSS_FG_REFLEX_SLEEP=0` = Reflex markers without the Reflex sleep, for A/B). The frame-rate setting caps the game's own frames; the Reflex cap keeps rendered × multiplier under the refresh rate. The HUD is split from the scene in the renderer (HUD draws after the 3D pass go to a UI layer that is composited after generation), so HUD text does not warp; when a frame's HUD can't be separated cleanly it is passed through untouched. FG pauses in menus, movies, loading screens, split-screen, while the game is paused and on scRGB HDR, and turns itself off (one `[fg-vk] frame generation off: ...` log line) on other GPUs, without the DLLs, or with FSR / XeSS / no AA. Debug: `R2_DLSS_FG_HUD=0` (no HUD split), `R2_DLSS_FG_HUD_DEBUG=1` (show the HUD-less image), `R2_DLSS_FG_MENU_OFF=0`, `R2_DLSS_FG_GAP=0` (warm up again after every scene-less frame), `R2_DLSS_FG_CAP=0`, `R2_DLSS_FG_YFLIP=0`, `R2_DLSS_FG_DEBUG=1`. With a fixed-refresh display and no G-Sync, vsync is replaced by the Reflex cap and may tear. If Streamline fails or faults while it sets up the Vulkan device (driver or plugin problem), DLSS-G is dropped for that run with a `[fg-vk]` log line and, with `R2_FG_BACKEND=auto`, FSR 3 2x takes over instead of the game crashing. Streamline plugins: the matched 2.14.16 set next to the exe is used and NVIDIA's over-the-air plugin updates are off (`R2_DLSS_FG_OTA=1` turns them back on); an NVIDIA App / driver *DLSS override* can still swap in the driver's own plugin builds (`ProgramData\NVIDIA\NGX\models\sl_*_override_*`, logged once), and `R2_DLSS_FG_OVERRIDE_PLUGINS=0` refuses DLSS-G in that case (auto: FSR 3). Diagnostics: `R2_FG_DIAG=1` logs a `[fg-diag]` line per second (real vs generated presents, generated frames Streamline did not present, frame-generation resets by cause with the held camera-cut values, pauses, a real present-interval histogram with spikes and pace jumps, Reflex sleep, DWM refresh / composition rate) and **Pause** (`R2_FG_DIAG_KEY=pause|scroll|f1..f24|none`) appends the previous 30 and next `R2_FG_DIAG_FRAMES` (default 120) presents frame by frame to `logs\fgdiag.txt`; `R2_FG_DIAG=2` also starts that dump by itself on a suspect event (at most `R2_FG_DIAG_AUTO_MAX`, default 10, 20 s apart). `R2_FG_DIAG=3` (the test launchers' setting) keeps the per-second lines and records every present, with the dump's columns, to `logs\fgdiag.txt` until the game closes (the previous session's file becomes `fgdiag_prev.txt`; if that rename fails, e.g. the old file is open in another program, it is left alone and this session writes `fgdiag_<pid>.txt`, named in `run.log`): resets with their reason, pauses, undelivered generated frames, DLSS-G status changes and spikes are `--- ... ---` lines in the stream, a `# second` line follows each second, and **Pause** writes a `--- user marker ---` line (press it when a duplicate frame or ghosting shows). One writer thread empties a preallocated queue every 250 ms (no file I/O on the present thread; a full queue drops rows, counted in the file and `run.log`); about 0.6 MB per minute at 60 rendered fps; the file stops at `R2_FG_DIAG_MAX_MB` (default 512). Without it, a `[fg-vk] frame generation in 10 s: N resets (...)` line follows the 10 s DLSS-G status line when resets, undelivered generated frames or pauses happened.
- **Frame Generation ghosting toggles** (DLSS-G and FSR 3) — `R2_DLSS_FG_HUD_HOLD=1` (**default on**; `0` = old behaviour): on a frame whose HUD could not be split from the scene (the classifier was unsure, or the "HUD" covered too much of the screen), the HUD area of the last frame whose split was used (under 2 s since then; frames where the split was tried but the "HUD" covered too much of the screen do not refresh it, so a long full-screen fade or overlay lets it expire) is still handed over as UI and frame generation's motion vectors are zeroed under it, so the HUD baked into that frame is not dragged along with the scene (HUD / crosshair trails while turning); `R2_DLSS_FG_HUD_DEBUG=1` shows that held area in yellow. `R2_DLSS_FG_FX_MV=0|1|2` (default `0`, experimental): motion of the pixels covered by this frame's blended effect draws (smoke, sparks, muzzle flash, glows; the `PORT_DLSS_BIAS_MASK` coverage, so it needs DLSS with that mask on): `0` as rendered (the motion of the surface behind, characters included), `1` camera motion only, `2` none. `R2_DLSS_FG_STATS=1` (or `R2_FG_DEBUG=1`) logs two `[fg-vk] [fg-stats]` lines every 10 s: presents, FG on and resets, upscaler scene tags per present (`1` expected; `0` / `2+` = colour and motion from different frames), how many frames had the HUD split and why the others did not, and GPU-read motion-vector statistics of what frame generation got (share of moving pixels, object motion that differs from the camera's, effect coverage and effects over moving objects, sky, mean / camera-only / max motion in render pixels). `R2_DLSS_FG_MV_DEBUG=1` (or `R2_FG_DEBUG=2`, which also turns the stats on) tints the shown frame with the motion vectors frame generation gets: **green** = object motion (differs from the camera's by more than 1 render pixel; stronger green = more), **blue** = camera motion only, **magenta** = invalid (NaN / behind the camera), untouched = still; ghosting on something moving that is not green (a character, the weapon) means it has no motion vectors of its own. `RSX_DLSS_OBJMV_SWAY=1` (**default on**; `0` = old behaviour): a draw whose vertex shader sways its vertices by a per-vertex weight (wind-blown grass and leaves) is checked with that weight in place; if the sway moved since the last frame, the draw gets its own motion vectors instead of camera motion only (swaying foliage smeared under frame generation). The check runs the vertex program twice, so it is bounded to 64 draws per frame, and a program whose weighted part never moved is re-checked only every 120 frames. `RSX_DLSS_OBJMV_LOCKED=1` (**default on**; `0` = old behaviour): a draw whose shader constants are exactly the same as last frame's while the camera moved (the first-person weapon and arms, drawn locked to the view) gets its own (zero) motion instead of the world's camera motion (the background smeared around the gun edges); skinned (bone-palette) draws only, a non-skinned draw with unchanged constants already gets its own motion. With `R2_DLSS_FG_MV_DEBUG=1` both show green while turning. The `[r2aa] objmv own velocity` line counts them (and the sway probe checks). `RSX_DLSS_OBJMV_MULTI=1` (**default on**; `0` = old behaviour): draws issued as several index ranges at once, or as plain instances of one mesh, also get their own motion vectors in the onepass mode (they were skipped and kept camera motion only). `RSX_DLSS_OBJMV_DEFORM_REBASE=1` (**default on**; `0` = old behaviour): a mesh the game rewrites each frame (SPU-skinned characters, cloth, animated foliage) whose vertex data moved to another place in the game's buffers, with the same attribute layout and vertex count, uses last frame's copy of it (it fell back to camera motion: `layout` in the `objmv2 detail` line). `RSX_AA_EVALS` now defaults to `4096` scene draws per frame (was `2048`; `RSX_AA_EVALS=2048` = old): busy scenes hit the cap and the draws after it got camera motion only. The `[r2aa] objmv2 fallbacks` line (with the other 60-s statistics) lists why draws still got camera motion only: velocity redraw skipped (other depth target, multi-range, instanced, instanced constants, conditional render, programmable blending, other) and the deform layout fallbacks (attribute layout, vertex count / size, range only). `R2_DLSS_FG_CAM_RESET=0|1|2` (**default `1`**; `0` = old behaviour): on a frame whose camera motion was not measured — the camera vote failed and a guess was used (the largest group of draws, or no motion), or the depth check threw the measured motion away (`RSX_AA_MV_CONFIDENCE`) — while the camera moves (the game's own view-projection says so when the port has it; else the stand-in motion itself — a held motion or the largest group of draws, whose near-zero motion means a still camera; else the last measured motion, for up to 8 frames — by 1 render pixel or more; the motion the depth check threw away is not used, it is usually an object's), frame generation resets instead of blending the two frames with the wrong camera motion (the whole scene doubled while turning, seen at the Chicago Leviathan); the cost is one frame without a generated in-between. `2` also resets on a failed vote that reused the last measured motion (`RSX_AA_VOTE_HOLD`). The `[r2aa]` statistics line `frame generation reset on N moving frames without a measured camera motion` counts them.
- **Camera-cut sanity** (upscaler and frame generation) — `R2_FG_CAM_SANITY=0..3` (default `3`; `0` = old behaviour; bits): `1` = the frame's screen transform (depth range, used for the camera motion, the camera-cut check and frame generation's near / far) is the widest one most depth-writing scene draws used, not the last draw's: on many frames the last scene draw is the weapon with its own depth range (0.2), which made the world's depth reproject behind the camera and reset the DLSS / FSR history and frame generation as a false camera cut (`[r2aa] ... rule offscreen ... motion 1000000000` in `logs\run.log`); `2` = a camera cut found from a weak motion vote (under a quarter of the matched draws agree, the game's own view-projection not used) is held like an untrusted parallax cut (frame generation still resets, the camera motion is the last trusted one or none) and the depth check resets the history a few frames later only if it was a real cut. `logs\run.log`: `frame screen transform ... R2_FG_CAM_SANITY=3: N replaced by the widest depth range`, `camera cut: ... N weak-vote cuts held`.
- **FSR 3 Frame Generation (fallback)** — `R2_DLSS_FG=fsr3` (launcher: *Frame Generation* › *FSR 3 2x*, listed on GPUs that are not RTX 40/50), or `R2_FG_BACKEND=auto|dlss|fsr3` (auto = default: DLSS-G first, then FSR 3 2x when DLSS-G is unavailable; `dlss` = DLSS-G only; `fsr3` = FSR 3 only, also on RTX cards). AMD FidelityFX frame interpolation (FidelityFX API 1.1.4, `tools\ffx_vk\amd_fidelityfx_vk.dll`, MIT, shipped with the port) on any Vulkan GPU with a spare present-capable queue and timeline semaphores; 2x only. Needs Anti-aliasing = FSR, DLSS or XeSS (for depth and motion vectors) and SDR or HDR10 output. Uses the same inputs, HUD split (the HUD-less scene goes to interpolation, the HUD layer is composited on every shown frame), camera-cut resets and pause rules as DLSS-G. No Reflex while it is selected (FidelityFX's swapchain has no low-latency mode), so it adds a little more input lag than DLSS-G; the game's frame cap still applies to its own frames and FSR 3 paces the generated ones. Turning it on or off mid-game waits for the GPU once (a short hitch). HDR10 works on the usual A2B10G10R10 swapchain; a driver that only offers A2R10G10B10 for HDR10, and scRGB HDR, keep FG paused. Debug: `R2_DLSS_FG_DEBUG=2` (FidelityFX tear lines and reset markers); the HUD switches above apply too. Off reasons are logged as `[fg-vk] ...` lines.
- **HDR output** — `R2_HDR=1` (HDR10 / PQ, `VK_COLOR_SPACE_HDR10_ST2084_EXT`) or `R2_HDR=scrgb` (FP16 extended linear sRGB), opt-in, Compatible renderer, Windows HDR must be on (`R2_HDR=auto`: HDR10 only when Windows HDR is on for the game's monitor, else SDR). The final output pass converts the SDR image to linear and scales it so SDR white = `R2_HDR_PAPER` nits (default 203), then encodes PQ or scRGB; `R2_HDR_PEAK` (default 1000) is sent as `VK_EXT_hdr_metadata` and caps highlights. Falls back to SDR when the display/driver has no HDR surface format (the log says so). The F3 overlay, PC menu and screenshots (GDI) stay SDR.
- **Hold to skip movies** — `R2_CUTSCENE_SKIP` (default on): hold Space / Enter / A / Menu for 1 s while a pre-rendered movie plays and the port presses the game's own skip button. The game itself only skips a movie you have already watched; **Skip unwatched movies** — `R2_CUTSCENE_SKIP_ALL` (default on, `0` = off; only with Hold to skip movies) — makes the game's "watched?" check (`is_fmv_seen`, `func_002AB8EC`, called from the movie update `func_002CAD1C` at `0x002CAFC8`; hook `r2x_movie_seen` in `tools/hooks/r2.json`) answer yes while the hold is firing, at that one call only, so the game ends the movie through its normal skip path (the Cinematics menu's unlocks are unchanged; the game marks the movie watched as it ends, as after a normal skip). `logs\run.log` says how each movie ended (`[r2x] movie closed (played to the end / skipped: ...)`). In-engine cutscenes are not skipped (not safe: they drive level scripting). A *Hold Space / A to skip* notification when a movie starts: launcher *Show cutscene skip hint* (`PORT_SKIP_HINT`, or `R2_SKIP_HINT`) **Auto** (default, unset) shows it when Skip unwatched movies is on, since every story movie can then be skipped; *On* (`1`) always, *Off* (`0`) never. Holding skips either way.
- **Subtitles** — not available: the subtitles are drawn by the game's Scaleform movies at a fixed size; there is no size or background setting to hook. Camera shake: `R2_FX_CAMERA_SHAKE=0` above.

- **Photo mode** — `R2_PHOTO` (default on; `0` = off): **F7** pauses the game, hides the port's overlays (F3, crosshair, hints) and shows a short note; **F12** takes the screenshot; F7 again resumes. HUD hide: `R2_PHOTO_HIDE_HUD` (default on; `0` = off) shows the last frame as it was right before the game drew its HUD (the frame-generation HUD split, which then also runs with frame generation off; needs DLSS/FSR/DLAA on; one extra copy of the display buffer per frame). If that frame had no cleanly separable HUD, the HUD stays and `logs\run.log` says `photo mode: no HUD-free image`.
- **Cheats** (optional, off by default, single player; local co-op players get them too, enemies never): launcher Advanced ? *Cheats (single player)* or the F9 menu rows *Cheat: God mode*, *Cheat: Infinite ammo*, *Cheat: Infinite grenades* (`PORT_CHEAT_GODMODE` / `PORT_CHEAT_AMMO` / `PORT_CHEAT_GRENADES` = `1`; the older `R2_CHEAT_GOD` / `R2_CHEAT_AMMO` still work). - **Per-save backups (automatic):** just before the game overwrites a save, the previous version of that save folder is copied to `saves_backup\<save folder>\<date>_<time>\` (UTC time; the newest backup always sorts last, even after a clock change) (next to `gamedata`; inside the save folder you chose when the saves live elsewhere), keeping the newest 5 per save. Unchanged saves and saves over 64 MB are not copied; a failure only logs one `[savebackup]` line and the game saves as normal. `PORT_SAVE_BACKUP=0` turns this off, `PORT_SAVE_BACKUP_KEEP=<n>` (1-100) keeps n. This is separate from the launcher's whole-folder backups in `save_backups\` (made when you press Play).  **To restore one:** close the game, open `saves_backup\<save folder>\`, pick the `<date>_<time>` folder you want and copy its files into `...\dev_hdd0\home\00000001\savedata\<save folder>\` (replace the files), then start the game.
- **Save manager** — launcher **Saves & tools**: lists the saves (title from `PARAM.SFO`, date, size), *Back up now*, per-backup *Restore* (the current saves are backed up first as `_before-restore`) and *Delete*, and *Open* buttons. *Back up saves before playing* (`R2_SAVE_BACKUP`, default on, keeps the newest 10 automatic backups; `5` / `30`; `0` = off): Play copies the save folder to `save_backups\<date>_auto` when it changed since the newest backup.

**How to check them in game:** F9 opens *More PC Options*; toggle Screen blur and take damage / sprint; Colour-blind filter changes colours at once; F7 = photo mode; unplug the controller during play = pause message; hold Space during the intro movie of a level = skip; drag the window edge in windowed mode; Alt+Enter; `logs\run.log` lines start with `[r2x]` (options, level names, Discord, benchmark result).

## Graphics options

- **Frame rate:** 60 fps by default (the game was 30 fps on PS3). The game's own frame limiter is replaced by a precise PC-side one, the same idea as RPCS3's "Unlock FPS" patch. 30 fps is still available in the launcher.
- **Display mode:** borderless fullscreen, exclusive fullscreen or windowed, with VSync off / on / adaptive.
- **Anti-aliasing → NVIDIA DLSS** uses DLSS on GeForce RTX cards and falls back to FSR 3.1 on other GPUs. The DLSS SDK is downloaded by Setup into `tools\dlss` (if that fails, the port still builds without it).
- **Upscaling** (with FSR or DLSS on): Native (DLAA), Quality, Balanced or Performance. The default is DLSS Performance at a 4K render resolution, which is then downscaled to your screen: sharper than native at about the cost of native. Menus and HUD stay at full resolution.
- **Intel XeSS (experimental, Compatible renderer):** XeSS 2 (`rpcs3/Emu/RSX/VK/VKR2XeSS.cpp`, Vulkan `xessVK*` API, Intel's `libxess.dll`; runs on any GPU through DP4a) is hooked into the RPCS3 renderer's upscaler. Pick **Intel XeSS** in the launcher's upscaling option, or set `RSX_FSR=4`. If XeSS can't start, or on the native renderer, FSR 3.1 is used instead. The preset follows the Upscaling ratio (Native → Native AA, Quality → Ultra Quality, Balanced → Quality / Balanced, Performance → Balanced / Performance). `RSX_XESS_QUALITY=aa|uqp|uq|q|b|p|up` asks for a preset, `RSX_XESS_JITTER_SIGN=-1` / `RSX_XESS_JITTER_SIGN_Y=-1` flip the jitter, and `RSX_XESS_LOG=1` logs XeSS's own messages. Setup downloads the XeSS SDK (`tools/xess/`) after you accept Intel's licence.
- Moving objects (like rotating weapon pickups) are masked for DLSS so they don't leave ghost copies.
- **Low-end PCs:** the launcher's **Recommended for this PC** button picks settings for your CPU and GPU. Tuned for a 4-core CPU, a GTX 1050-class GPU and 8 GB of RAM; on 4 cores the first level holds 60 fps. On CPUs with fewer than 8 threads the port stops raising thread priorities (except the RSX thread's, `PORT_RSX_PRIO`) and pinning threads to cores, and its busy-wait loops give the CPU to other threads. The audio threads are the exception: on every CPU (`SPURS_AUDIO_BOOST_FORCE`, default on) the synth lane, the game's audio threads (`syn_tick`) and raw SPU 0 (one step up, only while its waits park) keep a raised priority, so the game sound keeps its speed when the frame rate drops (`SPURS_AUDIO_BOOST_FORCE=0` turns this off, and so does `PORT_PLACE_AUDIO=0` unless `SPURS_AUDIO_BOOST_FORCE` is set). The game's job-manager spin-waits hand the core over every 8th check and pause in between (`R2_SPIN_YIELD_EVERY=1` = every check, the old behaviour), and only one background shader thread runs during play on 8 threads or fewer (`R2_PRELOAD_THREADS`). If a 4-core PC still stutters, use 30 fps, or let the game reduce detail earlier: *Reduce detail when the CPU is slow* = Earlier (`R2_GOVERNOR_MS=30`). Advanced: `PS3_PRIO_BOOST=0/1` forces priority boosts off or on; `PORT_MAIN_CPU=<n>` pins the main thread to CPU n.
- **Shader-program re-sends** (renderer, on by default): the game sends the same shader programs again hundreds of times per frame. A re-sent fragment program with the same code only has its constants refreshed (`R2_FP_REBIND=0` turns this off), a vertex program uploaded or selected again with the same code keeps its analysis (`R2_VP_REBIND=0`), and when only render state changed and the previous draw's pipeline still matches it is reused without a cache lookup (`R2_PIPE_MEMO=0`). `R2_RSX_PROF=1` shows them as *re-sent FP/VP kept* and *pipeline memo hits*. All renderer switches are listed in `ps3recomp/third_party/rpcs3/README.port.md`.
- **Skipped re-uploads** (renderer round 8, on by default, output byte-identical): transform constants that have not changed since the last upload for the same vertex program are not uploaded again (`R2_XFORM_MEMO=0` turns this off), and an index range identical to one already converted this frame reuses the converted copy (`R2_IDX_DEDUP=0`). `R2_FIFO_MERGE=1` (off by default) lets RPCS3 merge back-to-back draws from 400 draws per frame instead of 2,000 (`R2_FIFO_MERGE=<n>` sets the threshold). Asynchronous texture streaming (`R2_ASYNC_TEX=1`) stays off: it only moves the GPU copy to another queue (the CPU work stays on the render thread), stops texture memory reuse and adds queue hand-overs, and the profiler shows almost no texture uploads in play (`texture uploads` on the `r8 per frame` line). `R2_RSX_PROF=1` prints two `r8` lines (where the end of each draw goes, Vulkan recording share, skipped bytes, pipeline misses, FIFO redundancy); adding `R2_RSX_CENSUS=1` prints `r9 census` lines (most frequent GPU commands, render-target, depth and texture formats) used to pick the next game-specific fast paths.
- **ZCULL labels over a flip** (`R2_ZCULL_FLIP_LAG=<n>`, experimental, **default 0 = off**): in strict ZCULL mode, lets occlusion labels still waiting on the GPU be carried over up to `n` flips instead of waiting at every flip. They are also released whenever the RSX command queue runs dry. It hung Resistance 3 in one bench, so leave it off unless you are testing it.
- **Occlusion queries kept over a flip** (RPCS3 #18148, missing or popping objects at uncapped frame rates; on by default, same as Resistance 3): RPCS3 throws away every occlusion query the game has not read yet at each flip (a regression since RPCS3 #18019), so objects tested late in a frame get a stale or zero visibility result. The port keeps those queries for one more frame; queries still unread a flip later, or more than a quarter of the query pool, are dropped as before, so nothing leaks and no GPU wait is added. Logged as `[zcull] flip keep (default; RSX_ZCULL_FLIP_CLEAR=1 reverts): ...` at start-up and every 10 s. `RSX_ZCULL_FLIP_CLEAR=1` = RPCS3's discard, `0` = no flip clear at all.
- **Occlusion reports flushed when the RSX goes idle** (on by default; `RSX_ZCULL_IDLE_FLUSH=0` turns it off): with relaxed ZCULL sync, an occlusion report the game polls could sit in an unsubmitted Vulkan command buffer while the FIFO ran dry, so the game's per-object occlusion wait timed out after 1 s (the hang of 2026-11-13). After 200 us of idle FIFO with a claimed report the game already read, the RSX thread now submits it. Listed in the `[native]` line as `rsx-zcull-idle-flush` (shown off when ZCULL sync is strict or queries are off, where it never runs).
- **Occlusion reports the game is waiting on are submitted after 1 ms** (on by default; `RSX_ZCULL_CRIT_FLUSH_US=<us>`, default `1000`, `0` = off): with relaxed ZCULL sync and the game's blocking occlusion wait (`R2_OCC_BLOCKING=1`), a report the game already reads could stay in the open Vulkan command buffer until the next natural submit, while the game thread waited 18-26 ms per frame (`guestwait top 0x001723c8`) in big scenes (water, the giant machines). Once the oldest claimed, unsubmitted report is older than the threshold and the guest has touched report memory, the RSX thread hints it to the GPU (same hint strict sync issues; it only submits if that query is in the current command buffer). Counted as `zcull-forced` on the `[spike]` line.
- **Occlusion kick** (on by default; `RSX_OCC_KICK=<draws>`, default `384`, `0` = off; `RSX_OCC_KICK_MIN_US=<us>`, default `750`): while the command buffer being recorded holds an occlusion query, it is submitted once it has that many draws and that much time has passed since the last submit, so the GPU starts the work in front of a report early instead of all at once when the report is flushed. Only submit timing changes. `[occ] kick 5 s:` shows kicks/s and draws per kick.
- **Precise occlusion submit** (on by default; `RSX_OCC_PRECISE=0` = off, `RSX_OCC_PRECISE=<n>` (n > 1) = at most n per 16.7 ms, default 6; `RSX_OCC_PRECISE_MIN_US=<us>`, default `250`): the report addresses the game blocks on (`func_006483A8`) are learned; when `GET_REPORT` claims a learned address again, the command buffer holding its query is submitted at once. Only submit timing changes; `RSX_OCC_KICK` stays the fallback. `[occ] precise 5 s:` shows learned addresses, submits and rate-limited claims.
- **Speculative-visible occlusion answers** (off by default; `RSX_OCC_SPEC_VISIBLE=1`, needs `R2_OCC_BLOCKING=1`; `RSX_OCC_SPEC_NEED=<n>`, default `2`): a late set whose reports were all visible in its last n real evaluations is answered visible at once instead of waiting (never hidden). A report-write fence on that report then keeps every set visible until the RSX wrote it and two more guest frames began (the late-write popping that made the blocking wait the default). `[occ] spec-visible 10 s:` shows avoided waits and the all-visible frames they cost.
- **No frame stall on late occlusion results** (on by default; `R2_OCC_NOWAIT=1`, needs `R2_OCC_BLOCKING=1` and `RSX_OCC_SPEC_VISIBLE=0`; `0` = the game's own wait, exactly as before): the main thread's per-object occlusion wait (`rsx:occlusion-report@0x001723C8` on `[spike]` lines, 10-30 ms in big fights and explosions) now waits at most `R2_OCC_NOWAIT_US` (default `2000`); a set still not in is answered at once for that frame (`R2_OCC_NOWAIT_LATE`, default `glare`): objects are drawn visible (never hidden: an object that really is behind a wall is drawn and hidden by the depth test, at the cost of a few extra draws), while the light-flare points tested in the same sets keep their last real result (at most 8 frames old; none yet = not visible). Answering those visible too made every flare behind a wall glare for that frame - the sudden bright flash for about a second when the jungle first appears in the intro. `R2_OCC_NOWAIT_LATE=prev` also gives objects their last real result (visible when there is none); `=visible` is the old all-visible answer. Logged as `[occ] nowait late answers 10 s:` (with `PORT_HITCH_LOG=1`). Its reports can still land after the game reused their slots (the popping above), so the first occlusion read of the next frame drains the RSX once: it waits until the RSX has run every command sent so far and written every report claimed by then. The main thread is held during that wait (no slot can be reset), so afterwards every report slot holds its newest result and the game's own results are exact again. A drain that takes longer than `R2_OCC_NOWAIT_DRAIN_MS` (default `100`) draws that frame visible and retries next frame; after 3 in a row it turns itself off (the game's own wait, with all sets drawn visible until the RSX has caught up once on its own). `R2_OCC_NOWAIT=2` also skips the one global set (`0x0026C1E0`, possibly flares/glows: a flare could then show through a wall for a frame). Logged as `[occ] R2_OCC_NOWAIT=...` at start and `[occ] nowait 10 s:` (sets drawn visible, drains and their time). Not for the frame-label wait (`rsx:frame-label@0x006364A0`), which is the game holding the CPU at most a frame or two ahead of the GPU.
- **Present uses the display surface's own scale** (#27; `R2_PRESENT_SURFACE_SCALE`, default `1`, `0` = old): the shadow-map scale, effects full-res and 4-sample-target upgrades raise the global resolution scale (for example 200% -> 800%) while their target is bound, until the next target is bound. A flip in that window sized the shown picture by the raised scale (`[r2aa] present downscale: 10240x5760 -> 2560x1440` or `5120x2880`), so for one frame the whole picture sat in the top-left quarter (or sixteenth) with stretched edges around it: a "flicker across the screen", most often in water areas. The flip now uses the scale the display surface was drawn at. With `R2_PRESENT_DIAG=1` logged (first 8) as `[r2aa] present: active scale X% at flip, using display surface's Y%`.
- **Scaled depth copies are one GPU blit** (`RSX_DEPTH_BLIT_DIRECT`, default `1`, `0` = the upstream carrier path): when the game copies a depth buffer to a depth buffer of another size (R2 fights: about 20-30 per frame between the scene depth and its half-size copy, at 300% 3840x2112 <-> 1920x1056), RPCS3 on Turing+ NVIDIA sent each copy through a colour carrier: depth and stencil separately, image -> buffer -> colour image -> scaled blit -> buffer -> image, with a barrier between every step. A RenderDoc replay of an R2 fight frame (2684) put those buffer copies at 30.6 ms of the frame's 40 ms GPU time; all draws together were about 4 ms. Now the depth buffer is blitted directly with nearest filtering when the GPU supports blits of that depth format (logged once as `[rsx] depth scale blits for format ...`), which selects exactly the same texels, so the result is bit-identical. Falls back to the old path when the format has no blit support, when the copy is linear-filtered (`RSX_BLIT_EXACT=0`) or the image is copied to itself.
- **No inherit copy before the upscaled-scene writeback** (`RSX_WB_SKIP_INHERIT`, default `1`, `0` = old): under DLSS/FSR/XeSS the upscaled image is copied into the full-resolution scene surface. RPCS3 first filled that surface with a scaled copy of the reduced-scale scene (and could clear or reload it from memory) that the copy then overwrote completely: a 2560x1408 -> 3840x2112 blit every frame at 300% (RenderDoc 2684 EID 2715). When the copy covers the whole surface that step is skipped.
- **4-sample effect targets at their sample resolution** (`RSX_AA_SAMPLE_RES`, default `1`, `0` = old): DLSS/FSR/XeSS turn host MSAA off, so a PS3 4x (2x2) antialiased target became a 1-sample image at its pixel size, although its memory holds the 2x2 sample grid. The game's half-size effect buffer (640x352, 4x) shares its memory with the 1280x704 post buffer that way: every switch between the two copied the post image down to half size and back up with nearest filtering, about 15 times a frame (RenderDoc 2684 EIDs 2785/2830), so the post chain and the final picture were a pixel-doubled half-resolution copy of the upscaled image (and the depth buffer made the same trips). These targets are now drawn at twice the scale (one pixel per PS3 sample), so the copies are exact 1:1. Only targets whose sample grid fits within the scene size are affected.
- **Blit trace** (`RSX_BLIT_TRACE=N`, default off; `1` = 300 lines): prints `[blit]` lines for the first N game blits (NV3089: guest source/destination address, pitch, size, scale, host rectangles, filter) and surface-cache inheritance copies (address, pitch, native size, samples per pixel, scale, rectangles). For diagnosing blurry or pixelated passes.
- **Early readback copies that are always wasted are stopped** (`RSX_ADS_KICK_ADAPT`, default `1`, ported from Resistance 3; `0` = copy every time): the async readback (`RSX_ADS_ASYNC_RB`) copied a hot render target to host memory ahead of the CPU/SPU read, but in R2 the surface is drawn again after the copy nearly every time (`kicks 1105 wasted 1100` per 5 s), so each was a full GPU copy plus DMA load for nothing. After 3 unconsumed copies in a row a surface is only copied early on every 32nd read (a probe that resumes as soon as one is used). Exact: the read path copies the surface itself when there is no early copy. Logged as `| kick-adapt suppressed N` on the `[ads-rb]` line.
- **RSX memory tiling** (RPCS3 #19676 / #19785; on by default, same as Resistance 3): "Handle RSX Memory Tiling" is now on (`rpcs3_config.yml`, and forced on by the renderer for older edited ymls), so surfaces the game keeps in tiled main memory are detiled when they are loaded as textures or render targets and re-tiled when written back, instead of being read raw (striped / purple textures). CPU blits whose source is in a tiled main-memory region are detiled first too (`RSX_BLIT_DETILE_SRC=0`, old name `R2_BLIT_DETILE_SRC`, turns that part off; the first ones are logged as `[tiling] RSX_BLIT_DETILE_SRC: detiled CPU blit source ...`). Logged as `[r2rsx] tiling: Handle RSX Memory Tiling on`. `RSX_TILING=0` (old name `R2_RSX_TILING`) turns tiling off. Cost: nothing for render-thread work outside tiled main-memory surfaces (a 15-entry tile check per texture / surface / blit lookup); a compute detile or tile pass per load / write-back of a surface that does sit in a tiled main-memory region. The CPU blit detile/re-tile is byte-identical to the original per-texel code but copies 32-byte runs, only touches the source rows and columns the blit reads and reuses a per-thread buffer: a 1280x720 32-bit blit source went from 5.4 ms to 0.46 ms and its re-tile from 4.2 ms to 0.7 ms (micro-benchmark, `scratch\detile_bench`); `RSX_DETILE_FAST=0` restores the per-texel code (logged once as `[tiling] RSX_DETILE_FAST=...`). The source window also covers vertically flipped blits (read upwards from the source), horizontally flipped blits (read right to left from the source), clip rectangles taller than the source, and the unpadded read of swizzled blits to sizes that are not a power of 2. The first three used to read past the scratch buffer, and the last one read stale bytes between rows when `RSX_DETILE_FAST` was on.
- **Accurate ZCULL stats A/B** (`R2_ZCULL_ACCURATE=0|1`): overrides the renderer's "Accurate ZCULL stats" setting from `config.yml` (default `true`). Unset = use the yml value, unchanged. `0` = fast approximate occlusion counts: less GPU waiting, but objects may pop in or out. The value in use is shown in the `[r2rsx] perf:` log line as `ZCULL accurate`.
- **Occlusion count mode** (`RSX_ZCULL_COUNT=approx|precise`, same switch as Resistance 3): `approx` = RPCS3's "ZCULL Accuracy: Approximate", where any visible pixel reports the object as fully visible, so an object near the game's pixel threshold cannot drop out from DLSS jitter or reduced-scale count noise. `precise` = exact counts. Takes priority over `R2_ZCULL_ACCURATE`. Unset = the yml value (precise), because Resistance 2's sun and bloom occlusion fades with the exact count. Other values are ignored, with a warning. Logged as `[r2rsx] ZCULL counts: ...`. **Why R2 and R3 differ** (deliberate, not drift): R2 keeps *precise* for the sun/bloom fade above, while R3 defaults to *approx* because its per-object pixel threshold made Haven's carpet clip with jittered, reduced-scale counts (RPCS3 #12051 / #15928). Both use *relaxed* sync (`R2_ZCULL`): in R2 it measured 48 fps vs 33 fps strict on the helicopter bench with identical visuals, and in R3 it is paired with the blocking occlusion readers (`R3_OCC_BLOCKING`).
- **Scene depth vote** (`RSX_AA_CLASSIFY_DWRITE=1`, the Resistance 3 default; off here): the DLSS/FSR scene detection ignores a depth buffer written by fewer than a quarter of the depth-writing draws of the busiest main-view depth (depth copies/downsamples). Resistance 2 keeps the tested vote by default.
- **Depth bias at the resolution scale** (`RSX_DLSS_DEPTH_BIAS=scale|color|0`, same switch as Resistance 3; applies with or without DLSS). Vulkan's slope-scaled depth bias is measured per host pixel, so at a resolution scale `s` it is `1/s` of the PS3 value. *scale* (default since 2026-11-14) multiplies the slope factor by the bound target's scale on every target, shadow maps included. Before, with shadow maps at 300% but filter taps in PS3 texels, surfaces at a grazing angle to the light shadowed themselves into dark patches at distance. *color* is the previous default (shadow maps keep the upstream slope), and `0`/`off` is upstream. `RSX_DLSS_DEPTH_BIAS_LOG=N` logs the first N polygon-offset draws.
- **No anisotropic filtering on depth textures** (`RSX_ANISO_SHADOW=0|1`, same switch as Resistance 3). *0* (default since 2026-11-15) gives shadow maps and other depth-class samplers the game's own anisotropy instead of the `RSX_ANISO` override. 16x anisotropic shadow compares spread their taps over many shadow texels on distant or grazing receivers, which gives self-shadowing and bleeding. *1* is the old behaviour. `RSX_SHADOW_DIAG=N` (diagnostic, default `0` = off; e.g. 24) logs distinct depth-texture samplers and polygon-offset setups as `[shadowdiag]` lines. `RSX_DEPTH_DIAG=N` (diagnostic, default `0` = off; e.g. 48) logs the depth-path mechanisms (offset, depth bounds, alpha test, conditional render with CPU-skipped and GPU-predicated draw counts, jitter, shadow units) of polygon-offset / EQUAL / conditional draws as `[depthdiag]` lines. With hardware conditional rendering (NVIDIA, AMD), draws with a pending query are discarded on the GPU and counted as GPU-predicated, not skipped. `RSX_COND_RENDER_CPU=1` (default off, A/B test only, may stall) waits for each query on the CPU instead.
- **Per-draw CPU memos** (renderer): `RSX_SAMPLER_CACHE` (**default on**; `RSX_SAMPLER_CACHE=0` turns it off) reuses the derived sampler settings of a fragment texture unit when every register, format field, LOD bias and anisotropy input is bit-identical to an earlier one. `RSX_VTX_REUSE=1` (experimental, **default off**) skips re-copying an uncached vertex upload when its guest bytes are byte-identical to the same draw's copy already in this frame's vertex ring. Both give exactly the same output and save at most about 0.5 ms per frame in dense fights. With `R2_RSX_PROF=1` the `[r2rsx-prof]` block gets a line with memo hits and reused uploads. Both switches take the `[native]` switch values (`1`/`on`/`true`/`yes`, `0`/`off`/`false`/`no`) and are listed in the `[native]` line as `rsx-sampler-cache` and `rsx-vtx-reuse`. The sampler-cache key holds every register the sampler is derived from plus the effective LOD bias (the DLSS/FSR negative bias, including the alpha-test exception and `RSX_AA_ATEST_LOD`), and a bias or alpha-test change marks it dirty first, so a cached sampler never carries a stale mip bias (checked for the 2026-11-14 renderer audit; no change needed).
- `RSX_TEX_SEARCH_MEMO` (default on; `RSX_TEX_SEARCH_MEMO=0` = off) and `RSX_SAMPLER_CACHE_WIDE` (default on; `0` = off): two more exact RSX-thread memos for large outdoor scenes (R3's diner: about 3,000 draws and hundreds of textures per frame, RSX thread CPU-bound at 30-38 fps). `RSX_TEX_SEARCH_MEMO` remembers which cached texture the texture cache's lookup returned for an address, format, size and pitch, and reuses it while no texture section has been created, re-protected, blitted or invalidated since (framebuffer re-locks excepted, they can never answer a texture lookup) and that texture still passes every check the lookup applies; otherwise the full lookup runs as before. `RSX_SAMPLER_CACHE_WIDE` gives the `RSX_SAMPLER_CACHE` memo 16 hashed sets of 4 entries per texture unit instead of 4 entries, which outdoor scenes overflowed (about 600 re-derivations per frame). Both give exactly the same output. The `[texcache]` line ends with `lookups N (search memo M)`: memo-eligible texture lookups and how many the memo answered.
- `RSX_AA_PRECREATE_INIT` (default on; `=0` = at the first flips) and `RSX_AA_PRECREATE_IDLE` (default on; `=0` = create at the 3rd flip as before): DLSS/NGX setup can take about 3 s on the RSX thread. Run inside a flip, the upscaler pre-create (`RSX_AA_PRECREATE`) stalled a label the guest was polling, and R2 printed "GPU sit and spin timeout" at boot (the guest's watchdog gives up after about 2.5 s; the REF register is unused at that point, so its 0xffffffff value is not the cause). With a size file (`r2aa_size.txt`), the pre-create now runs in the renderer's init under the start-up screen, before the guest can queue anything. Without that, the flip-time pre-create waits for a sustained idle FIFO: no flip, no pending commands, deferred labels or zcull reports for `RSX_AA_PRECREATE_IDLE_MS` (default 250) in a row. If that never happens by flip 603, the first scene creates the upscaler. A later size or format change recreates it as before. The `[r2aa]` line says when it ran and how long creation took.
- `RSX_DS_RO_DEFER` (default on; `RSX_DS_RO_DEFER=0` = off): soft particles alternate draws that sample the bound depth (feedback-loop layout) with draws that don't, and each switch cost a depth layout barrier plus a render pass break (about 60 per frame in transparents). A non-sampling draw that writes neither depth nor stencil now keeps the feedback-loop layout and the read-only barrier chain stays elided; the restore runs at the next depth/stencil-writing draw or depth clear. Output-identical (no depth writes happen between the elided barriers).
- Log hygiene: `logs\rpcs3_rsx.log` no longer opens a compressed `.gz` copy (it never worked and left a 0-byte file and a "Log file open failed" line every run; `RSX_LOG_GZ=1` restores it). RPCS3's overlay icons are not shipped, so their absence is one notice instead of about 30 errors. FIFO-recover lines no longer end with a stale Windows error ("Not enough memory resources"). The `[texcache]` line counts `raced` faults: unclaimed faults on a page that another thread's fault had already opened again. They are retried and harmless; only the remainder are real unclaimed faults (logged as `[vm] unclaimed protection fault`).
- `RSX_AA_RESOLVE_MEMO` (default on; `0` = off) and `RSX_OBJMV_FAST_VHASH` (default on; `0` = off): cut the per-draw cost of the DLSS camera vote and object motion vectors. `RSX_AA_RESOLVE_MEMO` keeps the last 512 camera-matrix extractions (vertex program, branch bits and the exact constants it reads) and reuses a result when a later draw's inputs are byte-identical, for example the material pass after the depth pre-pass, or a camera that hasn't moved. The output is exactly the same. With `RSX_DLSS_OBJMV` on, the log prints `[aa] resolve memo: N hits, M misses` with the objmv2 line. `RSX_OBJMV_FAST_VHASH` hashes the same 16 sampled vertices per block 8 bytes at a time instead of byte by byte (about 4x faster). The hash is only compared with the previous frame's, so results can differ only on a 32-bit hash collision.
- **CPU profile** (Performance page): Auto picks from the cores the game can use (logged as `[cpu]`). Low (≤4 cores) turns off the timing spin-waits, folds the Vulkan submit thread into the render thread and uses fewer shader-compiler threads; below 8 CPU threads it also runs the RSX thread (`rsx::thread`) above normal priority, so the other game threads stop taking its core (`PORT_RSX_PRIO=0` turns this off, `1` forces it with any profile but Off; log: `[cpu] rsx::thread (thread N): priority above normal`). Mid (6 cores) shortens the spin-waits. High changes nothing. The port also spreads its main, RSX and FIFO threads over separate cores, keeps them on P-cores on hybrid Intel CPUs and lowers background threads. Advanced: `PORT_CPU_PROFILE=auto|low|mid|high|off` (env settings you set yourself always win); `PORT_THREAD_PLACEMENT=0` turns off thread placement. See *CPU performance switches* below.

## Graphics enhancements

Beyond DLSS / FSR, all optional and off by default (launcher: Graphics page, "QUALITY" and "VIEW"). Each logs a `[patch]` line at boot.

- **Native scene resolution** (`R2_PATCH_FULLRES=1`). Resistance 2 has dynamic resolution: its render targets are 1280x704, and each frame a governor (`func_002C3780`) reads the previous frame's GPU time from RSX timestamps; when it is over budget it draws that frame's 3D scene at 1152x640 inside the same targets, and the final pass stretches it 10/9 onto the 1280x720 display. This patch keeps every frame at 1280x704 (the targets' full size, so nothing can be cut off; the remaining 704 → 720 stretch is 2%). With `RSX_RES_SCALE=3` the scene is 3840x2112 instead of 3456x1920; `RSX_RES_SCALE=1.5` gives a 1920x1056 scene for 1080p → DLSS 4K. Rendering a true 1280x720 scene was not done: the 704-line targets are allocated at boot in a fixed video-memory layout shared by several systems, and the gain over 704 is under 3%.
- **No load shedding** (`R2_PATCH_NO_LOADSHED`, default on; `=0` or launcher *Never reduce quality under load: Off* restores the game). Disables the governor's GPU-time path entirely: no resolution drop, no LOD-distance cut (x0.75) and no effect-budget cuts (x0.5 / x0.25 / x0.05) on slow frames. The governor compares host RSX times with the PS3 budget, so on PC heavy views could trip it frame by frame: the scene viewport inside the DLSS/FSR input flipped between 1280x704 and 1152x640 (scaled), and LOD distances / effects popped (same finding as R3's `R3_NO_LOADSHED`). Implies `R2_PATCH_FULLRES`. The CPU-time path is left as is.
- **CPU detail governor** (`R2_GOVERNOR_MS=<ms>`, 20..200, or `off`; launcher: Performance › Processor, *Reduce detail when the CPU is slow*). The governor's CPU-time path cuts detail once a frame takes more than 36.6 ms of CPU time, i.e. below ~27 fps, and restores it under 30 ms. On weak CPUs (4 cores, e.g. Ryzen 5 3400G) `R2_GOVERNOR_MS=30` lets it step in earlier (cut above 30 ms / ~33 fps, restore under 24.6 ms), which keeps the frame rate and therefore the game audio closer to full speed in big fights, at the cost of the game's own reduced detail in those moments. `off` never cuts (fast CPUs that want full detail). Unset = the game's 36.6 ms.
- **LOD distance** (`R2_PATCH_LOD_SCALE=1.25 / 1.5 / 2 / 3 / 4`). Detailed models stay in use further away and distant objects fade out later. The multiplier is the one the game itself lowers to 0.75 under load; values above 1 are beyond what the game was tuned for, so watch for pop-in changes and frame time. The LOD rebuild (`func_00652F40` / `func_00652C24`) only clamps against small minimum distances, so values up to 4 are passed through unchanged. Far clip, foliage and particle limits were not found as separate tunables; on this game the LOD fade distance is what culls distant objects.
- **Field of view without broken shadows** (`R2_FOV_SAFE`, default on whenever a FOV is chosen). RPCS3's Extended FOV patch lowers the constant term of the game's `tan()` (`func_00788068`). Every `tan()` in the game shares that constant — the shadow-cascade fitting and the light frustums too — so the shadow maps stop covering what the camera sees and jump as it moves. Safe mode leaves the constant at 1.0 and widens only the 16:9 scene camera by exactly the same amount, in the two frustum-setter hooks (the culling frustum follows: the safe-mode hooks change the setter's inputs, so the stored tangents, projection and planes, and the LOD projection see the widened FOV, and the SPU geometry cull (dd413, native or lifted) has no FOV or guard-band constant of its own, it only tests the clip codes of the matrix the PPU hands it; no culling path that rebuilds a frustum from the original FOV was found in the 2026-11-14 audit). The launcher / PC menu choice and the live change in the PC menu work as before. `R2_FOV_SAFE=0` restores the plain RPCS3 patch.
- **Shadow resolution** (`RSX_SHADOW_SCALE=2 / 4`, Compatible renderer). The game's shadow maps (1024² and 256² depth-only targets) are rendered at 2x / 4x per side by the renderer: only depth-only, square, power-of-two targets between 256 and 2048 are scaled (capped at 8192), they are sampled at their own scale, and the slope-scaled depth bias is multiplied by the same factor to avoid shadow acne. Costs GPU time and video memory (a 1024² map becomes 4096² at 4x).
- **Shadow map scale cap** (`RSX_SHADOW_SCALE_CAP=<percent>`, default off): renders the game's shadow maps (every Z16 depth-only target up to 2048 of any size or aspect, so maps packed side by side share one scale, plus square power-of-two depth-only targets of 256-2048) at most at this resolution scale instead of the global one (at 300% a 1024² map is 3072²). `200` or `100` saves GPU time on the shadow passes; shadows get softer than at 300% (100 = the PS3's own sharpness). The scaled slope depth bias follows the cap. Ignored with `RSX_SHADOW_SCALE=2|4`. Logged as `[r2gx] shadow map ... capped to N%`.
- **Native shadow maps** (`RSX_SHADOW_NATIVE=0|1`, default 0 (off, opt-in)): renders Z16 depth-only shadow targets (any size up to 2048, including the 256x64 strips packed next to the square maps) at the PS3's native 100% scale, with no scaled slope bias. Shadows are PS3-sharp; set `0` for scaled shadow maps. Takes precedence over `RSX_SHADOW_SCALE`/`RSX_SHADOW_SCALE_CAP`, which only apply to maps it does not cover (set `RSX_SHADOW_NATIVE=0` to use them on Z16 maps). Logged as `[r2gx] shadow map WxH ... native 100%`. All three detect depth-only passes by checking only the active colour slots (R3 leaves stale addresses in inactive MRT slots).
- **Shadow slope bias multiplier** (`RSX_SHADOW_SLOPE_K=<k>`, default 1 (off), 1-8): multiplies the polygon-offset slope factor of the shadow maps (every Z16 depth-only target up to 2048, plus `RSX_SHADOW_SCALE`'s square maps), on top of any resolution ratio from the native / cap / `RSX_SHADOW_SCALE` paths; maps none of them rescales keep their resolution and get only the extra slope (R2 defaults, scale <= 100% or <= the cap). More caster bias against self-shadow acne (hatched stripes on grass blades and other thin or grazing casters); too much detaches contact shadows. Try `2`. Logged as `[r2gx] shadow slope bias xK ... shadow-map binds` every 5 s.
- **Precise vertex-program dot products** (`RSX_VP_PRECISE_DOT`, default 1 (round 11 briefly defaulted it to 0 as a rubble-garbage suspect; the garbage persisted, so it is back on); `0` = plain fp32 `dot()`): the DP4/DPH of every translated vertex program (and the vertex interpreter) use a compensated Dot2 sum. The scene sits in the last few percent of standard-Z depth, so plain fp32 rounding of world position x view-projection gave each mesh a few D24 steps of camera-dependent depth noise and the cut line between a poster and the wall behind it crawled by several pixels from frame to frame (poster edge flicker). Identical in pre-pass and EQUAL passes, so material passes still match.
- **Unjittered effect draws** (`RSX_FX_UNJITTER`, default 1 = additive effects; `2` = every blended effect draw; `0` = off): effect draws into the scene before the upscaler that write no depth and do not test EQUAL skip the camera jitter. Dust motes are ~1 render-pixel additive quads; jittered, the jitter phase decided whether they covered a pixel centre, and the DLSS bias mask shows that raw (sparkles popping in and out). Logged as `fx unjitter`.
- **Light quad jitter** (`RSX_AA_LIGHT_JITTER=0|1`, default 1 (on) since round 10): the deferred light quad (stencil-tested, 3-6 vertices) gets the jitter shift of its stencil marks, so the view ray it interpolates pairs with the jittered depth of the same sample. Off, the rebuilt position is off-surface by dz/dx x jitter, which moves shadow edges on grazing floors and toggles self-shadowing on thin blades every frame (white-noise flicker DLSS cannot converge). Logged once as `light quad jitter f...` and counted in the 5 s `light quads given their stencil marks' jitter` line.
- **Full-resolution effects** (`RSX_FX_FULLRES=1 / 2`, Compatible renderer). The PS3 draws particles, smoke, glow and the blur inputs (bloom, depth of field, motion blur) into half- and quarter-resolution targets. `1` renders the half-resolution passes (half the scene size) at full resolution, `2` also the quarter-resolution ones (bloom). The game's own upsample and composite passes then read them at their new resolution, so they need no change. This is how depth of field and motion blur get better here: the game's passes, at full resolution; there is no separate replacement pass.
- **Ultrawide HUD** (`RSX_HUD_FIX=1`, experimental, Compatible renderer, with `R2_ASPECT`). The 3D view stays Hor+ and stretched to the window; the HUD and menus (drawn after the 3D scene into the final picture) are squeezed back into a centred 16:9 area, so they are not stretched. Only 2D (orthographic, w = 1) vertices are moved, the same split RT64 uses (gameplay projection widened, 2D anchored to a 16:9 safe area): 3D draws, full-screen quads (the tone-mapped scene, fades, damage and scope overlays, letterbox bars) and edge-to-edge vertices stay where they are. The 3D view is widened game-side (scene camera frustums only, with K = 1 for every other `tan()`), so shadows stay aligned as with *FOV safe*. Limits: world-anchored markers (objective and grenade markers) drift towards the centre, and HUD elements meant for the screen edge sit at the edges of the 16:9 area. Because of that, `R2_ASPECT` stays off by default (also on non-16:9 displays): turn on *Ultrawide* and *Ultrawide HUD* together.
- **Ambient occlusion** (`RSX_SSAO=1`, experimental, Compatible renderer). A screen-space AO pass from the scene depth, applied to the 3D scene before the game's post-processing (found the same way as the DLSS scene detection). Needs a non-MSAA scene (*Anti-aliasing* off or FSR); with MSAA it is skipped (logged). With DLSS, FSR or XeSS it runs on the upscaler's input (internal resolution, same frame and jitter as the scene the upscaler gets), just before the upscale; `RSX_SSAO_DLSS=0` turns it off under DLSS only, `RSX_SSAO_UPSCALER=0` restores the old post-upscale trigger (diagnostics only). `RSX_SSAO_STRENGTH=0..1` (0.6), `RSX_SSAO_RADIUS=0.1..8` (1.0), `RSX_SSAO_DEBUG=1` shows the AO term alone. The game's near plane is not known to the renderer, so the radius is a screen-space approximation.
- **CACAO ambient occlusion** (`R2_AO_MODE=cacao`, experimental). AMD FidelityFX CACAO at the same point as the port SSAO (the scene before post-processing / the upscaler input), multiplied into the lit scene: Resistance 2 has no AO of its own to replace. Uses the game camera's near / far / field of view when the upscaler knows them (else near 0.08, far 4000, 44.6 degrees). `R2_AO_QUALITY=low|medium|high` (3 / 5 / 12 samples), `RSX_CACAO_RADIUS` (0.6, metres), `RSX_CACAO_STRENGTH` (0.5) (below FFX's defaults: the AO darkens the final lit colour, so flat walls must stay unshaded), `RSX_SSAO_DEBUG=1` shows the AO term alone. Skipped with MSAA like the port SSAO. Costs about 0.2 / 0.25 / 0.35 ms at 1280x704 (RTX 4070 laptop, offline harness).
- **Texture packs** (Compatible renderer). `RSX_TEXDUMP=1` (or `=<folder>`) writes every texture the game uploads to `texdump\`: DXT1/3/5 as DDS (with mipmaps), 32-bit ARGB as PNG, named `<key>_<w>x<h>_<format>_m<mips>`, and lists each one in `texdump\manifest.tsv` (key, size, format, mips, file; textures already listed are not dumped again on the next run). `RSX_TEXPACK=1` (or `=<folder>`) loads replacements from `mods\textures\` (searched recursively; only the first 16 hex digits of the file name, the hash, matter): a DDS in the same DXT format or a PNG, the same size as the original or 2x..8x it with every mip level (HD, see HD UI pack below). Missing mip levels are generated (PNG) or kept from the game (DDS; a swizzled texture with missing levels is left unchanged). The key is a 64-bit hash of the texture's content (every mip level, pitch padding excluded) plus its size, format and mip count, never its memory address, so it is the same across runs and in every level. With neither switch set there is no per-upload cost.
- **HD UI pack** (`RSX_HD_UI=1`; experimental, off until you make a pack): AI-upscaled menu / HUD / loading-screen textures, made on your PC from your own game (nothing game-derived ships with the port), like the Bloodborne PC port's 4K UI mods. Most of the HUD is Scaleform vector art and text, which already renders at full resolution; this sharpens the bitmap parts (icons, button prompts, map and menu art). **One click:** launcher › Saves & tools › **Create HD UI pack**. It runs `HDUIPack.exe` (built with the port, nothing to install): it reads the menu / HUD textures straight from the game's archives (`USRDIR\packed\**\*.psarc`, the images the Scaleform menus show), upscales every texture with Real-ESRGAN on the graphics card (`tools\hdui_upscaler\`, comes with the port: Real-ESRGAN-ncnn-vulkan built against ncnn 20261020, SHA-256 checked before every run, with the official `realesrgan-x4plus` model, taken from Real-ESRGAN's release zip, downloaded once (45 MB, SHA-256 pinned); alpha separately, so edges stay clean; textures under 64 px are padded with their edge pixels for the model and cropped back) to 2x..4x the original (4096 px per side at most) and writes DDS files in the game's own format with every mip level to `mods\hd_ui\`. The launcher shows progress (done / total, time left) and can cancel; when it finishes it turns HD UI pack on and shows a summary. A full pack (~740 textures) takes a few minutes on a recent graphics card (about 1 hour on a 6-core CPU if it falls back to the CPU) and a few GB of disk; running it again continues where it stopped (finished textures are kept, also after a cancel) and **Update HD UI pack** only makes what is missing. Every upscaled texture is compared with the original (reduced back to its size); one that does not match (damaged output) is not used: from the graphics card it is made again on the CPU, and if the CPU's is unlike it too the game keeps the original texture and `pack.tsv` notes it as `refused` so later runs leave it alone (`HDUIPack.exe --force` tries again). Textures an earlier version made with another model before this check are made again by the next Update. **Remove HD UI pack** deletes `mods\hd_ui\` and turns the option off (the launcher waits for the deletion to finish; anything an ended removal left in `mods\.hd_ui.removed` is deleted by the next run). Without a usable graphics card it runs on the CPU (see *GPU safety*). How it matches the game: the key the game's texture upload computes (a 64-bit hash of the texel data, size, format and mip count) is computed by the tool from the same archive bytes with the same code (`rpcs3/Emu/RSX/Common/r2_hd_ui.h`), so no dumping or playing is needed. The pack is built beside it in `mods\.hd_ui.stage` (a dot folder, which nothing loads; on the same drive, so `--out` and `--tools` may be on different drives) and renamed into place, so an interrupted run never leaves scratch files where the game loads replacements; if a run is cancelled between the two renames, the next run puts the new (or else the previous) pack back, and while a file is held open (antivirus, Explorer) it keeps both and says so instead of deleting anything. In game the log says `HD UI pack: N texture(s) in mods\hd_ui` at start and `HD UI pack: N texture upload(s) replaced so far` as they are used. A replacement is 2x..8x the game texture (same factor on both axes, 8192 px per side at most) and is drawn over exactly the same screen area, so layouts do not change; files that do not match (size, format, missing mips) are skipped with a log line and the game's texture is used. Copies (blits) from a replaced texture are taken from the game's own texture, so they are never cut off. `RSX_HD_UI=<folder>` uses another folder; `RSX_HD_UI_CACHE_MB` (default 512) caps the decoded replacements kept in memory. **GPU safety:** the AI upscaler runs on the graphics card (Vulkan) in **one** upscaler run for all textures, with the upscaler's own tile size and job counts, the way the Bloodborne PC port (Lantern Engine) runs the same Real-ESRGAN with the same model, which works on an RTX 5070 (earlier versions started the upscaler hundreds of times with tiny tiles and the remacri model; on an RTX 5070 that ended in NVIDIA driver resets, nvlddmkm 13 / 153, and a PC restart). If anything goes wrong on the graphics card (the upscaler's own stop at the first failed GPU submission, `GPU_STOP`; a lost device, `vkQueueSubmit failed -4`, seen by the watchdog; 90 s without progress; a crash or no output) the upscaler is ended at once, so nothing more is sent to the graphics card; the textures it already made are kept and the rest are made on the CPU (`tools\hdui_upscaler\bin\realesrgan-ncnn-cpu.exe`, which contains no Vulkan code at all, with the bundled `fast` model, at below-normal priority on about half the CPU threads). The failure is recorded in `tools\upscaler\gpu_fault.txt` and later runs use the CPU until you delete that file (e.g. after a driver update) or run `HDUIPack.exe --use-gpu` (when that run makes everything on the graphics card, the file is removed). When no usable Vulkan graphics card is found or the GPU upscaler does not start (no fault), that is recorded in `tools\upscaler\gpu_unavailable.txt`: later runs keep the textures the CPU made with `fast` instead of making the whole pack again, and each **Update** first runs one small test image on the graphics card; once it works (e.g. after a driver install) the file is removed and those textures are made again with `x4plus`. `tools\upscaler\upscaler_running.txt` exists only while the GPU upscaler runs; if it is still there after a reboot and Windows logged an unexpected shutdown at its next start (Kernel-Power 41 / EventLog 6008 within minutes of the first start after the run), or Windows' log cannot tell, that counts as a failure too and the marker and the upscaler's log are kept as `tools\upscaler\upscaler_crashed.txt` / `.log`; a normal restart or sign-out does not count. `HDUIPack.exe --cpu` uses only the CPU; `--safe` runs the GPU in conservative mode (`-c`: fp32 storage, no fp16 / int8 / cooperative-matrix / subgroup ops) with `-t 64` tiles and `-j 1:1:1`; `--status` prints where the next run upscales (`@gpu gpu|cpu ...`) and starts nothing. Advanced: `HDUIPack.exe --help` (`--model x4plus` (the default on the graphics card) / `fast` (the default on the CPU) / `remacri` / `ultrasharp` (sharper ESRGAN models for personal use), the larger ones downloaded once into `tools\upscaler\models\` and SHA-256 checked and about 30x slower than `fast` on the CPU; `--use-gpu`, `--cpu`, `--force`, `--safe`, `--status`, `--dry-run`, `--list`, `--gpu N`); the older dump-based path still works for textures outside the archives: set Dump textures to **Menus / HUD only** (`RSX_TEXDUMP=ui`), play, then `python tools\hd_ui_pack.py` (Python 3 with Pillow and numpy) writes to the same folder. Tests (offline, no game run): `cmake -S project\tests\hd_ui -B build\hd_ui_test -G Ninja -DCMAKE_CXX_COMPILER=clang-cl -DCMAKE_C_COMPILER=clang-cl` then `cmake --build build\hd_ui_test` and `ctest --test-dir build\hd_ui_test` (`hdui_upscaler_install` checks the pinned upscaler files and runs a test image through the real CPU-only build; `hdui_gpu_safety` checks the command line, the GPU-or-CPU choice after a fault, that a crash's evidence is kept, the watchdog on a stand-in upscaler, the padding of small textures and the single GPU run handing the rest to the CPU after a lost device, without starting the Vulkan upscaler; with the game files present, `hdui_real_keys` checks every key against RPCS3's own upload layout code). The `x4plus` and bundled `fast` models are BSD-3-Clause; the optional remacri / UltraSharp models are for personal use (CC BY-NC-SA); do not share the generated pack.
- Renderer-side switches (see the bridge): `RSX_ANISO`, `R2_LOD_BIAS`, `R2_HIGHP_Z`, `R2_MSAA`, `R2_GPU_TEX_SCALING`, sharpening.
- **GPU selection** (`RSX_ADAPTER`, default unset = `rpcs3_config.yml` Video › Vulkan › Adapter, else the first discrete GPU): the exact Vulkan device name as listed in `logs\rpcs3_rsx.log` (`Found Vulkan-compatible GPU: '...'`), e.g. `RSX_ADAPTER=AMD Radeon 780M Graphics` to run a hybrid laptop on its integrated GPU.
- **Video memory** (shared with Resistance 3, GitHub R3 #33): on a GPU with 2.5 GB of video memory or less (for example a 2 GB GeForce GTX 1050), a render resolution above 1.25x (1600 x 900) is lowered to 1.25x when the renderer starts, since 1920 x 1080 and higher run out of video memory there; the run log then has one `[rsx] ... MB of video memory: render scale capped` line. `RSX_VRAM_AUTOCAP=0` keeps the chosen resolution. When video memory runs out anyway, the renderer first drops unused cached textures and moves unused render targets to system RAM, then places new graphics data in system RAM (slower; one `[rsx] video memory is full` line). Only if that also fails does the game close with a message and a crash report in `logs\crash` instead of freezing. Test switch: `RSX_VRAM_LIMIT_MB=<MB>` (256 to 65536, off by default) makes the renderer act as if the GPU had only this much video memory (with 2560 or less the cap above applies too; add `RSX_VRAM_AUTOCAP=0` to test running out).
- Texture-source diagnostics (shared with Resistance 3): `RSX_DEBUG_TEX_SRC=1` (`2` = every address) logs `[texsrc]` lines for texture addresses served by a mismatched render target (`FMT`, `BPP`, `DEPTH`, `SWZ`, `SIZE`) or uploaded from memory over a live GPU surface (`OVER`), with a summary every 2 s (`RSX_DEBUG_TEX_SRC_LINES`, default 3000). `RSX_DEBUG_TINT_SURFACE=<mask>` draws them solid green (`1` format / texel-size mismatch (`SWZ`, `SIZE` log-only), `2` depth as colour, `4` any surface, `8` `OVER`, `16` `OVER` on textures of at most 64x64; depth-format textures become a flat colour, not necessarily green, and multisampled ones are left alone; `RSX_DEBUG_TINT_ADDR=<hex>,…` also tints the listed texture addresses whatever their source). RenderDoc: `RSX_RDOC_FRAMES=<n>` makes `F6` (`RSX_RDOC_KEY`) capture `n` whole guest frames aligned to the game's flips; `RSX_RDOC_AT=<flip>` captures automatically. `RSX_DEBUG_SMALL_RT=1` logs `[smallrt]` lines (`FB`, `BIND`, `DROP`, `KEEP`, `NFLUSH`, `NSKIP`) for render targets of at most 64x64 (`RSX_DEBUG_SMALL_RT_LINES`, default 4000, caps `FB`/`BIND`; `RSX_DEBUG_SMALL_RT_EVENT_LINES`, default 4000, caps the others).
- `RSX_FLUSH_KEEP_NEWER=0` (shared with Resistance 3; default on): writing a render target back to guest memory skips the rows of newer overlapping surfaces, so a dead older target cannot overwrite them (R3's bullet-rubble chunk textures were trampled this way), and a write-back is skipped only when wholly excluded. `0` = upstream.
- `RSX_AV_NEIGHBOUR_SMALL_FLUSH=0` (shared with Resistance 3; default on): a CPU/SPU access fault next to a render target of at most 64x64 (`RSX_AV_NEIGHBOUR_SKIP`) writes it back instead of releasing it dirty (R3's 16x16 rubble targets share a CPU-written ring; the skip lost their GPU data). `0` = skip them too.
- `RSX_NV0039_PREINVAL=0` (shared with Resistance 3; default on): before an NV0039 buffer copy, the protected texture-cache pages of its destination are invalidated in one pass on the RSX thread instead of one access fault per page during the copy. `0` = the old fault-per-page behaviour.

Not found statically with enough confidence to patch: the game-side shadow-map allocation (render targets are allocated once at boot in a fixed video-memory layout, so shadow resolution is done in the renderer instead), motion blur, depth of field and film grain toggles, particle/decal limits. The game's own debug arguments (`-noeffects`, `-nodecals`, `-shadows` …) only remove things or enable debug views.

## Shader precompile and rebuilding the shader cache

Shader caches are never shipped with the port: they are built on your PC, from the shaders your game uses, the first time each one is seen. Launcher, Performance page, **SHADER CACHE**:

- **Compile shaders before playing** (default On, `PORT_SHADER_PRELOAD=1`, which means `R2_PRELOAD_BOOT=-1`; an explicit `R2_PRELOAD_BOOT` still wins): at start-up the Compatible renderer builds every pipeline in its disk cache before the game gets its first frame (the game's RSX context waits for it), so nothing seen before compiles during play. Progress: a centred **Compiling shaders N / M** panel with a progress bar, drawn into the game image (`R2_PRELOAD_OSD=0` uses a separate window, not shown over exclusive fullscreen) and log lines `[r2rsx] shader preload: compiling every cached pipeline before the game starts on N threads`, `compiling n/N pipelines`, then `done, every cached pipeline is ready`. A few seconds with a warm driver cache, a minute or two after a driver update or a rebuild. Off (`PORT_SHADER_PRELOAD=0`): nothing is built at start-up, in the background or replayed from the Fossilize database; each pipeline is built when the game first draws with it (can hitch briefly; log `[r2rsx] shader preload: off`). Pipeline creation is SEH-guarded everywhere (boot and background preload, Fossilize replay, render and compiler threads; `PORT_PRELOAD_SEH=0` disables): a driver fault skips that pipeline and its draw, stops the preload and replay, and the preload pipeline is quarantined. On AMD GPUs pipelines are created one at a time (`PORT_PIPE_SERIAL`, default 1 on AMD, 0 elsewhere). The launcher's **Compile shaders before playing** sets `PORT_SHADER_PRELOAD` (the same switch in all three Resistance ports, default on; `off`/`0`/`false`/`no` turns it off). Every start logs `[shaders] loaded N cached pipelines in X ms (...)` once the cached pipelines are built (with the option off, `0 ... (preload off, on demand)`). `PORT_SHADER_PRELOAD_BUDGET=<seconds>` (old name `R2_PRELOAD_BOOT_BUDGET`, used when the new one is unset or not a number; default 0 = no limit, negative counts as 0) stops the preload after that long, as if skipped.
- **Shader compile threads** (`R2_PRELOAD_BOOT_THREADS`, default Auto = every logical core but one, 1 to 64): the threads that build the pipelines before the game starts.
- **Shader interpreter while compiling** (`R2_SHADER_INTERP=1`, default Off): RPCS3's "Async with Shader Interpreter": a shader that isn't compiled yet is drawn by the interpreter instead of being skipped (no briefly invisible geometry on a cache miss; slower frames while it is active). **Not used on AMD GPUs** (RPCS3 #20025 / #16587: the interpreter and its shader preload hang or crash AMD drivers): on a PCI vendor 0x1002 GPU this setting, `R2_SHADER_MODE=interp` and `R2_SHADER_MODE=interpreter` fall back to the asynchronous / synchronous recompiler, logged as `[r2rsx] shaders: AMD GPU ...: shader interpreter disabled`. `RSX_AMD_SHADER_INTERP=1` (old name `R2_AMD_SHADER_INTERP`) keeps the interpreter on AMD.
- **Rebuild shader cache** (button, asks first; refused while `Resistance2.exe` is running) deletes the compiled, driver-specific part and keeps the list of shaders and pipelines to build, so the next start with Compile shaders before playing on rebuilds all of them. Deleted, from `shadercache\` and from its backup in `%LOCALAPPDATA%\Resistance2Port\shadercache` (`run.bat` restores missing files from there):
  - `rpcs3\shaders_cache\vk_pipeline_cache.bin` (and `.bin.tmp`): the Vulkan driver's pipeline cache (driver blobs; saved with a size + checksum trailer, and a file that is damaged, too large or from another GPU is ignored at start-up: `[r2rsx] vk pipeline cache: ... is <why>, starting empty`)
  - `rpcs3\shaders_cache\r2_gpu_stamp.txt`: the GPU and driver that cache was built for
  - `rpcs3\shaders_cache\shaderscan.stamp`: makes the launcher run shaderscan again on the next Play (see below)
  - `rpcs3\shaders_cache\r2_pipelines.foz`, `r3_pipelines.foz`: Fossilize databases (`R2_FOSSILIZE`)
  - `vk_pipeline_cache.bin`: the native renderer's Vulkan pipeline cache

  Kept: `rpcs3\shaders_cache\pipelines\vulkan\...\*.bin` and `raw\*.vp` / `*.fp` (RPCS3's pipeline list and shader programs: what gets rebuilt) and the native renderer's `vk_pipeline_variants.bin`, `rsx_engine_programs.bin` and `pipelines_*.db` lists.
- **GPU or driver change:** `r2_gpu_stamp.txt` records vendor, device, driver version, pipeline cache UUID and GPU name when the driver cache is saved. When they differ at start-up the log says `[r2rsx] vk pipeline cache: GPU or driver changed since the cache was built (was: ..., now: ...)`, the old `vk_pipeline_cache.bin` is deleted and every pipeline is rebuilt from the kept list (before play with the option on).
- **Offline shader scan:** [shaderscan](https://github.com/miroslavdanutalexandru-alt/shaderscan) (GPL-2.0, its own repository) is downloaded by Setup / `build.bat` into `tools\shaderscan.exe`: `tools\get_shaderscan.ps1` fetches the release pinned in `tools\shaderscan.version` and checks its SHA-256 (offline: skipped; set `SHADERSCAN_EXE=<path>` to use your own build). It is not part of the port's source or Setup, and the launcher works without it. When `shaderscan.exe` is next to `Launcher.exe` (or in `tools\`), Play first runs `shaderscan --check --out shadercache\rpcs3\shaders_cache`; if that says the cache isn't seeded (first launch, a new shaderscan version, or after Rebuild shader cache), it runs `shaderscan --game <folder> --out ... --progress`, which extracts every RSX shader from your game files into the cache so Compile shaders before playing covers the whole game without a playthrough. The launcher shows a progress panel (Esc or **Skip for now** stops it; the game starts either way) and logs the tool's output to `logs\shaderscan.log`. It runs at most once per launcher session.
- **Pipeline seed:** `tools\pipeline_seed.bin` lists the shader pipelines the game only creates in play (shader hashes and render state, no shader code and no game data). Each start copies the missing ones into `shadercache\rpcs3\shaders_cache\pipelines`, so Compile shaders before playing also builds them and a first visit to an area no longer skips draws (purple / green patches) while they compile. Their shaders come from your own game files through shaderscan; without it they are skipped. `PORT_PIPELINE_SEED=0` turns it off. Release builds refresh it with `scripts\export_pipeline_seed.ps1 -Merge` after a playthrough.
- **Object motion vectors** (`RSX_DLSS_OBJMV`, default Off, Compatible renderer): DLSS/FSR get per-object motion for moving characters and objects (sharper, less ghosting on them) at some CPU cost; Off = camera motion only.
- **Camera motion before confirmation** (`RSX_AA_EXACT_UNPROVEN`, default 1; `0` = old): when the per-draw camera vote fails, DLSS/FSR camera motion comes from the game's own view-projection (shared by at least 40 % of the draws) even before the draws have confirmed it. Before, frames where the vote failed often got zero camera motion (ghosting, smearing, boiling). Log: `camera exact: ... (N where the vote failed, M unproven)`.
- **Camera motion check against depth** (`RSX_AA_MV_CONFIDENCE`, default on; `0` = off): a 64 x 36 grid of the frame's depth is reprojected with the chosen camera motion and compared with the previous frame's depth (read back 4 frames later, `RSX_AA_MV_CONFIDENCE_LAG`). When more than 35 % of the samples are off (`RSX_AA_MV_CONFIDENCE_BAD`) and no motion would fit clearly better, camera motion is zeroed (one history reset) until a check passes. Log: `camera MV confidence: N checks, M rejected ...`.
- **Fewer DLSS history resets** (`RSX_AA_CUT_PARALLAX_GAP`, `RSX_AA_MV_CONFIDENCE_GAP`, default 120 frames each; `0` = old): a parallax-only camera "cut" (distant points barely moved, nearer ones did) or a new camera-motion reject run resets the DLSS/FSR history only when the last reset of the same kind was at least that many frames earlier (held-back triggers do not extend the window, so even a continuous run resets once per gap). A held-back parallax cut keeps the voted camera motion only with a clear vote majority and a parallax not far beyond the distant motion; otherwise (the R2 intro triggers: weak vote, parallax 0.2-0.4 of the screen) it uses the last trusted motion while that is at most `RSX_AA_VOTE_HOLD` frames old, then none (the same age limit now applies to failed votes). Its frame is re-checked by the depth grid (`RSX_AA_MV_CONFIDENCE`) on the voted motion: only when at least 70% of the samples are off with the voted motion AND with no motion (a real cut) is the history reset a few frames later, at most once per gap / 4 frames (a cut inside that window is deferred to its end, not dropped); a wrong transform alone goes through the normal confidence reject. The 11-14 log showed a parallax "cut" every 1-8 frames in the intro and the jungle while walking (plus 16-31 confidence resets per 5 s): the history was thrown away every few frames (unstable frames, boiling foliage). Log: `camera cut: N parallax-only cuts ... kept the history (U untrusted ...); depth check: C real cuts reset, G deferred, X unchecked`, `... K reject runs without a reset`. Confidence rejects held back by the gap are deferred (reset as soon as the gap allows while the rejects go on), not dropped. `RSX_AA_CONF_CUT=1` (opt-in, default 0): every depth-check verdict is also tested for a real camera cut (at least 70% of the samples off with the applied motion and with no motion, the parallax test) and resets the history at once, gap or not; log: `... N cut resets (RSX_AA_CONF_CUT 1)`.
- **Smoke / dust / sparks under DLSS** (`PORT_DLSS_BIAS_MASK`, default 1; `0` = old): blended, non-depth-writing effect draws into the scene before the upscaler (about 25 per frame in R3 gameplay) are redrawn into a coverage target that goes into the DLSS bias-current-colour mask (`PORT_DLSS_BIAS_MASK_VALUE`, default 0.6). Before, DLSS accumulated animated sprites into a flat smear while the camera was still and the real smoke popped in when the camera moved. Log: `PORT_DLSS_BIAS_MASK: N effect draws redrawn, ... mask used in F frames`.
- **Light-volume stencil jitter** (`RSX_AA_OCC_JITTER_STENCIL`, default 1; `0` = old): the stencil-marking light volumes (no colour, depth test, stencil on) that test against a copy of the jittered scene depth get the copy's sub-pixel shift, like the occlusion probes (`RSX_AA_OCC_JITTER`). Before, on some jitter phases a volume face crossing a surface at a grazing angle marked a different band: a one-frame hatched light leak on a static sun patch every few frames. Log: `occlusion probes given their depth copy's jitter (RSX_AA_OCC_JITTER): N (S stencil-marking light volumes, ...)`.
- **Decal depth bias follow (`RSX_DECAL_ZBIAS_FOLLOW=0` to opt out).** A biased decal pre-pass whose EQUAL material redraw is never found stops being biased only after 3 misses on different frames (misses while the decal table overflowed, this frame or, for a redraw after the frame boundary, the previous one, are not counted). The mark expires after 600 frames, a matched redraw clears it, and the table is cleared after 60 frames without decals (loading screens), so reused addresses don't inherit it.
- **Decal pairing by content (`RSX_DECAL_ZBIAS_PAIR=1` to opt in; `=2` learns and logs only).** Off by default. Pairs a depth-writing quad of the scene pre-pass with the depth EQUAL quad that redraws it in the material pass by the bytes of its positions and the transform constants both vertex programs read, instead of the buffer address (R3 moves the vertex buffers between the passes). After 8 frames in a row where every pre-pass draw of that content got exactly one paired redraw, both draws get the same `RSX_DECAL_ZBIAS` depth bias (the R3 poster edge). A biased draw whose redraw does not come blocks its content for 600 frames. The log line "decal pairing" counts paired / unpaired redraws, learned keys and biased draws.
- **Decal depth bias EQUAL guard (`RSX_DECAL_ZBIAS_EQGUARD=0` to opt out).** The decal pre-pass bias is applied only in forward-rendered scenes: no depth-EQUAL no-write draw of any size in the last 120 display frames (the 120 frames restart on every frame of boot and of any loading screen, however long). The material pass batches the redraws of pre-pass quads (12 to 3000+ indices), so they can't be matched to a biased quad; their EQUAL test then fails and the pre-pass normals show as neon-green floor, foliage and poster patches. The 5 s `decal bias:` line counts the pre-pass draws held unbiased and the EQUAL draws seen.
- **Deformed-mesh motion** (`RSX_DLSS_OBJMV_DEFORM_CARRY`, default 1; `0` = old; `RSX_DLSS_OBJMV_DEFORM_MB` 32 / `_MAX` 192, were 16 / 96): CPU/SPU-rewritten meshes updated every other frame are copied on the unchanged frame too, so the next change has a previous copy (before: ~93 % of the captured deformed draws fell back to camera motion). Log: `objmv2 detail: ... deform carried N, fallback: no previous copy A, layout B, history C; not copied D`.
- **Deformed-mesh motion, every gap** (`RSX_DLSS_OBJMV_DEFORM_CARRY` is now a frame count, default 12, `0` = off, `1` = the old one-frame carry; `RSX_DLSS_OBJMV_DEFORM_MB` 48 / `_MAX` 384, clamp 1024): a deformed mesh that last changed up to N frames ago is still copied each frame, so animations that update every 2-12 frames keep a previous copy ("no previous copy" fallbacks were ~20 draws/frame at the diner).
- **Camera vote by object** (`RSX_AA_VOTE_OBJECT`, default 1; `0` = old far-plane screen metric): two draws agree when their object origin and unit axes land within the vote tolerance, as om_pick_nearest tests. The far-plane test amplified float noise, so only ~7-11 of ~1300 diner draws agreed and every frame fell back to an unconfirmed camera exact. Log: `camera vote: ... agreeing`.
- **Separate budget for draws without depth writes** (`RSX_AA_EVALS_NOWRITE`, default 384; `-1` = old shared `RSX_AA_EVALS` cap): transparents and particles can no longer use up the 2048 capture budget before the opaque draws are captured.
- **Unchanged-constants static path** (`RSX_DLSS_OBJMV_FAST_STATIC`, default 1; `0` = off): a rigid draw whose constants differ from its previous-frame pair (or another occurrence of the same draw) only in the shared camera rows is static without running the vertex-program interpreter twice. The result is the same; it costs less CPU. Log: `objmv pairing: ... N by unchanged constants`. The loose key (`RSX_AA_MATCH_LOOSE`) is no longer hashed for skinned programs, which never read it.
- **Review fixes (round 2)**: the unchanged-constants static path now also requires this draw's camera rows to equal this frame's camera (the rows `om_exact_ref` last proved separate from the whole transform), so an object that sat at identity last frame and moves now is no longer called static. 1 in 16 fast hits still takes the full path (log `+ N sampled full checks`). The draw keys and their per-frame ordinals (strict and loose) are now made for every scene draw before the `RSX_AA_EVALS` / `RSX_AA_EVALS_NOWRITE` budget test. The budget only gates capture, so the draws it cuts no longer shift the pairing of later draws with the same key.
- **Deferred classification, A/B** (`RSX_AA_OBJMV_DEFER`, default 0; `1` = worker thread; `2` = render thread at the flip): a matched rigid draw that was static last frame (paired, no own motion, no skin or deform history) is predicted static at draw time and classified after the scene. If the prediction misses (the object started moving), that frame gets camera motion and the object's history capture starts on the next frame. These misses are counted as `late-start`. `RSX_AA_OBJMV_DEFER_HOLD=8` (**default**; `0` = old): a draw that moved in any of the last 8 frames is not predicted static, so objects the game moves on alternate frames (doors, props and foliage animated at 30 Hz) no longer get camera motion only on every moving frame (30-40 late starts per frame in R2 logs); the `objmv defer` line counts them (`not predicted: moved in the last N frames`). `RSX_AA_OBJMV_DEFER_HOLD_HIST=1` (**default**; `0` = off): such a held draw also keeps its GPU motion history while it is static, so its next move has its own velocity; without it the move found no history (`no-history`, camera motion only, the same door ghost). Held copies stop once three quarters of the history slots are taken (moving draws keep priority); the `objmv defer` line counts them and splits `no-history` by reason. Log: `objmv defer (RSX_AA_OBJMV_DEFER=N): ... late-start N ...; fast exit (RSX_AA_FAST_EXIT) N of M draws`. Compare it with the `objmv cpu` line.

- **Velocity for conditionally rendered objects** (`RSX_DLSS_OBJMV_COND=0|1`, **default `1`**; `0` = old behaviour; onepass mode only): moving draws the game issues under a conditional render (occlusion-tested objects such as doors and props) now bind their velocity variant like any other draw. They were skipped and got camera motion only, so frame generation ghosted them (Iceland door run: about 51 such moving draws per frame, the largest camera-only group left). The `objmv2 fallbacks` line shows `conditional-render draws given velocity N (RSX_DLSS_OBJMV_COND=1)`; `conditional render` under "skipped" should drop to 0. `RSX_DLSS_OBJMV_DEFORM_WARM=0|1` (default `0`): also keeps a copy of the vertex data of foliage-like draws that have not changed for a while (or never), when their vertex program is known to deform, so their next change gets real per-vertex motion instead of camera motion; uses at most three quarters of the history slots and of the deform draw budget (`warm deform copies N` in the same line). `RSX_DLSS_OBJMV_SLOTS` now accepts up to `4096`.
- **Non-scene fast exit** (`RSX_AA_FAST_EXIT`, default: on with `RSX_AA_OBJMV_DEFER`; `1` / `0` = force): a draw outside the scene surfaces whose targets and depth/stencil/colour state match the previous draw that needed nothing returns from the DLSS draw hook first, without other work. Any state change (surface bind, section, readback, depth clear, flip) invalidates the cache.
- **Draw-hook profile** (with `R2_RSX_PROF=1`): every stats window logs `r2aa_on_draw split (R2_RSX_PROF): N draws/frame (S scene, F fast exit); us/frame: head, scene keys, capture, classify, tail, fast exit; ns/draw`. AA runs fired inside the hook are excluded. The jitter bookkeeping per jittered draw (`jd_depth` / `jd_shift`) and the depth-latch lookup (`RSX_AA_DS_LATCH`) now reuse the previous draw's entry when the target is the same, instead of hashing again; the results are unchanged.
- **Alpha-to-coverage** (`RSX_AA_A2C`, default `stable` as in R3; `noise` = old; `hashed` = opt-in): RPCS3's emulated A2C uses a fixed 0.5 threshold instead of per-pixel noise that boils under the jitter. R2's shader caches showed no A2C draws, so it normally changes nothing (`RSX_AA_A2C=stable: alpha-to-coverage program #N ...` is logged when one appears). `RSX_AA_A2C=hashed` (with FSR/DLSS on; aliases `hash`, `2`) replaces the hard 0.5 cutoff with Wyman & McGuire's hashed alpha test: the threshold is a hash of the object-space vertex position in cells about one render pixel wide, so the pattern sticks to the surface (no swimming like a screen-space dither, no frame-index term that DLSS would treat as noise); the upscaler's sub-pixel jitter lands on neighbouring cells, and DLSS/FSR accumulate a soft edge instead of a stair-stepped one. Alpha 1 always passes, 0 always fails, and the alpha test still runs first. A vertex program that does not read attribute 0 gets the plain 0.5 cutoff (no stale vertex-layout read). Trade-off: thin distant foliage can shimmer slightly where `stable` is a clean (aliased) cutoff, so `stable` stays the default. Logged as `[r2rsx] RSX_AA_A2C=hashed: alpha-to-coverage program #N ...`. `RSX_AA_A2C_MIPSCALE=<k>` (default 0 = off; try 0.25) additionally scales the alpha of 2D texture samples in A2C shaders by `1 + mip * k`, so minified foliage keeps its coverage instead of thinning out at a distance (it scales every 2D sample of those shaders, hence opt-in). Unit test: `test_r2_a2c_hashed`.
- **Distant cut-out foliage** (`RSX_AA_ATEST_MIPSCALE`, default `0.15` with FSR/DLSS on; `0`/`off` = old; `0.25` = stronger): R2's foliage is alpha-tested (GEQUAL), and box-filtered alpha mips average thin leaves below the cutoff, so distant vegetation thinned out and its surviving texels boiled under the jitter. GEQUAL/GREATER tests on minified texels now compare `alpha * (1 + mip * k)` (Castaño's coverage-preserving mip alpha), only for cutoffs above 0.3. Only the mip level of the one texture whose alpha reaches the output (found by data-flow in the shader decompiler) counts; programs whose alpha comes from several textures or none are left alone (logged as `skipped`). Only jittered main-scene draws (depth pre-pass and material pass alike) use it, so shadow maps keep the plain test. Mip 0 / near foliage, the written colour and other test functions are unchanged. Logs `RSX_AA_ATEST_MIPSCALE=0.15: alpha-tested program #N ... of texK`.
- **Render-target CPU authority** (`RSX_RT_CPU_AUTH`, default on as in Resistance 3; `0` = RPCS3 behaviour): once a colour surface has been read back to guest memory and not drawn to since, a sample that reinterprets it in another format is decoded from guest memory, so CPU/SPU writes after the readback are seen. RPCS3's 3-sample memory tag misses SPU writes that leave those samples unchanged (Resistance 3's aim-down-sights blur showed a checkerboard). Logged as `[r2rsx] RSX_RT_CPU_AUTH #N: ... decoded from guest memory` (rate-limited). Unit test: `test_rt_cpu_auth`.
- **Tiled texture reads from guest memory** (`RSX_DETILE_GUEST_SRC`, default on, shared with Resistance 3; `0` = RPCS3 behaviour): textures and render targets loaded from main memory (tiled or not) read a copy of guest memory taken when the work is recorded, not the renderer's shared DMA mirror, and the upload heap holding those copies is kept until the frame using it has finished on the GPU. Render-target readbacks still in flight (aim-blur early readbacks, fault copies) rewrite that mirror on the GPU afterwards, which in Resistance 3 showed the old light buffer as purple/black bands over the aim blur.
- **Protect before the guest-memory copy** (`RSX_GUEST_SRC_MMFLUSH`, default on; `0` = off): before that copy is taken, the page protection the texture cache queued for the texture is applied, so a game/SPU write landing between the copy and the GPU submit faults and re-uploads the texture instead of leaving a half-written copy cached. This also covers the CPU decode path (all guest-memory sources of an upload are flushed once before they are read). It is race hardening, not the splash fix below.
- **Linear textures decode on the CPU** (`RSX_TEXDECODE_LINEAR_CPU`, default on; `0` = GPU decode for linear textures too): linear (non-swizzled) uploads from guest memory byteswap on the CPU instead of the zero-copy scratch buffer + compute shader; swizzled uploads keep the GPU deswizzle. With the GPU path the Resistance 2 boot splash (1280x720 linear D8R8G8B8) intermittently lost its text and only the loading icon showed; `RSX_GPU_TEXDECODE=0` alone fixed it.
- **Texture-upload split and optional CPU work on worker threads** (`RSX_TEX_PAR_CONV`, experimental, default off; `1` = on; `RSX_TEX_PAR_THREADS`, `RSX_TEX_PAR_MIN_KB`, `RSX_TEX_PAR_SPIN_US`): with `RSX_TEX_PAR_CONV=1`, for an upload with at least 256 KB of guest data, the CPU conversions of its mip levels / faces / slices and the guest-memory snapshots of its zero-copy levels (split into 256 KB pieces) run on a small thread pool. The RSX thread still reserves every upload-heap slice in the original order and joins the pool before it records the upload's copy commands (or before a heap grow would unmap the slices), so the bytes, heap offsets, command stream and the point where guest memory is read are unchanged. Only sources that cannot fault (the unprotected guest mapping or host memory) go to the workers. The `[spike]` frames in `logs\run.log` get a `[spike] tex-upload X ms/N (conv / heap-wait / mm-protect / cs-compile / rec)` line with the split of that frame's uploads, the MB uploaded, heap grows and the longest one, and every 5 s a `[spike] tex-upload 5 s:` summary (with the hitch logger, `PORT_HITCH_LOG=1`). Off by default because the conversions are memory-bandwidth bound: a standalone benchmark of the pool gained 0-15% and lost on 4 MB copies; the split shows whether in-game uploads are dominated by conversion, page protection (`mm-protect`), first-use compute-shader compiles (`cs-compile`) or command recording.
- **Failed pipelines** (log only): a pipeline whose link failed (a driver fault caught by the compiler) keeps its placeholder, so its draws are skipped for the rest of the session and it is never relinked; this is now logged once per pipeline in the RPCS3 log (`rsx_log` error `Pipeline link failed (vp id = N, fp id = M): its draws are skipped for this session`, written by the compiler thread with the real result; a pipeline that is merely queued for an async compile is not reported). Draws are only skipped *temporarily* while a new pipeline compiles asynchronously (until that compile finishes).
- **Graphics feature trace** (`RSX_FEATCOV`, default off since it costs about 2.5 ns per RSX method write; `1` = on; shared with R1 / R3): every RSX method, render state value and shader op the game uses is listed once in `run.log` as `[featcov]` lines, each marked with what the renderer does with it (real / noop / ignored / unhandled). Dumps every `RSX_FEATCOV_SEC` seconds (default 60; only newly seen items; `0` = only at exit) and at exit. Summarise with `python scripts\featcov_report.py run.log`.
- **Camera vote from static draws** (`RSX_AA_VOTE_STATIC_ONLY`, default on; `0` = off): skinned / animated programs (indexed constants or more than `RSX_AA_VOTE_STATIC_CONSTS`=24 constants beyond the MVP) stay out of the camera vote and no longer use up the draw cap. Log: `camera vote static-only: ...`.

## Performance work

### CPU switches and builds

The frame rate in heavy scenes is set by two threads: the game's main PPU thread and **rawSPU0**, the SPU job kernel (the main thread waits on its jobs). Env switches (unset = default):

- `PORT_SPU0_CPU=<n>` — with ≥ 12 logical CPUs rawSPU0 gets logical CPU 6 and an empty SMT sibling, like the main thread (`PORT_MAIN_CPU`, default 2) and the RSX thread (`PORT_FIFO_CPU`, default 4). `-1` turns this off. In the Compatible (RPCS3) renderer the RSX core is the thread named `rsx::thread`, which now gets the `PORT_FIFO_CPU` core (it was left with the other threads before and that core sat idle). Everything else shares the remaining cores. The log prints `[affinity] ... pinned` lines. `PORT_MAIN_CORE=0` turns off all of this pinning.
- `PORT_CPU_PCORES=off` (launcher: Advanced > CPU threads > Prefer P-cores): on Intel hybrid CPUs (P + E cores, 12th gen and newer) the main guest thread, raw SPUs, SPURS lanes, the RSX FIFO / render / engine threads (`rsx::thread`, FIFO walker) and the audio mixer get P-core thread CPU sets (`SetThreadSelectedCpuSets`; a thread runs only where its sets and its affinity overlap) and EcoQoS off, as many of them as the usable P-cores allow (about two hot threads per P-core: main and FIFO from 2, render / engine, raw SPU 0, lanes 0-2 and the mixer from 4, raw SPUs 1-3 from 6, lanes 3 and up from 8; fewer than 2 = nothing). Usable = P-cores inside the process affinity, or, while the core keeper hard-pins main / FIFO / raw SPU 0 (12+ logical CPUs), inside the mask it leaves for the other threads; the threads it pins get no CPU sets. Other threads are left to Windows (Resistance 2 / 3 with 4+ usable P-cores: the process default CPU sets are the P-cores too). CPUs whose cores all share one efficiency class (AMD, multi-CCD included, older Intel) are not changed. Default on; `off`/`0`/`false`/`no` turns it off; `PORT_PCORE_HOT=0` is the older name. `PORT_THREAD_PLACEMENT=off` also turns it off. Log: `[cpu] hybrid CPU ...` or `[cpu] P-core placement off (<why>; ...)`, and `pcore-pin` in the `[native]` line.
- `PORT_LARGE_PAGES` (default off): **not available in this port.** Resistance 1 can put guest memory in large pages; here the Compatible renderer's texture cache write-protects guest memory in 4 KB pages to notice CPU writes to textures, which a large page cannot do, and the guest space is one pagefile section mapped twice. Setting it only makes the `[native]` line say `large-pages(PORT_LARGE_PAGES,overridden: texture cache needs 4 KB page protection)`. (For Resistance 1: Large pages (2 MB instead of 4 KB) cut TLB misses on the game's scattered memory accesses; the gain is small (a few % at most, CPU-bound scenes only). Windows gives them only to an account with the **Lock pages in memory** right: run `secpol.msc` (Windows Pro / Enterprise; on Home use `ntrights -u %USERNAME% +r SeLockMemoryPrivilege` from the Windows Server 2003 Resource Kit, or a policy editor), Local Policies > User Rights Assignment > **Lock pages in memory** > Add User or Group > your account, then sign out and back in (no administrator rights needed afterwards). Without the right, or when Windows cannot find enough contiguous free memory (more likely the longer the PC has been up), normal pages are used and the `[native]` line says why: `large-pages(PORT_LARGE_PAGES,overridden: no privilege)` (or `not enough contiguous memory`, `not supported`).)
- `PORT_THREAD_PRIORITY=on` (launcher: Advanced > CPU threads > Raise game thread priority): the main and RSX threads run at above-normal priority (only raised, never lowered; any CPU). Default off: on CPUs with 4 cores or fewer a raised spinning thread can starve the others. Each changed thread is logged as `[cpu] <thread> (thread N): ...`.
- `PORT_KEEPER_MS=<ms>` — the two thread-placement keepers rescan the process threads every 1–2 s while new threads appear, then every 5000 ms (each scan walks every thread on the system; at 1 Hz they cost 4–7 % CPU each).
- `PORT_PIN_TOPO=0` — the default pin CPUs above (main, RSX, rawSPU0) are now taken from the detected CPU topology: the first logical CPU of physical cores 1, 2 and 3 (P-cores first on hybrid CPUs). On a 6-core/12-thread CPU that is still 2, 4 and 6; on CPUs without SMT it is 1, 2 and 3 instead of two hot threads sharing a core. `=0` uses the old fixed 2 / 4 / 6. The `[affinity] main thread ...` line shows the CPUs and the switch values.
- `PORT_REST_SMT=<spu0|0|1|2>` — where all other threads (SPURS lanes, rawSPU1, RSX workers, driver, audio) may run. `spu0` (default): the cores that have no pinned hot thread plus the SMT sibling of the rawSPU0 core (on 6C/12T mask `0xF83`). rawSPU0 spends ~90 % of its core polling, so a SPURS lane on its sibling runs only ~1.18x slower, against ~1.7x when two lanes share a core (offline replay of the heaviest job, Ryzen 5600X). `0`: only the cores without a pinned hot thread (the old default, mask `0xF03`). `1`: also the sibling of the RSX core. `2`: also the main thread's sibling. It costs the hot threads some SMT throughput.
- `SPU_FAST_LLPOLL=<n>` — an SPU that re-reads an unchanged lock line (GETLLAR) more than `SPU_FAST_LLPOLL_AFTER` times in a row (default 64) is polling, so each further re-read first executes `<n>` CPU pause instructions (default 8, about 0.1 µs). A tight poll slows the thread on the other half of the same core by ~1.6x; with the pauses that drops to ~1.18x. rawSPU0 and rawSPU1 poll like this all the time. The poll still sees a write on its next read. `=0` turns this off. Logged once as `[spu-llpoll]`.
- `PS3_USLEEP_NOTIFY_PUT=0` — a short guest `usleep` poll (under 1 ms) already ends early when an SPU atomic writes guest memory (`PS3_USLEEP_NOTIFY`). It now also ends early on a plain SPU DMA PUT, so the main thread's SPU-job wait (`guestwait` at `0x006B8D3C`) re-checks as soon as a job writes its result instead of finishing its 128 µs sleep. It costs nothing while no thread is waiting. `=0` turns this off. Logged once as `[usleep] PS3_USLEEP_NOTIFY=1 PS3_USLEEP_NOTIFY_PUT=1 ...`.
- `SPU_INLINE_CH=0` — the lifted SPU code writes the MFC DMA parameter channels (LSA, EAH, EAL, size, tag, tag mask) and reads the status channels directly instead of calling the channel runtime (thousands of call sites, each of which also reloaded every live register). The command and blocking channels still go through the runtime. `=0` restores the calls. Build option `-DPORT_SPU_INLINE_CH=OFF`.
- `PORT_SPU_SPINWAIT=old|backoff|wait` — how a raw SPU spins in a blocking channel wait (mailbox, signal, event / lost-reservation) before it sleeps on the wake-up. Default: `wait` (picked by `PORT_NOSPIN`, on by default, with a pause-only spin); `old` (the default with `PORT_NOSPIN=0`): the original tight spin. `backoff` (experimental, no measured gain): `_mm_pause` bursts that grow 4 → 128 per poll, then `SwitchToThread` on each poll after 20 µs, so the core is shared with the main thread and the other SPUs instead of burned. `wait`: the same but goes to sleep after `PORT_SPU_SPINWAIT_US` (default 20) instead of the full `SPU_WAIT_SPIN_US`. Producers already wake the waiter. Logged every 10 s as `[spuwait] mode=... waits= done-in-spin= slept= polls= yields= wakes=`. A/B: run the same big fight with the variable unset, `=wait` and `=backoff` and compare fps / the `[spuwait]` line. In the offline contention benchmark (`scratch\spinwait_bench`), `wait` was within ~10% of `old`, while `backoff` was 25–35% slower and collapsed when every core was busy (its `SwitchToThread` hands the core to another ready thread for a whole time slice). So try `wait` first.
- `PORT_NOSPIN=1|auto|0` — the no-spin wait profile. Default `1` (on for every CPU); `auto` = on only below 12 logical CPUs; `0` (or `off`) = the old spinning waits. It sets the default of: `SPURS_TARGETED_WAKE` (SPURS wakes only the SPU that has work), `PS3_USLEEP_PARK` (short `sys_timer_usleep` waits park instead of spinning), `PORT_SPU_SPINWAIT` (`wait` instead of `old`, pause-only spin) and `R2_JOBWAIT_WAKE` (job waits are woken instead of polled). Setting any of these explicitly overrides `PORT_NOSPIN` for that one. Logged as `[nospin] on|off`.
- **`PORT_SPU_SPIN_ADAPT=<percent>`** — adaptive SPU wait spin (adapted from the inFAMOUS 2 PC port, MIT). Each SPU thread tracks how often its pre-sleep spin ends with the channel ready, and skips the spin while that share is below `<percent>`. Every 8th skipped wait spins anyway to measure again. This stops an idle SPU (menus, pause, a sleeping sound engine) from spending its spin window on every wait, which matters most on 4-core CPUs. Default `25`; `0` = spin on every wait as before. Logged as `[spuwait] adaptive spin`.
- **`PORT_CORE_SCARCE=0|1`, `PORT_CORE_SCARCE_BELOW=<n>`** — "few cores" detection: physical cores (SMT siblings counted once) in the process affinity mask, below `<n>` (default `6`) = scarce. Logged as `[cores]`. `0`/`1` forces it. Shared with Resistance: Fall of Man, where it picks the event-woken RSX frame clock; here it is only reported.
- `PORT_SPU_SCHED=0`: an SPU job that waits for another job or the PPU to change a shared memory line (lock-line reservation wait: SPURS job queues and locks) is woken by every write that goes through the runtime's coherence path. A write that bypasses it was only noticed on the next 10 ms poll; such waits now re-check the line every `PORT_SPU_SCHED_MS` (default 1, 1–10), so a missed wake costs at most about 1 ms. Waits only end when their condition holds, as before; other channel waits are unchanged. Logged once as `[spu-sched] PORT_SPU_SCHED=1 ...`, and every 10 s as `[spu-sched] 10s: lost-reservation sleeps=... missed wakes=...` (missed wakes = sleeps that timed out with the line already changed). `=0` restores the 10 ms poll. With `PORT_SPU_SCHED_STATS=1` (diagnostic, default off; it also turns on the `[spuwait]` 10 s line) the 10 s line also gives the total and average time asleep, how many sleeps ended on the timeout instead of a writer's wake, the sleeps and time per SPU image, and the line of the last missed wake (to find the writer that bypasses the coherence path). Shown as `spu-sched(PORT_SPU_SCHED)` in the `[native]` line. Offline test: `ps3recomp\runtime\spu\tests\test_spu_sched_wake.c`.
- `PORT_NOTIFY_ALL_WRITES=1` (experimental, **default off** since 2026-11-17): the RSX's own writes into game memory (semaphore labels, report and zcull results, blits and inline images, surface flushes back to game memory, the async aim-blur readback serve) also wake an SPU job waiting on a memory line they touch, instead of the job finding out on its next re-poll. The check is a bitmap scan of the written range, so writes to lines no SPU job ever waited on cost almost nothing. It was on by default for one test round, which brought back one-frame black screens while firing in aim-down-sights in Resistance 3, so it is off in both ports until an A/B clears it; without it, such a job notices the write on its next `PORT_SPU_SCHED_MS` re-poll. With it on, the `[spu-sched]` line counts these wakes as `range-notify wakes`.
- `RSX_FIFO_RETURN_CAPTURE` (aliases `R3_FIFO_RETURN_CAPTURE`, `R2_FIFO_RETURN_CAPTURE`; default on, `0` = off): fixes FIFO desyncs (`[fifo] desync #N`, lost or corrupted frames) when the RSX thread is CPU-bound, for example R3 at the diner at 30-38 fps. The game links a short command segment into the ring and ends it with a JUMP back to where it came from. It waits until GET == PUT at the segment end, moves PUT, and soon reuses the segment memory. A late RSX thread then runs data as commands. The puller now remembers that return JUMP while it waits at PUT and runs it if the word was reused before it saw PUT move. It only overrides a word reused as data or a method header. If the game rewrote the segment end with its own JUMP, CALL or RET, that live word runs. It also requires PUT to be near the ring the JUMP returns to. A loop detector turns the capture off for the session if, after a substitution, the RSX jumps to the same place again before it reaches PUT while PUT stands still. It then resumes at the segment end if the game has re-linked it there with its own JUMP or CALL, so the live word runs and nothing is skipped. Otherwise it resumes at PUT and skips the commands up to PUT. It also clears the restore point and CALL return left in the old lap, and logs `[fifo] return-capture loop: ...`. The detector uses progress, not time, so long semaphore waits never trigger it. GET publication is unchanged. `[fifo] return-capture #N` lines count the saves. Desyncs also print `[fifo-diag]` lines in both games (`R3_FIFO_DIAG=0` = off).
- `R2_OCC_BLOCKING=1` (default) — occlusion-query results: the game's own (0.2.3) blocking wait, shortened by `R2_OCC_NOWAIT` (default `1`, see *No frame stall on late occlusion results*; `R2_OCC_NOWAIT=0` = the plain wait). `R2_OCC_BLOCKING=0` enables the non-blocking skip described next (faster in big fights, but with the default relaxed ZCULL it made objects pop on and off; see `scratch\cpu_occ.md`). `R2_OCC_SKIP` and `R2_OCC_WAIT_US` only apply with `R2_OCC_BLOCKING=0`. `R2_OCC_SKIP=1` (default under `R2_OCC_BLOCKING=0`) — Each frame the game waits for the GPU to finish last frame's occlusion queries before it continues, so the CPU and the renderer take turns instead of working in parallel. With `=1`, when a result is not ready yet, that set is drawn all visible once (never hidden, so no pop-out; a little extra drawing), and the game waits normally on the next frame (heavy fight: 35.7 → 45.5 fps). `=0` waits every frame. `R2_OCC_BLOCKING=2` blocks with the native capped wait. `R2_OCC_SYNC_SITES=0x0026C1E0` keeps the wait for the game's one global query set (a candidate for flares/glows; try it if a flare or glow shows through a wall). `R2_OCC_WAIT_US=<n>` caps the wait at n µs (default `50000`; `-1` = the game's own 1 s wait). A set that times out is also drawn all visible (`R2_OCC_TIMEOUT_VISIBLE=0` keeps last frame's flags instead, the old behaviour). After a skip or timeout the object stays all-visible (even when a result "arrives": it may be a late write from before) until the renderer has executed `R2_OCC_FENCE_FLIPS` (default `3`) more flips and a wait completes normally again. Logged every 10 s as `[occ] report sets ... ready / skipped / waited`, with skip/wait per caller.
- `R2_PIC_SWITCH` (code generation, default on; `R2_PIC_SWITCH=0` when running `tools/r2_regen.py` generates the game code as before) ? the position-independent SPU job modules that jobs load at run time (`wwspic_*`) are also translated at the `case` labels of their `switch` jump tables (a `bi` through a table of offsets, found from the `clgti` bound and `lqx` table load before it). Without them a jump into such a table found no translated code and the rest of the job ran in the SPU interpreter: in Bryce Canyon's *Control Room* the Swarm's job (`img 217`, modules `DFF680` / `E00F00`) took 66 ms per run instead of well under 1 ms and the game dropped to ~5 fps (#15). Takes effect when the game code is regenerated.
- `SPU_LIFT_CODE_PTRS` (code generation, default on; `SPU_LIFT_CODE_PTRS=0` when running `tools/r2_regen.py` generates the game code as before) - SPU job code that is only reached through an address stored as data (a C++ static-constructor list, a function-pointer table) or built in a register and called indirectly is also translated (`tools/spu_code_ptrs.py`). Without it such a call found no translated code and ran in the SPU interpreter: the mesh job (`img 222`) ran its empty static constructor at LS `0x49D8` interpreted on every run, 33-143 ms each (`[spu] img=222 ... unlifted job code at LS 0x049D8` / `[spu-jobs] ... INTERPRETED` in `logs\run.log`). The regen lists what it added in `build_regen\spu\jobmods_code_ptrs.txt`. Takes effect when the game code is regenerated.
- `R2_NATIVE_JOBS` (default on; `R2_NATIVE_JOBS=0` runs only the translated SPU code, as before) — native, bit-exact replacements for three hot SPU job routines: the dd413 geometry job's packed-vertex transform + clip-code loop (`0x4030`, AVX2, 2.1-2.4x faster per call) and its triangle cull + index compaction (`0x42E0`, AVX2, 2.6-3.3x per call; the CPU reads its output), and the Edge zlib decoder's inner loop (`spuelf0 0x8240`, asset decompression, 1.85x per whole decode call, 3.8-4x for the inner loop). A call whose inputs are outside the verified cases (bad count, LS overrun, overlapping in/out buffers, a pending SPU interrupt) runs the translated code. Each kernel checks itself: its first 8 calls, then 1 in `R2_NATIVE_JOBS_CHECK` (default 4096; 0 = never), run both versions and compare the whole SPU local store and the kept registers; on a difference the translated result is kept (the game never sees the native one) and both versions are run once more on copies of the same input: only a difference that repeats turns that kernel off for the run (`[native-jobs] ... kernel DISABLED`, with the input registers); one that does not repeat (memory changed under the check, e.g. another SPU or the PPU writing this local store) leaves the kernel on and is counted as `races=` in the `R2_NATIVE_JOBS_STATS` lines. One `[native-jobs] <name> ... native ON` line per kernel when it first runs. `R2_NATIVE_JOBS_MASK` picks kernels (bit 0 = dd413 transform, bit 1 = Edge zlib, bits 2-4 = water kernels below, bit 5 = dd413 cull, bit 6 = the 029d job's memcpy at `0x1DF90`; default `0x7F`); `R2_NATIVE_JOBS_VERIFY=1` checks every call; `R2_NATIVE_JOBS_STATS=1` prints counts. On/off switches take `1/on/true/yes` and `0/off/false/no` (any case), the same rules as the `[native]` line in all three ports. `PORT_NATIVE_EDGE_ZLIB=0` still turns the zlib kernel off (`=1` turns it on even if the mask leaves it out). Offline: 60000 fuzz cases for the transform, 40000 for the cull (`test_cull.exe`) and 25000 fuzz states + 436k real chunk calls for zlib, 0 mismatches (`scratch\native_jobs`, `scratch\edge_zlib_native`). Report: `native_hot_r2.md`.
- `R2_NATIVE_JOBS_WATER` (default on since 2026-11-13, like the dd413 kernel; `R2_NATIVE_JOBS_WATER=0` turns these three off, `=1` turns them on even if the mask leaves them out) — three more native kernels under `R2_NATIVE_JOBS`, for the water/ocean SPURS jobs (SPURS lane 2: about 19 % of that lane's time): `7db0 0x9440` height field → 2-channel signed-8-bit gradient (normal) map (2.4x faster per call), `7db0 0xAC48` 2x upsample of the coarse water grid blended with two ring buffers (2.2x), and `4154 0x81C0` ocean-spectrum phasor rotation, the input of the job's FFT (17x). Mask bits 2-4 of `R2_NATIVE_JOBS_MASK`; AVX2 builds only (like the dd413 kernel). Same decline rules and self-check as above; a self-check difference is now run again on both sides (the translated re-run uses a copy of the SPU context, so the live local store is never redirected), and only a difference that repeats turns the kernel off (one caused by memory changing during the check is counted as `races=`). Offline: 100000 fuzz cases per kernel (random, extreme, denormal, NaN and huge floats, random shuffle tables, strides, aliasing), 0 mismatches, every injected 1-bit output fault caught (`scratch\native_jobs\test_water_jobs.exe`). No real job inputs have been captured yet, so the run-time self-check is the safety net for real data. Estimated saving: about 13 % of SPURS lane 2 (≈ 130 ms per second of lane time); it only shortens the main thread's `0x006B8D3C` wait when that wait is for these jobs. `R2_NATIVE_JOBS_PROF=1` measures exactly that: every ~3 s a `[native-jobs] prof <name> lifted N x us | native N x us | ... ms/s while main waits` line per hooked routine, also for the dd413 cull loop `0x42E0` (kernel bit 5, see above).
- `RSX_FIFO_GET_DEDUP` (default on; `0` = always store): the FIFO puller skips publishing GET when the guest-visible GET already holds that value (run_FIFO publishes after every packet, ~60k times a frame, mostly the same cache end while the puller lags PUT). Guest memory stays identical; it saves the redundant stores to the control line the guest polls. `[fifo-get]` (with `[fifo-merge]`, every 5 s) prints stores/f vs identical skipped/f.
- `RSX_FIFO_NOP_LAZY_TS` (default on; `0` = upstream): a FIFO NOP no longer reads the clock (QPC) twice to time a zero-length idle; the idle start is taken only when the FIFO really goes empty/spins or a reader needs it. `[fifo] RSX_FIFO_NOP_LAZY_TS=1: N NOP idle entries/s ...` every 5 s.
- `RSX_FIFO_INLINE` (alias `R2_FIFO_INLINE`, default on; `0` = off) — RSX thread FIFO decode fast path: command headers and arguments that are already in the FIFO cache are read inline, and the method register is stored inline instead of through an out-of-line call. It runs the same code as the normal path, so the results are identical. A replica benchmark (`R3 scratch\rsx_thread\fifo_bench.cpp`) shows 10.9 → 6.8 ns per method, about 0.5 ms per frame at the ~129k methods of an R2 heavy scene. It was opt-in after the 2026-11-11 freeze report but was never the cause; the R3 FIFO desyncs were later traced to the upstream GET-before-execute bug (RPCS3 #20055). It is listed in the `[native]` line as `rsx-fifo-inline`.
- `RSX_IBIND_SKIP` (default on; `0` = off) and `RSX_VPRUN_FAST` (default on; `0` = off; both were checked against the R2 hang of 2026-11-13 and are not on its path: the index-bind skip is reset every render pass and command buffer, and the interpreter records no GPU commands) — two more exact RSX-thread fast paths, output identical. `RSX_IBIND_SKIP` binds the renderer's index ring once per command buffer and render pass instead of before every draw, and passes each draw's start as its first index; the GPU reads the same indices from the same address (offline Vulkan harness `R2 scratch\rsx_native\dm_bench.cpp`: 0 differing colour/depth bytes, about 13 ns less per draw). `RSX_VPRUN_FAST` is a specialised version of the vertex-program interpreter that DLSS object motion vectors (`RSX_DLSS_OBJMV`) use to find each object's matrix: the same arithmetic in the same order, but only the operands an instruction reads are fetched (differential fuzz over 6 million random programs including NaN/infinity inputs: 0 differences; 1.75x faster). Both take the `[native]` switch values (`1`/`on`/`true`/`yes`, `0`/`off`/`false`/`no`) and are listed in the `[native]` line as `rsx-ibind-skip` and `rsx-vprun-fast`. With `R2_RSX_PROF=1` the `[r2rsx-prof]` memo line also counts the index binds left out; with `R2_RSX_CENSUS=1` an `r9 census draw-call reduction` line shows the share of draws that differ from the previous one only in constants, vertex base or index address, and the share with the same Vulkan state (counts only, nothing is merged). Together about 0.3 ms per frame in R2 heavy scenes with object motion vectors on (about 0.06 ms without).
- `RSX_ATEST_RESAMPLE` (default on; `0` = off): when the upscaler's alpha-test LOD bias (`RSX_AA_MIPBIAS_ATEST`) toggles, the fragment texture units the draw uses re-derive only their sampler from the unchanged descriptor instead of going back through the texture cache. The fallback is the old full re-upload, used for render-target sources, cyclic references, or after any invalidation. Output is identical. With `R2_RSX_PROF=1` the `RSX_SAMPLER_CACHE` line reports the re-uploads avoided per frame.
- `RSX_PIPE_MEMO_WAYS` (default 16; `1` = the old single-entry memo; `R2_PIPE_MEMO=0` turns the memo off): the pipeline memo keeps the last 16 pipeline-cache answers instead of one. A draw whose cache hint still names the same two programs, with identical pipeline properties, reuses the pipeline without the shader-cache lookup. Output is identical, because pipelines and programs live until the cache is cleared, and that also clears the memo.
- `RSX_AA_TEXREAD_MEMO` (default on; `0` = off): the upscaler's per-draw texture-read check computes the sampled addresses once for all of its checks, and its jittered-content check reuses the previous draw's answer when the draw samples the same addresses in the same frame and the set of jittered surfaces has not grown. Same result; `R2_RSX_PROF=1` prints the cost and the hits on a `resolve split` line.
- `RSX_TEX_SEARCH_MEMO_RANGE` (default on; `0` = off): the texture-search memo is invalidated per 1 MB storage block (the block that owns the looked-up address) instead of globally, so the uploads and faults of a busy outdoor frame no longer drop every memoised lookup. Results are unchanged.
- `RSX_TEX_SLOT_MEMO` (default `0` since round 11; `1` = on; `2` = validate): a front memo in `upload_texture` keyed by the raw texture-unit registers (offset, format, address, control1, image rect, control3) plus the resolved address. A repeat answers with the `RSX_TEX_SEARCH_MEMO` entry that hit for the same registers, re-running every check that hit makes (generations, section validity, `address_is_bound`, `sync_protection`), so the attribute derivation and memo hashing are skipped. Round 10 shipped it on; it was turned off after the purple / rainbow bullet-hole debris regression (unproven culprit, the perf win is small). Round-11 hardening: an entry also needs an unchanged global epoch (bumped by every invalidation, page fault, host DMA / blit write, flush, unprotect, purge, trim and cache-tag event), an unchanged surface-cache tag, and the same section lifetime serial and write tag (a reset, re-created, destroyed, dirtied or re-protected section never answers). `2` always takes the full path and compares the memo answer with it. A `[tex-slot-memo]` line every 5 s shows lookups/s, hit %, stores/s, validated/mismatch counts, self-checks and guard refusals.
- `RSX_TEX_SLOT_MEMO_CHECK` (default `64`; `0` = off): with `RSX_TEX_SLOT_MEMO=1`, 1 in N memo hits also runs the full path and compares. The first mismatch logs `[tex-slot-memo] self-check MISMATCH ... memo disabled for this session` and turns the memo off until exit.
- `RSX_OBJMV_ONEPASS_KEEP_DYN` (default `0` since round 11; `1` = the round-10 behaviour): after an object-motion onepass variant draw, keep the dynamic state and index binding instead of a full re-set at the next draw. Turned off with the moving-debris regression (unproven; tiny perf win).
- `RSX_PIPE_SPLIT` (default 0; `1` = on; `2` = on + validate): two-stage split of the per-draw r2aa work. Turns on the `RSX_RECORD_DEFER` lane (unless `RSX_RECORD_DEFER` is set) and moves a depth-writing objmv scene draw's loose key + ordinal and its transform-constant capture onto it, ahead of the classification; rsx::thread only snapshots the key words and the capture inputs. Exact: every r2aa entry point joins the lane first, and nothing writes the registers between `r2aa_on_draw` and the draw's own `pre_draw` join. `2` derives the expected loose key, ordinal and constant hash on rsx::thread and compares them at the join. A `[pipe-split]` line every 5 s (with the objmv2 line) shows draws/frame moved, us/frame moved off rsx::thread, stage-2 busy % and stalls. Vulkan recording is stage 2 via `RSX_RECORD_THREAD`.
- `RSX_SPLIT2` (default 0; `1` = on; `2` = on + validate): stage 2 of the r11 rsx::thread split (`VK\VKSplit2.h`). The transform-constant UBO fill of `load_program_env` (REGS -> mapped ring, ~2-3 KB per draw) runs on an ordered worker thread; rsx::thread still allocates, maps, windows and memoizes the range. Joins: before any queue submit (so before every label/report/flip/readback/texture-cache flush reaches the GPU), before any transform-constant write, before a ring heap is unmapped (grow/destroy) and at exit. `2` hashes the bytes the inline path would write at the kick and compares them with what the worker wrote. `RSX_SPLIT2_SPIN_US` (default 200) = worker spin before sleeping. `[split2]` line every 5 s: jobs/KB per frame, ms/frame moved, joins/stalls per frame by reason, ring-full stalls, validated/mismatches.
- `RSX_FIFO_HOOKS_FAST` (default on; `0` = off): the FIFO method loop tests all of its debug hooks (draw log, frame capture, draw flattener, feature coverage, profiler) with one combined branch per method and skips them together when none is active. With `R2_RSX_PROF=1` the profiler's FIFO counters are plain single-writer stores instead of locked atomics, and `R2_RSX_CENSUS=1` adds a per-register handler-time census and a housekeeping split (context, local tasks, zcull, labels, host DMA) to the RSX summary.
- `RSX_VK_PUSH_DESC` (default `0`; `1` = on, opt-in A/B): the game shaders' fragment descriptor set is pushed per draw with `VK_KHR_push_descriptor` instead of being allocated from a pool, written and bound. It needs device support and a set within `maxPushDescriptors` (otherwise the pool path is used), and it works with `RSX_DLSS_OBJMV=1` one-pass mode: the velocity variant re-pushes the draw's last fragment writes with its own layout instead of binding the set by handle (log `objmv onepass: N draws re-pushed their fragment descriptor set`; `RSX_VK_PUSH_DESC_ONEPASS=0` = old rule, push descriptors off with one-pass). A Fossilize cache recorded with it on skips those layouts when replayed with it off.
- `R2_DMA_INLINE_MAX=<bytes>`, `R2_OM_FASTHASH=1` — RSX DMA copies up to this size run directly on the RSX thread instead of waking the Offloader thread (default `0` = the upstream 3.5 KB limit; `65536` was the earlier default); and a cheaper hash for the DLSS object-motion vertex key. Both are off by default since a 2026-11-11 freeze report (RSX FIFO stalled with get ≠ put). They were not confirmed as the cause, but they are only worth about 1 %. The rest of the RSX thread's time is spread over many functions; the profile is in `scratch\r2_hotpath.md` (section 7), and the RSX-thread notes are in `R3 scratch\rsx_thread`. The largest single cost left is DLSS object motion vectors (`RSX_DLSS_OBJMV=0`: 43 → 47 fps in the airfield fight, at some DLSS quality cost).
- `R2_HOT_NATIVE` (default on since round 8; `R2_HOT_NATIVE=0` runs all translated code as before; small gain, ~57-85 ms of PPU time per 10 s; 320k-case difftest 0 failures) — the game's own memcpy, memset, strcmp, strlen, strcpy, memcmp and its signed string compare (`0x006BB908`) run as native host code when the call is in the plain case (no overlap, ordinary guest memory, no SPU-reserved destination line); otherwise the translated code runs. Since the native-hot pass five engine leaves are on too (difftest 0 failures, injected mutations caught): the 192-bit bitmap scan `0x00AF2700` (~1.9 % of the main thread), the u16 min helpers `0x0079F394` (in the main thread's SPU-job wait) and `0x00B15354`, and the gcm SET_TEXTURE / 4x4 constant-load command writers `0x00A92CDC` / `0x00AD74F4`. With it on, `R2_HOT_MEMCPY=0`, `R2_HOT_MEMSET=0`, `R2_HOT_STRCMP=0`, `R2_HOT_STRLEN=0`, `R2_HOT_STRCPY=0`, `R2_HOT_MEMCMP=0`, `R2_HOT_GSTRCMP=0`, `R2_HOT_BITSCAN=0`, `R2_HOT_MIN6=0`, `R2_HOT_U16MIN=0`, `R2_HOT_GCMTEX=0`, `R2_HOT_GCMVPC=0` turn them off one at a time. One call in `R2_HOT_SAMPLE` (default 4096) runs both versions and compares them (not the gcm writers, which advance the command pointer); a mismatch is re-run on both sides, and only a confirmed one (each side repeats its own result) turns that routine off for the rest of the run, while one caused by memory changing under the check (SPU-written job counters) is only counted as `race=`; every 10 s `[hot]` lines give calls, the native share, cycles per call translated vs native, the estimated time saved and any mismatch (diagnostic: only with `R2_HOT_LOG=1`). Details: `scratch\r2_hotpath.md`.
- `R2_NATIVE_AUDIO_JOB` (default on since round 8; `R2_NATIVE_AUDIO_JOB=0` runs only the translated SPU code, as before) — nine leaf routines of the SPU audio synth job (resampler, (de)interleave, four allocators, two ring-buffer copies) run as native code, 3.4-6x faster per call, about 13 % of the synth lane's time. Each call declines to the translated code when its inputs are outside the verified cases. Offline: 20000 fuzz cases per kernel with 0 mismatches, 540/540 injected faults caught. `R2_NATIVE_AUDIO_MASK=0x7F` leaves the two ring copies to the translated code. `R2_NATIVE_AUDIO_VERIFY=1` runs both and compares; `R2_NATIVE_AUDIO_STATS=1` prints counts.
- **Native replacements at a glance:** one start-up log line lists which native (hand-written C/C++) replacements are on and which are off, with the switch that controls each, in the same format in all three Resistance ports: `[native] on: hot-ppu(R2_HOT_NATIVE) spu-jobs(R2_NATIVE_JOBS) audio-jobs(R2_NATIVE_AUDIO_JOB) edge-zlib(PORT_NATIVE_EDGE_ZLIB) detile-fast(RSX_DETILE_FAST) water-jobs(R2_NATIVE_JOBS_WATER) ...` (edge-zlib and water-jobs are kernels of spu-jobs; they show their effective state after `R2_NATIVE_JOBS`, `R2_NATIVE_JOBS_MASK` and the build (AVX2) are applied; a switch that is set but overridden by another one is shown as `(<switch>,overridden)`). The module-specific lines (`[hot]`, `[native-jobs]`, `[naudio]`) follow with the details.
- `SPU_ASYNC_INTERP` (default on) — an SPU task whose image has no translated code now runs in the SPU interpreter instead of being dropped (a dropped task leaves its PPU waiter blocked). The log shows `async dispatch MISS` followed by `-> running ... interpreted`. `SPU_ASYNC_INTERP=0` drops it as before.
- `PORT_HIRES_SLEEP` (default on) — the runtime's 1 ms naps (SPU interrupt and mailbox waits, SPU group start, SPURS job-guard and queue waits, timed mutex locks) use a high-resolution waitable timer, which wakes after about 1 ms instead of at the next 1–2 ms scheduler tick. `PORT_HIRES_SLEEP=0` uses plain `Sleep(1)`.
- `PS3_EXIT_CRT` (default unset) — when the game exits, the port flushes output and ends the process at once (`ExitProcess`) instead of running the C runtime's exit handlers, which could hang while game threads were still running. `PS3_EXIT_CRT=1` uses the old `exit()` path. PGO builds set it automatically so their profile is written.
- `SPU_PROF=1` (also on with `R2_RSX_PROF=1`) — every 5 s, a `[spu-prof]` line per raw SPU and for the SPURS/thread SPUs: % of time in channel waits (spin / sleep split), GETLLAR (and lock-free share), PUTLLC (and fail %), DMA commands and MB/s, channel runtime calls and indirect branches per second.

Not done, and why: large pages for guest memory (the 4 GB guest reservation is committed lazily on fault and the RPCS3 texture cache write-protects single 4 KB guest pages, neither of which works on 2 MB large pages; large pages also need the *Lock pages in memory* right). Running SPU jobs in parallel (the job kernel runs a job list in order and jobs share data; nothing in the image says which are independent). The main thread's SPU-wait spin (`r2_spin_relax`) is unchanged: main has its own core, so it only shows how long rawSPU0 takes.

**CPU target:** The normal `build.bat` build compiles the lifted PPU/SPU code for x86-64-v3 (AVX2, FMA, BMI2: Intel 4th gen / AMD Ryzen or newer) and the runtime and hand-written code for x86-64 + SSE4.1 (CMake `PORT_ARCH=mixed`, the default). FMA contraction is off everywhere (`-ffp-contract=off`), so the lifted float results match the PS3's separate multiply and add. At start the exe checks the CPU and, on one without AVX2, shows "This build cannot run on this processor" with the hint to build the variant without AVX2 instead of crashing (on a CPU without SSE4.1, which no build supports, it says the processor is below the minimum instead; `PORT_CPU_CHECK=OFF` drops the check). `build_cpu.bat baseline` builds the variant without AVX (x86-64 + SSE4.1, `PORT_ARCH=baseline`; its start-up check asks for SSE3, SSSE3 and SSE4.1) into `build_baseline\`; setup builds it by itself on a CPU without AVX2 that has SSE4.1, and the launcher then starts it (`PORT_CPU_V3=0`). `build_cpu.bat` (`PORT_ARCH=AVX2`) also builds the runtime and hand-written code for x86-64-v3.

**Renderer (rpcs3_rsx) code generation:** `build.bat` builds the RPCS3 renderer library with `/GS- /Gw`, `-march=x86-64-v3 -mno-fma` (AVX2 without FMA; the exe already needs AVX2) and ThinLTO (`-flto=thin`); the runtime and hand-written code get `/GS- /Gw` too (CMake `PORT_GS_OFF`). `/fp:precise` stays. Without LTO these produce exactly the float results of the old generic build: `-mno-fma` keeps clang-cl's `a*b+c` contraction folded fused at compile time and run as a separate multiply and add at run time. **ThinLTO and PGO builds of the renderer have the same semantics as /O2 with `-ffp-contract=on`, but are not guaranteed bit-identical** to the non-LTO build: a cross-file inline that turns an `a*b+c` into constants is folded fused, where the non-LTO build computed it unfused (a probe showed 1.49e-8 vs 0). port_dlss_quality's tests pass through the ThinLTO link. For a strictly identical renderer, `set PORT_RSX_LTO=0` before `build.bat` (and do not use the PGO builds); `set PORT_RSX_ARCH=generic` restores the old CPU target. `build_cpu.bat` builds a matching renderer per mode (`build_rpcs3_generic`, `build_rpcs3_pgo_gen`, `build_rpcs3_pgo_use`).

## Audio

When the frame rate drops, the game's own audio mixing (on the recompiled PPU/SPU threads) can fall behind real time. The port therefore keeps a buffer of mixed audio between the game and the sound card, as RPCS3 does with its "audio buffering" and "time stretching" options:

- **Buffer:** mixed audio goes into a ring buffer with a target of `PORT_AUDIO_BUFFER_MS` (100 ms by default). The sound card is kept topped up from it, about 30 ms at a time.
- **Time stretching:** when the buffer drops below `PORT_AUDIO_STRETCH_THRESHOLD` % of the target, playback slows down through [SoundTouch](https://www.surina.net/soundtouch/) without changing the pitch, so a slow stretch of frames sounds slightly slower instead of gapping. Tempo returns to 1.0 as the buffer refills.
- **Underrun:** if the buffer still runs dry (a hitch longer than the buffer), the last few milliseconds fade out to silence and fade back in when audio returns. No repeated blocks, no clicks.
- **Mixer thread:** runs at TIME_CRITICAL priority with Windows MMCSS "Pro Audio" scheduling. It also stays off the cores reserved for the main game thread, the RSX thread and rawSPU0 (`PORT_MAIN_CPU`, `PORT_FIFO_CPU`, `PORT_SPU0_CPU`).
- **Late game audio:** when the game's next block of audio has not been written in time, the mixer waits up to `PORT_AUDIO_LATE_WAIT_MS` (22 ms) for it. The game's audio clock slips slightly and the buffer absorbs the slip.

| `PORT_DIALOGUE_DIAG` | `0` | One `[dialogue]` line in `logs\run.log` per movie opened (system language, fallback decision, the audio tracks on the disc, which voice tracks were renamed) and per audio port opened (channel count and how it is folded to stereo: centre x0.707). For reports of cutscenes without dialogue. `1` = on. |
| `AUDIO_FILL_MAX_BLOCKS` | `4` | A late block is bridged by repeating the last 5 ms of audio for at most this many blocks, with the last one fading out. `24` = the old length, which could buzz. |
| `PORT_AUDIO_LOG` | `5000` | Period of the `[audio]` log line in ms. `1` = every second (also with `R2_RSX_PROF=1`), `0` = off. |
| `PS3_THREAD_SLOT_FIX` | `1` | Shared with the R1 / R3 ports: a thread that ended through `sys_ppu_thread_exit` while another thread was already waiting to join it could keep its slot in the 64-entry thread table for good, until thread creates failed and the game waited for a thread that never started (R1 issue #17: black screen after a cutscene). A refused thread create is now logged (`[SYS] sys_ppu_thread_create ... FAILED: all 64 thread slots in use`). `0` = the old behaviour. |
| `PS3_PPU_HW_ESTIMATE` | `0` | `1` = the PowerPC `fres` / `frsqrte` reciprocal estimates return the PS3's table values (bit for bit as RPCS3's interpreter and LLVM recompiler). Off by default: with them, vegetation shimmers with DLSS frame generation on. `0` = the exact `1/x` and `1/sqrt(x)`. Logged at start: `[ppu-fp] ...`. |
| `PS3_PPU_FMADDS_INTERP` | `0` | A/B test for the Holar Tower checkpoint. `1` = `fmadds` rounds `a*c` to double before the add, as RPCS3's PPU interpreter does (the PS3 and RPCS3's LLVM recompiler fuse them, the default). |
| `R2_LUA_LOG` | `0` | The level scripts' progress messages (their `prt()`, silent in the retail game) as `[lua] ...` lines in `logs\run.log`; the last one shows which step a stuck level last reached. Repeats are counted, at most 20 lines a second and 5000 a run. `1` = on. |
| `R2_HOLAR_ASSIST` | `1` | Holar Tower elevators that wait for the whole crew: the lobby elevator, the node shaft elevator after the first Titan of the battlefield, and the ride back down after the second Titan. Every 15 s, starting 15-20 s after the script sends the crew there, each one not in place yet gets the script's order again; if some are still missing 60 s after the order and Hale has stood in place for 6 s, they are moved there; if the check still fails 10 s later, the elevator is started the way the script does. At the node shaft it also moves on if the first Titan has been dead for 2 min but the remaining-hybrids check still fails, if the leaper check still fails 5 min after the second Titan, or if the "are we clear" dialogue never gives the order to go down. Added in memory to the retail `iceland2_seg7_b` and `iceland2_seg9` scripts, text or compiled (`.lc`) form (left alone if a file differs). Logged as `[holar-assist] ...`. `0` = off. |

**Reading the log.** At start-up, `logs\run.log` shows `[audio] output: ... SoundTouch stretch (...)` with the MMCSS state and the mixer thread's affinity. Every 5 seconds there is a line like:

```
[audio] 5.0 s: buffer min 82 avg 101 ms (target 100) | tempo min 1.00 avg 1.000 (stretched 0%) | underruns 0 (silence 0 ms, device dry 0) | ...
```

- `buffer min` well above 0 and `avg` near the target: healthy.
- `tempo min`/`avg` below 1.00 and `stretched` above 0 % during a frame-rate drop: the stretcher is covering it. Tempo should be back to 1.000 within a second or two.
- `underruns` and `device dry` should stay at 0. A non-zero count means a hitch longer than the buffer; try a larger `PORT_AUDIO_BUFFER_MS`.
- `ring overflow` at the end: the game produced audio faster than it was played, so the oldest audio was dropped (harmless after a long pause).

The offline test for this stage is `ps3recomp\libs\audio\tests\test_audio_out.cpp` (part of `scratch\enginetest\run_all.ps1`).

## Steam Deck / Linux

The port is a Windows program. On Linux and the Steam Deck it runs through Proton (Wine). This has not been tested on a real Deck yet, so treat it as experimental.

1. Build the port, either on Linux itself with `setup_linux.sh` (see [Building on Linux](#building-on-linux-experimental) below), or on a Windows PC with Setup (no file picker is needed: the installer and Setup find the game on their own, or take a typed path). If you built it on another PC, copy the whole port folder to the Deck, for example to `/home/deck/Games/Resistance2Port` (or a microSD card). Setup.exe / Setup.bat themselves do not run under Wine or Proton (they need Windows PowerShell and Visual Studio).
2. In Desktop Mode, open Steam → **Games → Add a Non-Steam Game to My Library…**, click **Browse**, and pick `Launcher.exe` in the port folder.
3. Right-click the new entry → **Properties → Compatibility** → tick **Force the use of a specific Steam Play compatibility tool** and choose **Proton Experimental** (or Proton 9.0 or newer).
4. Launch options are not needed. `SteamDeck=1 %command%` forces the Deck preset on other Linux PCs.

What the port does under Proton:

- The launcher detects Proton and the Deck (its hardware line says `Steam Deck` or `Wine / Proton`). On the Deck, **Auto-detect** picks a Deck preset: PS3 resolution, FSR 1 scaling to a 1280x800 window, 30 fps.
- **Preset: Steam Deck** (launcher, the *Recommended for your PC* panel): battery-friendly handheld settings on any PC — the Deck recommendation (PS3 resolution, FSR), **40 fps** (set the Deck's screen to 40 Hz), 30 fps menus, a 1280 x 800 window, 150 % UI scale and Xbox button prompts. The Deck is detected by `SteamDeck=1` (set by Steam), the APU name, or (Windows on a Deck) the SMBIOS board name `Jupiter` / `Galileo`; there the 40 fps / 1280 x 800 choices appear and 1280 x 800, 150 % UI and Xbox prompts become the defaults.
- The frame rate list gets a **40** option. Set the Deck's screen to 40 Hz (Quick Access → Performance) to match it. The window list gets **1280 x 800** (the Deck's screen).
- DLSS is not used under Proton; choose FSR instead. The Vulkan renderer runs on the Deck's own Vulkan driver.
- In the launcher, the controller's **A** or **Start** button starts the game. In game, Steam Input presents the Deck's controls as an Xbox controller.
- The update check works the same way and can be turned off in the launcher.

### Building on Linux (experimental)

`setup_linux.sh` does what Setup does, natively on Linux and without PowerShell: it checks and copies your game, decrypts the program file, generates the game code, downloads and patches RPCS3's renderer source (with git) and builds the same Windows programs with LLVM (clang-cl and lld-link). The Windows headers and libraries (Microsoft's C runtime and the Windows SDK) are downloaded from Microsoft with [xwin](https://github.com/Jake-Shadle/xwin) into `tools_cache/msvc_linux`, after you accept Microsoft's licence. You then play the result through Proton as described above. It has been checked less than the Windows setup, so please report problems with `logs/setup_linux.log`.

1. Install the tools (LLVM 22 or newer is recommended; with older LLVM the PGO profile is skipped and the game runs a bit slower):
   - Arch: `sudo pacman -S --needed python cmake ninja clang lld llvm git curl 7zip`
   - Fedora: `sudo dnf install python3 cmake ninja-build clang lld llvm git curl 7zip`
   - Debian / Ubuntu: `sudo apt install python3 python3-venv cmake ninja-build clang lld llvm git curl 7zip` (LLVM 22 from [apt.llvm.org](https://apt.llvm.org) if your release has an older one)
2. Get the port (git clone or the source zip) into a folder with about 35 GB free, then run:
   ```
   ./setup_linux.sh --game "/path/to/Resistance 2 [BCES00226].iso"
   ```
   `--game` takes a decrypted .iso or a folder with `PS3_GAME` in it (for example from RPCS3's `games` folder). UDF disc images are unpacked with 7-Zip. Other options: `--jobs N` (fewer compile jobs if you have little RAM: 16 GB → 4, 8 GB → 2), `--check-only`, `--nopgo`; `./setup_linux.sh --help` lists them all.
3. Later rebuilds (after `git pull`): run `./setup_linux.sh` again (it regenerates the game code only when the code generator changed), or `./build_linux.sh` for a build only.

Steam Deck: SteamOS's system folders are read-only, so install the tools inside a [distrobox](https://distrobox.it/) container (for example Arch) and run `setup_linux.sh` there, or build on another Linux PC and copy the folder over. The build takes a long time on the Deck's 4 cores.

Not on Linux: NVIDIA DLSS / DLSS Frame Generation and Intel XeSS are not set up (Proton does not offer DLSS to the port; FSR 3.1 is used), and the launcher's **Update now** is not offered under Proton (the updater is a Windows PowerShell script): update with `git pull` and `./setup_linux.sh`, or the new release's source.

## Status

This is a work in progress, tested on a single PC.

- Runs at a steady 60 fps in most places on my PC; the biggest fights are CPU-bound and can drop to the high 30s, and level streaming can dip briefly lower.
- Performance is mostly limited by the game's SPU job system, so a decent CPU helps most.
- Performance fixes have been applied as far as I realistically could, on the CPU and render-thread side. In the first heli level (1080p internal, DLSS to 4K), the render thread went from about 30 fps to an average of about 54 fps (it was 30 because it waited on ZCULL occlusion queries). It now spends about 9 µs per draw at about 1,250 draws per frame. ZCULL reads no longer stall (`R2_ZCULL=sync` restores the strict behaviour). The game's own main PPU thread and SPU jobs are now the limit.
- The renderer recovers from a corrupt RSX command stream instead of freezing (it logs `FIFO: recovering` to `logs\rpcs3_rsx.log`).
- There are occasional freezes and other bugs.

If you hit a problem, let me know how to reproduce it, and if you can, send the log from the `logs\` folder for that session (the launcher has a button for it). That helps a ton.

## Known issues

- Occasional freezes. One cause (an SPU job jumping to an empty command slot, which showed up more often at 60 fps) has a workaround; there may be others.
- 60 fps and timing:
  - The game's own clock runs on real frame time, clamped to 0.08 s per frame.
  - Physics runs at a fixed 60 Hz step and carries the remainder over, so its speed is correct at any frame rate. Above 60 fps it still updates at 60 Hz, with no interpolation, so it can look slightly juddery.
  - Cutscene and keyframe timers convert 30 fps key frames to seconds, so they keep their speed.
  - The few frame-count timers that assume 30 Hz are scaled; see `R2_PATCH_TIMING_FRAMECOUNT` above.
  - Many AI and level-of-detail updates are staggered over N frames, so they run more often at 60 fps. That costs CPU but doesn't change game speed.
  - RPCS3 users report brighter lighting/bloom in some spots at 60 fps. The game's PowerPC code has no exposure or eye-adaptation logic, so the cause is probably in SPU or GPU-side lighting. It isn't fixed. If it bothers you, use 30 fps in the launcher.
- With DLSS, blob shadows under moving pickups can still trail a little, and some foliage and wire fences can still shimmer.
- Heavy fights are CPU-bound (high 30s in the biggest ones on a mid-range CPU). Frame Generation (launcher → Upscaling & Frame Gen) can help here.
- **Frame Generation is experimental** (DLSS on RTX 40/50, FSR 3 elsewhere; off by default). Known artifacts: jitter on grass / vegetation and around doors and entrances, some ghosting, HUD or menu artifacts; fixes are planned for an upcoming hot patch. Reports are welcome.
- **Changing Frame Generation in-game** can double the sound and then leave constant static. Change it in the launcher, or restart the game after changing it.
- Exclusive fullscreen can give black F12 screenshots. Use borderless.
- Some streaming sound/dialogue files that the EU disc doesn't have show "open FAIL" lines in the log. That's harmless.

## How it works

- `ps3recomp/` is a modified copy of [ps3recomp](https://github.com/sp00nznet/ps3recomp) by sp00nznet (MIT licence). It holds the runtime, the PS3 system libraries (audio, input, file system, SPU scheduling) and the lifters that translate PowerPC and SPU code into C/C++.
- Graphics: the game's RSX command stream is fed to RPCS3's RSX core and Vulkan renderer, built as a library. This repository only contains the patch to RPCS3 (`ps3recomp/patches/r2-rpcs3.patch`); Setup downloads the original source and applies it. The patch adds DLSS / FSR upscaling, display modes and fixes for running outside the emulator.
- `project/` is the game-specific part of the port: its hooks, the 60 fps limiter, mouse look, the launcher and the DLSS bridge.
- `tools/art/make_r2_art.py` draws the installer's wizard artwork (original, Python + Pillow); `tools/installer/make_wizard_images.py` sizes it for Setup.
- `tools/r2_regen.py` runs the lifters on your decrypted `EBOOT.elf`, then re-applies this port's own edits to the generated code (`tools/hooks/`).

## GPU offload switches

Graphics work runs on the GPU and game logic runs on the CPU. At startup the game prints one `[gpu-offload] <name> ON` line for each GPU path that is active.

| Variable | Default | What it does |
|----------|---------|--------------|
| `RSX_GPU_TEXDECODE` | 1 | Texture deswizzle/byteswap runs in a compute shader (images of 1 KB and up). Set 0 to decode on the CPU. |
| `RSX_TEXDECODE_LINEAR_CPU` | 1 | Linear (non-swizzled) textures byteswap on the CPU even when `RSX_GPU_TEXDECODE` is on. Set 0 to send them through the compute shader too. |
| `RSX_TEX_PAR_CONV` | 0 | Experimental. 1 = the CPU copy/conversion of a texture upload's mip levels, faces and slices (and large single copies, in 256 KB pieces) runs on a few worker threads; same bytes, same order, finished before the upload's copy commands are recorded. |
| `RSX_TEX_PAR_THREADS` | min(4, CPUs/3) | Threads for `RSX_TEX_PAR_CONV`, the RSX thread included (1 = off). |
| `RSX_TEX_PAR_MIN_KB` | 256 | Uploads with less guest data than this stay on the RSX thread. |
| `RSX_TEX_PAR_SPIN_US` | 200 | Worker threads poll this long for the next job before sleeping. |
| `RSX_GPU_BLIT` | 0 | Scales blits on the GPU (RPCS3 "GPU texture scaling"). |
| `RSX_GPU_TEXSTREAM` | 0 | Uploads textures on an asynchronous streaming queue. |
| `RSX_RECORD_THREAD` | 0 | Experimental. `1` = the RSX thread captures its Vulkan draw commands (vkCmd* calls and descriptor updates) into a ring and an "rsx record" thread records them into the command buffer. Command-buffer begin/end/submit, object destruction, descriptor pool resets, the flip and the upscaler drain the ring first. `2` = validation: same capture path, replayed on the RSX thread (no second thread). |
| `RSX_RECORD_RING_MB` | 16 | Size of the record ring (2-256 MB). |
| `RSX_RECORD_SPIN_US` | 250 | How long the record thread spins for new commands before it sleeps. |
| `RSX_RECORD_STATS` | 1 | With `RSX_RECORD_THREAD` set, prints a `[rec]` line every 5 s: packets, fallbacks, drains by reason, ring stalls and record-thread busy %. `0` = off. |

Vertex fetch (vertex shader) and tiled-surface detile (compute) are always on the GPU.
